# 纯 C Win32 进程挂钩库

M0 T21 S26 将已存在的普通进程 DLL 安装、跨位宽协调和进程内函数挂钩能力提炼为项目中立的 `src/lib-win32/process-hook`。调用方持有目标进程和失败回滚，决定 DLL、载荷、CreateProcess 语义与业务回调；库不依赖样式、NTVDM 或另一个仓库。

提取现有的同宽和跨宽挂起目标、调用方载荷、原函数 trampoline、错误与资源管理能力；隔壁 NTVDM64 所需的仅载荷、不安装 DLL 能力不在本项目现有实现中，本次不新增。纯 C17、x86/x64 与现有四产品约束不变。按许可保留 MinHook/HDE 原文。先审计所有实际调用和已测行为，再迁移唯一实现；不复制第二套生产逻辑。

现有 startup transaction 只适用于未交付的新进程，late patch 明确不实现已安装钩子的物理移除。本 S 提取已有晚期安装和清理能力，不新增物理移除能力；区分逻辑停用、事务回滚、未安装资源释放与已安装钩子移除。全局业务不纳入本 S 的重构范围。

设计目标是两个项目最终使用逐字节相同的库源码并让隔壁移除 Detours C++ 依赖。隔壁此次仅只读参考：其启动器 payload-only、载荷查找与恢复、跨宽 helper 和 NTHook CreateProcess 事务均需明确映射；最终可替换性需隔壁实际构建及原生回归，不能由本项目测试推断。

当前静态库包含挂起进程的导入表 staging 和载荷回读/恢复、跨位宽的 rundll32 交接、启动期 MinHook trampoline 事务，以及现有晚期 patch/guard 原语。载荷的解释、目标 DLL 的选择、CreateProcess 策略与产品初始化仍由调用方承担。跨宽交接沿用 DLL 的 ordinal 1 入口和原有超时协议，不能假定其他项目无需适配即可使用。

启动事务只适用于应用入口之前；提交后保留 trampoline，回滚失败时沿用原有的进程终止策略。晚期 guard 不阻止线程创建，也不证明回调已静止；安装后的 trampoline 保留，不能将 discard 等同于卸除已安装的钩子。隔壁的兼容性及完整 Detours 等价性均未验证。全局业务、其专用导入表操作和产品的 PE/路径校验仍留在调用方。

S27 在实现并验证纯载荷入口：由与目标同宽的安装方对新建挂起目标暂存数据，不增加 DLL 导入；目标自身链接该库，在系统加载器完成之后读取并恢复，释放暂存分配。跨宽纯载荷协调、Detours GUID 载荷协议、隔壁消费者适配及兼容验证不在此入口的已验证能力内。
