# 代码质量治理

用户准入 M0 T24：以第一性原理和 SoftPC 的通用质量原则为参考，减少代码足迹，追求极简、统一、宏观清晰、扁平控制流和有实际收益的复用。现有产品行为与责任边界必须保留；不为了形式统一而抹除真实平台差异或有效契约。

用户要求最终代码总量至少净减少数千行，以可审计的基线与 Git 差异统计；通过合并重复实现和删除无必要层次实现，不依靠压缩排版、删除必要测试或削减现有能力凑数。最终分别报告生产与测试代码的增删净值和功能验证。

错误规则：最内层能完整解决的就地解决；否则保留原始错误向外传播，由最外层决定报告或结束。中间层只释放自身资源并传播，可补充上下文，不重复报告、吞错或擅自重试降级。既有不可改变的公开接口和必要的系统回调边界应明确记录，不强行虚构统一异常机制。

## 顺序与退出条件

1. S1 冻结当前 main 生产代码及测试、构建入口的覆盖清单；按模块、调用链和错误所有权审计，先列证据、优先级、保留理由和可验证的处置方案。外部导入代码以来源和边界审计为主，不做无收益格式化。
2. 后续 S 按 S1 的实际发现和 ROI 顺序治理：优先错误传播及生命周期、重复实现和不必要的接线，再处理状态边界与可读性。每项都确认真实调用者和行为，合并实现而非增加转发层；具体顺序以 S1 证据决定。
3. 最终 S 对冻结清单逐项复核，列出已修复、保留的必要差异、无法处理及其原因；核对双位宽和实际包回归、性能与行为边界、发布和远端提交。不以文件数量、行数或测试数量单独证明质量，也不把未覆盖项称为通过。

全程保持 M0、C17、GCC/Ninja/ccache 和四产品文件；用户数据、资源、来源声明和既有可用行为不变。每次测试结束清理本次不再需要的 scratch；不得修改兄弟仓库，也不将其作为构建依赖。
