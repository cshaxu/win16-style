# M0 T18 S64: Delphi data-aware sample discovery

The official tDBF project publishes [demo 1.3.6](https://sourceforge.net/projects/tdbf/files/TDbf%20Demo%20App/TDbf%20Demo%201.3.6/). Its `tdbfdemo136.zip`, fetched into the registered `build/t18-s64-vb-mask-survey` scratch via the download page's actual mirror URL, has SHA-256 `4c1df83d1e07243cc7315f1759c5d6217408fb0ef0a4c919213af436499ef176`. The ZIP includes source, Delphi form resources, a GPL COPYING file and example DBF files, but no executable. `demo/simple.pas` declares eight `TDBEdit`, one `TDBGrid` and three `TDBNavigator` controls; its form resource contains the corresponding classes. Other forms also contain `TDBGrid` and `TDBNavigator`. The sample is a lead for a realistic data-bound probe, not a runtime witness; it has not been executed, copied into product source or used as a dependency.

An initial download response and a direct mirror response were HTML, not ZIP archives; neither was executed. The actual archive was identified by its PK signature and inspected as a ZIP. No `dcc32.exe` or `dcc64.exe` command was present on PATH and the checked standard Embarcadero/Borland program directories were absent. This is not an exhaustive compiler search. Next find an author-provided executable or a legitimately available Delphi environment, then use only isolated copies of the included data and verify native EDIT forwarding, data binding and behavior before considering a class candidate. No third-party code has been imported; no product source or binary changed.

## Self-contained real TDBGrid sample

[BabbageCom/DelphiGridTest](https://github.com/BabbageCom/DelphiGridTest) commit `2cebf3989f5cc79cf73a04f82474d7f490f73638` provides source, an x86 PE executable (`Project1.exe`, SHA-256 `b9bfdf29ac32803546837bcf9e601cec9700313a687dc07a36ecfbde71bcd4b9`) and sample XML. The source includes MIDAS statically and binds a `TDBGrid` to `TClientDataSet`; it resolves `my_xml.xml` in the process current directory. Its explicit merge/save button writes that file, so tests use only the copied scratch data and do not click that button. The source also offers a combo box for themed, classic and gradient drawing styles. No source is imported into the product.

A self-owned native driver started the released `assets/run16s.exe` and that executable with the copied sample directory as current directory. The shown `TForm1` had a visible `TDBGrid` child, x86, `style=54310000`, `ex=00000200`, and a normal target exit code 0; a private-desktop `PrintWindow` capture was saved in registered scratch. This proves the sample is runnable and the grid exists, not that the style DLL attached to the grid or changed its drawing. Two temporary in-process observer DLLs were successfully set as target-thread hooks but neither reported readiness within two seconds, and the self-owned job reclaimed those failed runs. The cause has not been established; no attachment or rendering result is inferred from these timeouts. Subsequent work needs an observer with independently proven loading/readiness, an original/style pixel and content comparison, input/data-binding restoration and negative tests.

A separate X-DBData vendor demo ZIP (SHA-256 `39cfcae2472cc0a1695d6ea6c4f38e68f12363b1e1664498dd47ab539f4a990f`) contains an x86 executable with TDBEdit and related class strings, but its own startup dialog reported `Error loading MIDAS.DLL`; no data-control runtime result was obtained. The initial form-selection attempt observed an invisible form and timed out; a corrected visible-window probe revealed the dialog. Neither third-party binary nor its dependencies are product inputs. The failed runs were confined to owned jobs and scratch.

## Grid print comparison and observer diagnosis

On the same x86 sample, a self-owned native driver compared bare and released-style runs, setting the styled form width eight pixels smaller so both actual grid windows measured 482 by 172. After synchronous redraw, `PrintWindow` captured each grid directly. All 82,904 RGB pixels matched, including the border and interior; both bitmap files had SHA-256 `b51937f9e59a82548b6e88b4dc5c9acd124198588e7b2ba951dd38b72b788551`. In-memory alteration of one RGB pixel produced exactly one difference, validating this comparator's basic negative case. Both targets returned exit code 0. This establishes no visible difference in this specific printed grid sample, not whether an attachment exists, whether on-screen painting differs, or whether other data, style modes and DPI work.

In further isolated attempts the target loaded the assets x86 style DLL. Two observers failed readiness both with and without the style launcher. An explicit remote LoadLibrary of a test observer into the self-owned test process succeeded, confirmed by module enumeration, but neither an installed thread-specific CALLWNDPROC nor GETMESSAGE hook produced the expected ready event. A test-only entry log was absent. The probes timed out and their owned job cleanup ran. This narrows the issue but does not establish why hook callbacks were missing; loaded observer is not evidence of callback initialization. No product hook or global state was changed. The screenshot comparator and observer code are temporary scratch, not yet integrated tests.

## Scratch TDBGrid frame prototype

A scratch-only x86 build from committed project source adds exact `TDBGrid` to the existing same-process, Unicode, same-thread, original-parent and client-edge grid candidate alongside `TValueListEditor`. It retains the existing public scroll-info check and renderer; no production source was changed. This is an experiment, not a new safety contract or deliverable. It was built using the existing MinGW GCC/Ninja/ccache toolchain in registered scratch; two earlier sandboxed configure attempts were interrupted after compiler detection stalled, and the unsandboxed configuration succeeded.

The self-owned x86 `DelphiGridTest` loaded a scratch launcher package containing the prototype DLL and exited 0. Its 482 by 172 direct `PrintWindow` grid capture shows classic vertical and horizontal scrollbar shapes, whereas the equally sized released-style capture did not. There were 11,708 differing RGB pixels, including 1,948 within a three-pixel outer band and 9,760 elsewhere; the latter includes scrollbar areas and potential clipping/layout changes. These are separate runs and cannot prove unchanged cells, successful attachment, or data behavior. The bitmap captures are in `build/t18-s64-vb-mask-survey/grid-proto-styled.bmp` and `grid-equal-styled.bmp`. No runtime-owner, thread-hook initialization, invalid-owner negative, data binding, input, alternate drawing style, DPI, x64 or lifecycle regression is established yet. In particular, earlier observer hook failure remained after a scratch private-desktop variant requested `DESKTOP_HOOKCONTROL`; that result does not establish its cause. Do not publish the scratch DLL. Next obtain same-window or otherwise attributable comparison and prove data/selection and lifecycle before considering production admission.

## TDBEdit: real sample and ANSI forwarding

The X-DBData 3.4 Delphi 7 executable (SHA-256 `6be92634da2fd685839c07d525dcf3ca3ea0d198e13db13d0bbfcdccacc676d9`) is distributed in the [vendor's demo archive](https://www.x-files.pl/download/xdbdata.html). Its archive contains no MIDAS DLL. For research only, an x86 `midas.dll` published by [L4 Sistemas on SourceForge](https://sourceforge.net/projects/l4-sistemas/files/midas.dll/download) was downloaded into the private sample directory. Its SHA-256 `0b0edf7067ecb7a9554ffe5743fb65ba6e25c6407c137cb3657f7b8dd046138e` matched that page; version resources say Borland MIDAS 7.0.4.453 but the file is unsigned and its publisher attribution is not independently verified. Neither file is a product input, system install or dependency.

After adding that private library, the original executable failed on an ISO-format date under the current locale. A same-length literal replacement experiment on a separate scratch executable failed with runtime error 217 and was discarded as evidence. A scratch-only style DLL instead called `SetThreadLocale` to set French Canadian for the target thread before application startup; this changed no Windows global settings and allowed the unmodified original executable to reach its 12-page main form. English Canadian instead failed on a comma-decimal value. These experiments do not establish a product locale fix, and the scratch locale code must not be delivered.

A self-owned, thread-directed native probe selected the second page using tab keyboard messages and observed two visible application-owned TDBEdit windows. The sampled controls had `style=540108c0` (including ES_READONLY), `ex=00000200`, Unicode window flag, and class module and parent class module both at the executable base. Initial addition of exact TDBEdit to the existing scratch Unicode edit candidate and protocol made no difference in the two 91-by-21 printed captures: their SHA-256 was identical. Private scratch instrumentation after the original WM_PAINT showed `candidate=1`, `attempted=0`, and no native W witness. Additional hooked-call diagnostics observed the application module forwarding that paint to the system ANSI EDIT procedure through `CallWindowProcA`; W calls observed for the same window came from USER32 thunks rather than the application module. This identifies a missing ANSI-forwarding witness for this sample; it does not prove every TDBEdit takes that route.

A second scratch-only experiment required the exact TDBEdit role, current paint scope/window, original owner caller and the registered ANSI EDIT procedure before setting the existing edit witness. The private diagnostic then recorded the application owner as witness and attempted=1. Separate 91-by-21 PrintWindow captures differed at 483 RGB pixels: 432 in an outer two-pixel band and 51 in the interior; neither difference nor attempted status alone proves correct binding or all font behavior. One first compilation failed because the scratch helper called a later undeclared function; a subsequent command unintentionally ran the stale previous DLL. That run is invalid and excluded. The corrected scratch build produced the reported results.

The sample's selected edit is read-only; with and without the candidate, a focus-linked message-level `X` then backspace left `Roberto` unchanged. This is not a successful editing, data-binding, physical-input or data-restoration test. Both baseline and candidate processes failed to exit within the driver's 3–5 second close wait and were reclaimed by their own kill-on-close job; clean shutdown and leak behavior remain unverified. The previously observed foreign-thread hook readiness issue also remains. Before any production change, obtain a writable bound TDBEdit or change the sample using its own supported UI, verify selection/edit/post/cancel and cleanup, implement two-width native witness/negative tests, and ensure unrelated ANSI or application-drawn controls are unaffected. No product code or binary changed.
