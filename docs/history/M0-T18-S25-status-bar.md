# M0 T18 S25 — status-bar protocol investigation

The S25 admission follows S24's documented progress-color handoff. The current product has no status-bar renderer: `rg -n -i 'statusbar|status_bar|STATUSCLASSNAME' src tests/ntw16s-dll` found the native demo and an OCX host observer, not a production painter. A Delphi `TStatusBar` must not be accepted from its name alone. A real Delphi status-bar instance and its registration owner have not yet been verified.

A scratch-only, self-owned C witness under `build/t18-s25-status` created a v5.82 native status control on an isolated desktop in each bitness. `SB_SETPARTS`/`SB_GETPARTS` round-tripped two edges, 120 and -1. The first part returned its eight-character ordinary string; the second identified `SBT_OWNERDRAW`, and printing the control caused one parent `WM_DRAWITEM` for item 1 carrying the original `0x12345678` value. Each witness entered and left simple mode and destroyed its windows and GDI objects, and both exited zero. This is a native common-control model, not a real Delphi test or an implemented style.

The first witness version wrongly assumed `SB_SIMPLE` returned a success boolean and failed in both widths after the owner-draw check. Microsoft's [SB_SIMPLE documentation](https://learn.microsoft.com/en-us/windows/win32/controls/sb-simple) says its return value is unused; the revised witness checks `SB_ISSIMPLE` instead. [SB_SETTEXT documentation](https://learn.microsoft.com/en-us/windows/win32/controls/sb-settext) confirms that the parent owns an owner-drawn part. Any eventual adaptation must preserve that callback and its data and cannot assume all parts are ordinary text. At that point the witness had not established v6 behavior, icons, actual VCL ownership, an accessible paint boundary, reentry, DPI or a safe renderer; S25 remains active.

The same witness was subsequently built with an explicit v6 activation manifest and confirmed loaded ComCtl32 6.16 on both widths; it passed the same ordinary/owner-drawn data and simple-mode checks. The linker reported `multiple non-default manifests` despite returning zero; the actual DLL version was read at runtime, so the result establishes the loaded version for this witness, not clean manifest-linking behavior. Each of v5/v6 and x86/x64 was then run bare and through the actual `assets/run16s.exe --wait`: all eight runs exited zero and preserved the owner-draw callback/data. In each styled run the matching assets DLL was loaded, the parent reported attached, and the status HWND reported unattached. The 384-by-24 printed-client pixel hash matched its corresponding bare run (v5 `06c8ae37bf258817`, v6 `a87de33711e3f6a5`). This locates a gap for this native model; a hash comparison is not a universal pixel or VCL assertion, and DLL load alone was not treated as initialization proof. DLL hashes were those in the S24 package record.

An `rg -a -l -F 'TStatusBar' D:/programs -g '*.exe'` search found only the previously indexed JoyToKey and cnc-ddraw configuration executables. Their fixed SHA-256 values remain those in the Delphi audit. All five ASCII matches in each were in the PE `.text` section, not `.rsrc`; their existence does not prove any actual status-bar instance. The programs were not modified or launched for this scan. Real Delphi registration, icons, dynamically changing parts, event reentry and a content-neutral rendering contract still require evidence; S25 remains open.
