# M0 T18 S25 — status-bar protocol investigation

The S25 admission follows S24's documented progress-color handoff. The current product has no status-bar renderer: `rg -n -i 'statusbar|status_bar|STATUSCLASSNAME' src tests/ntw16s-dll` found the native demo and an OCX host observer, not a production painter. A Delphi `TStatusBar` must not be accepted from its name alone. A real Delphi status-bar instance and its registration owner have not yet been verified.

A scratch-only, self-owned C witness under `build/t18-s25-status` created a v5.82 native status control on an isolated desktop in each bitness. `SB_SETPARTS`/`SB_GETPARTS` round-tripped two edges, 120 and -1. The first part returned its eight-character ordinary string; the second identified `SBT_OWNERDRAW`, and printing the control caused one parent `WM_DRAWITEM` for item 1 carrying the original `0x12345678` value. Each witness entered and left simple mode and destroyed its windows and GDI objects, and both exited zero. This is a native common-control model, not a real Delphi test or an implemented style.

The first witness version wrongly assumed `SB_SIMPLE` returned a success boolean and failed in both widths after the owner-draw check. Microsoft's [SB_SIMPLE documentation](https://learn.microsoft.com/en-us/windows/win32/controls/sb-simple) says its return value is unused; the revised witness checks `SB_ISSIMPLE` instead. [SB_SETTEXT documentation](https://learn.microsoft.com/en-us/windows/win32/controls/sb-settext) confirms that the parent owns an owner-drawn part. Any eventual adaptation must preserve that callback and its data and cannot assume all parts are ordinary text. At that point the witness had not established v6 behavior, icons, actual VCL ownership, an accessible paint boundary, reentry, DPI or a safe renderer; S25 remains active.

The same witness was subsequently built with an explicit v6 activation manifest and confirmed loaded ComCtl32 6.16 on both widths; it passed the same ordinary/owner-drawn data and simple-mode checks. The linker reported `multiple non-default manifests` despite returning zero; the actual DLL version was read at runtime, so the result establishes the loaded version for this witness, not clean manifest-linking behavior. Each of v5/v6 and x86/x64 was then run bare and through the actual `assets/run16s.exe --wait`: all eight runs exited zero and preserved the owner-draw callback/data. In each styled run the matching assets DLL was loaded, the parent reported attached, and the status HWND reported unattached. The 384-by-24 printed-client pixel hash matched its corresponding bare run (v5 `06c8ae37bf258817`, v6 `a87de33711e3f6a5`). This locates a gap for this native model; a hash comparison is not a universal pixel or VCL assertion, and DLL load alone was not treated as initialization proof. DLL hashes were those in the S24 package record.

An `rg -a -l -F 'TStatusBar' D:/programs -g '*.exe'` search found only the previously indexed JoyToKey and cnc-ddraw configuration executables. Their fixed SHA-256 values remain those in the Delphi audit. All five ASCII matches in each were in the PE `.text` section, not `.rsrc`; their existence does not prove any actual status-bar instance. The programs were not modified or launched for this scan. Real Delphi registration, icons, dynamically changing parts, event reentry and a content-neutral rendering contract still require evidence; S25 remains open.

An additional scratch-only observer installed process-local detours after its own loader finished and self-checked `DrawEdge` against an explicit call before measuring the owned status control. In the same two-part `WM_PRINTCLIENT` model, each local v5.82 build called `DrawEdge` twice, with rectangles matching `SB_GETRECT` for ordinary and owner-drawn parts, edge 2 and flags 8207; each local v6.16 build instead called `DrawThemeBackground` twice, part 1/state 0, with rectangles matching the same parts. The caller addresses resolved to the respective loaded Windows ComCtl32 image. Both border/background operations preceded the parent `WM_DRAWITEM` callback in this model. Changing the ordinary part to `SBT_NOBORDERS` reduced the observed native border/theme calls to one, while `SBT_POPOUT` restored two and changed the first v5 edge to 4; the owner-draw callback still ran. All four isolated runs exited zero and released their owned windows and GDI objects. This suggests a scoped, pre-content native-draw adaptation might preserve application-owned content, but it is not a verified public lifecycle contract: print is only one drawing path, v6 popout semantics, clipping, icons, simple mode, multiple threads, dynamic changes, detach/reentrancy, and a genuine Delphi status bar remain untested. No product hook or renderer was changed.

A further scratch-only prototype called the original v5 edge/v6 theme operation, then overlaid a black frame before the owned parent's owner-draw callback. In the two-part print model, the x86/x64 v5 runs each changed 836 sampled pixels and the v6 runs each changed 51; interior comparison regions for the ordinary and owner-drawn parts each had zero differences, and the parent callback ran once with its original data. All four runs exited zero. These are bounded interior comparisons, not a proof that all pixels outside the edge or all application content are preserved. The frame is a candidate experiment, not a finished classic renderer; real `WM_PAINT`, DPI, partial clipping, dynamic state, icons, real VCL, reentrant removal and safe per-control/DC scoping must be checked before any product change. The temporary process-local hooks exist only in the owned probe process, and no product files changed.

The prototype was then exercised through synchronous `RedrawWindow` with a system icon in the ordinary part and an owned colored `WM_DRAWITEM` callback in the other. In both widths, all valid client pixels were compared: v5 changed 796 and v6 changed 802, with no changes outside the two one-pixel frame perimeters, zero differences in the sampled icon and owner-drawn interiors, the same icon handle, and one original owner-draw callback. This is one native control, icon and DPI, not an exhaustive content or Delphi guarantee. Actual v6 `WM_PAINT` produced three theme calls: part 0 for the entire client and part 1 for each pane. An initial scratch prototype framed all three; the revised prototype restricted its candidate overlay to part 1 and no longer changed pixels outside the pane frames. A separate DC clip to the left 60 pixels yielded 182 changed pixels on v5 and 66 on v6, zero changes outside the clip and equal native/prototype callback counts of zero because the owner-drawn part was outside the clip. Its initial test incorrectly required a callback and failed; the corrected assertion compares the native and prototype behavior. The source remains scratch-only. Safe integration, external theme clip rectangles, caller/module identity, dynamic state, DPI and reentrant teardown still require proof; no product file was changed.
