# M0 T18 S64: TMaskEdit investigation

The [author’s Delphi XE date-input example](https://mrxray.on.coocan.jp/Delphi/plSamples/164_DatePickerComponent.htm) archive SHA-256 is `646b7ea766d1c601308e58dcf14cf6f9fd5f6ede7a3a99b8b6f7fb727e8f6ff2`; the exact x86 `03_TMaskEdit_EraValue/Project1.exe` SHA-256 is `e5fbfe97a20af5f7521f503ccd11dbb5ca046191f0a4c0b59f816172d0a19a32`. The form source initializes one actual TMaskEdit with a Japanese-era date mask, disables its own IME and displays the current date. The optional button invokes a message box; it was not clicked. Source and executable remain research-only in registered scratch, not product input.

A process-local observer temporarily replaced the sample’s own resolved CallWindowProcW import and restored it. It witnessed the same class-owning executable forward the control’s WM_PAINT and WM_NCPAINT to the registered system EDIT window procedure. The public EDIT limit, selection, formatting rectangle, native extra-byte count and parent thread checks were satisfied. On the published package the root was attached but TMaskEdit was not. An isolated source prototype added the exact class to both the creation candidate and verified EDIT protocol role, preserving their existing owner, thread, paint and public-protocol checks. The real sample attached under this prototype. A single same-window removal comparison recorded 672 changed border pixels and 388 changed client pixels; the latter has not been attributed to font, redraw timing or another cause.

An earlier observer ran repeatedly and overwrote its first report after removing the attachment, so its zero-attached records are invalid for the prototype. A corrected first-observation driver showed old package unattached and prototype attached; their owned processes exited zero and job active count reached zero. Earlier test runs timed out during close and reclaimed their own job; they are not normal-exit evidence. Sending `WM_CHAR` digit 9 at selection position 5 produced the same unchanged date string and selection transition in bare and prototype runs; it did not prove a valid text edit. The original content was restored. Physical input, other mask definitions, font fidelity, other runtime versions and DPI remain unverified. No product source or binary was changed by this investigation; prototype and probes remain under `build/t18-s64-vb-mask-survey`. The pending ControlBar candidate and failed menu test remain separate outstanding work. M0/T18/S64 remain open.

The subsequent same-window probe records `WM_GETFONT` as the private Win16 System font (height 13) while attached, and the application font (height -13) after removal; the 388 changed client pixels lie at x=3..114, y=3..14 within the 151x21 window. This establishes a font-handle transition and location, but not that every changed pixel is due to glyphs or that Japanese text is unclipped and legible. With actual focus and a keydown/char/keyup sequence at position 9, both bare and prototype samples changed the same string and selection (`9..9` to `11..12`) and restored the initial text; notably the produced Japanese date string lost its month marker in both runs. This is parity for one synthetic sequence, not proof of valid masked-date behavior or a reason to treat this sample as a correct locale configuration. Both runs exited zero with owned jobs empty.

A second [author example](https://mrxray.on.coocan.jp/Delphi/plSamples/168_TEdit_VerticalAligment.htm) archive SHA-256 `b8a346a67534bd33c3782e8f8f81c53084ad4892e9aa703c4ef07fa574205e90` contains x86 `03_TplMaskEdit_VerticalAlignment/Project1.exe` SHA-256 `e3370def91325145e257add98fbbeb138279acaf01fdfe38eeba149354288e85`. Its source creates a derived `TplMaskEdit` with `000-9999` digit mask and deliberately enables ES_MULTILINE to arrange its text vertically. It is not an ordinary TMaskEdit and its source/artwork are research-only. The self-owned import observer restored its slot after witnessing same-owner WM_PAINT forwarding to the registered system EDIT procedure. A further scratch-only prototype allowing this exact derived class with its actual multiline flag attached. A bare/prototype comparison of 16 selection positions and digit 7 showed identical text and selection; positions 0 and 1 actually inserted 7, and the initial text was restored. Both owned processes exited zero. The sample class name is not a general public contract; no product change is admitted on that basis.

A separate same-window removal measurement for this derived control returned zero nonclient and two client pixels, despite attached=1 and the font handle transitioning from Win16 System to the application font. This does not prove the desired border appeared, nor that all masks, layout changes, DPI, physical input, clipboard, font clipping or resource lifetime work. The prototype remains scratch; the reason for the missing border difference requires investigation.

The derived sample zero-border result was traced to the existing EDIT renderer: when `edit_scrollbars` is enabled, its `WM_NCPAINT` branch returns immediately after `nonclient_scrollbars`, bypassing the later `list_border` path. The prototype enables that path for multiline controls, including this sample. An isolated prototype added the existing `list_border` call only for `WS_EX_CLIENTEDGE` before that early return. The same real sample then showed 628 nonclient and 2 client pixels changed on removal; the 16 input/selection outcomes remained equal to bare and restored text. Both self-owned instances exited zero. This establishes the missing branch and observed behavior for this one sample, not safe general multiline adoption: scrollbar coexistence, clip, DPI, reentrancy, existing TMemo, disabled state, x64 and negative tests remain pending. The changes remain scratch only.
