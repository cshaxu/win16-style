# M0 T18 S64: ordinary Delphi TScrollBar investigation

The earlier 74-family inventory did not establish a real Delphi TScrollBar receiver. A newly owned DelphiVCL4Python 1.0.7 x86/x64 sample at 144 DPI created a horizontal `TScrollBar` with range 0..100, page 10 and position 25. In both bare and current assets runs the actual runtime-owned class reported `TScrollBar`, extra window bytes 352/448, and the styled run loaded its corresponding assets DLL but reported the control unattached. GetScrollInfo(SB_CTL) returned the configured range/page/position; a temporary SetScrollInfo changed 25 to 50 and restored 25. This direct API experiment does not prove native user input or Delphi property/event coherence.

A test-only observer temporarily changed the runtime module's exact CallWindowProcW import on the self-owned process, requested a redraw and sent SBM_GETPOS, and then restored the import. Both calls used the system-registered SCROLLBAR class procedure on both widths in both bare and assets runs. This establishes a concrete runtime native-paint witness for the sample rather than equating name or message response with ownership. The owned target processes ended after WM_CLOSE; the abbreviated driver did not verify their exit codes or job active counts. The first x86 run could not load the scratch observer because it depended on a missing libgcc DLL; it was rebuilt with static libgcc before the reported four runs.

Candidate: add an exact newly created `TScrollBar` passive role, activate only after the same-thread owner module forwards its own WM_PAINT to the registered system SCROLLBAR procedure, then bind that verified role to the existing scrollbar painter and input handling. Identity, lifecycle, same-owner and native protocol must be checked after callback/reentrancy. Need genuine horizontal and vertical samples, enabled/disabled and range/page/position, event notifications and input, dual-width impostor/wrong-owner/reparent/removal/clipping tests and old-package negative. No product source or binary changed in this investigation.

The real current-package sample was then exercised horizontally and vertically on both widths. The vertical control reported style `0x54010005` and client size 25x250; horizontal reported `0x54010000`, 250x25. Each again forwarded WM_PAINT and SBM_GETPOS to the registered native SCROLLBAR procedure. A self-owned parent subclass observed two WM_HSCROLL/WM_VSCROLL notifications following synthetic right/down key messages, with final code 8 (`SB_ENDSCROLL`); the native position subsequently read 26 from the initial 25. This confirms a useful event/position baseline for that sample, but only the final notification code was recorded, not the complete notification sequence or physical input. The test then temporarily set position 50 and restored 26, not the original 25. The observer removed its parent subclass and restored IAT slots. Four owned target processes ended after WM_CLOSE; exit codes and job activity were not independently recorded. No production code or binaries changed.

A scratch candidate added a verified SCROLLBAR role and bound the existing renderer only after the target class-owner forwarded its own WM_PAINT to the system-registered procedure. Real horizontal and vertical x86/x64 samples attached and showed visibly classic scrollbar pixels; client captures differed from the prior package in all 6,250 RGB pixels, consistent with a palette-wide change rather than a geometry proof. Both widths and orientations gave the same synthetic keyboard notification sequence SB_LINEDOWN then SB_ENDSCROLL and position 25 to 26. Arrow mouse-message tests likewise gave SB_LINEDOWN then SB_ENDSCROLL, position 26 to 27, and released capture on both old and candidate. The first mouse probe synchronously sent down then up on the same UI thread; native scrollbar tracking blocked before up could be sent, and the owned process was timed out. Posting the up message before the synchronous down made the isolated native tracking complete; only corrected runs count, and they are not physical mouse tests.

A disabled test initially used the Delphi property before the HWND existed, but later observed an enabled HWND; those runs are not counted. After explicit EnableWindow(FALSE) on the owned created HWND, the old native path accepted direct synthetic key messages, issued line-down/end-scroll, advanced 25 to 26 and the actual VCL window became enabled. The first candidate suppressed keydown while disabled and differed. A revised scratch candidate forwards disabled key messages only for the verified Delphi scrollbar role; the real x86/x64 horizontal/vertical runs then matched the old notification sequence, position and enabled state. This observed re-enable is an empirical behavior, not an endorsement that disabled physical input should act.

A project-authored x86/x64 synthetic DLL model tests no-native-paint impostor, wrong-caller module forwarding, horizontal/vertical paths, keyboard and arrow notifications, a disabled direct-key path, clipped paint, reparent retirement and removal during a scroll notification. The previous assets package fails the positive attachment check on both widths; deliberately removing the disabled-key forwarding causes the x86 disabled assertion to fail. The initial x64 wrong-caller test had an optimized tail call that made the fixture the apparent caller; a noinline callback with a non-tail return restored the intended foreign identity and both widths passed. An initial DPI-aware run supplied an erroneous argument list and failed; corrected direct-argument runs passed. These fixture and candidate files remain in scratch and are not release artifacts. No product source or binary change has been made yet.

A further explicitly disabled real VCL test sent a direct synthetic mouse click first. In old x86/x64 horizontal and vertical samples, no notification occurred, capture was released, the HWND remained valid and disabled, and the read-back range/page/position changed from 0..100/10/25 to 0..0/0/0. The first candidate swallowed the messages and kept 0..100/10/25. The cause of the native range change was not determined; a revised candidate forwards these disabled mouse messages to the original procedure and matched the old observed results in all four configurations. This is a synthetic edge case, not evidence of physical interaction with a disabled window. The x86 scratch negative with disabled mouse forwarding omitted failed a new fixture assertion that the downstream original procedure received the down message; corrected dual-width fixture passed. The initial clean package build was already started before this finding; it was not accepted or published and a new snapshot is required.
