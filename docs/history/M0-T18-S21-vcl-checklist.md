# M0 T18 S21 — scoped VCL checklist glyph

DoubleKiller 1.6.1.80 (32-bit EXE SHA256 `cdd83ab909db749992d11ace2dff671493c0568d7a14697f8bef4b06d8647ca8`) was observed only as a task-local copy on an isolated desktop. Its Options page has three application-owned `THintCheckListBox` windows with native LISTBOX superclasses and fixed owner-draw/string styles; one has four visible items. The class is an observed application subclass, not a general claim about all Delphi TCheckListBox implementations. The original application executable and configuration are not distributed or modified.

The drawing trace established the exact path: parent `WM_DRAWITEM` identifies the list, item rectangle and same window DC; the application's code calls `DrawFrameControl(DFC_BUTTON, DFCS_BUTTONCHECK)` with the checked flag. Two mouse-message cycles changed that flag 0x400 -> 0 -> 0x400 and restored it. The test observer initially failed with error 127 because this old PE has no `OriginalFirstThunk`; the revised test-only observer identified exactly one resolved USER32 import by address and restored it after tracing. No application entry point or other process was patched. The scope is a public owner-draw API operation, not private Delphi fields or an inferred bitmap color.

The new bounded path attaches only newly created same-thread, same-process `THintCheckListBox` LISTBOX superclasses with the observed fixed owner-draw/string form and no RTL layout. A parent DRAWITEM scope validates the item, DC, caller module, list ownership, map mode and bounded rectangle. After successful native `DrawFrameControl`, only a normal, checked or pushed checkbox primitive is rendered using the existing original Win3.1 bitmap; unsupported flags, including disabled and adjust-rectangle, remain native. A single temporary in-memory DIB transfer is used; native API return, rectangle and last error, application item data, input and callbacks remain owned by the application. Reparenting and destruction retire the scope. No original graphic or provenance bytes, title/menu/font code, public ABI or number of product files changed.

On the actual candidate at 96 DPI, the four-item control remained native-owned. For its first item, the selected, deselected and restored states each matched all 81 pixels visible within the application's actual paint clip. After removing this project's attachment, 30 of those 81 pixels differed from the original glyph. Item count stayed four; selection became zero after the deliberate mouse messages, and capture was released. The surrounding portion of the 13x13 primitive is clipped by the application and remains its native drawing; a full 169-pixel comparison had 75 differences while attached and 105 after removal, so this is explicitly an interior-glyph improvement, not complete frame fidelity. A separate non-intercepting screenshot and normal window lifecycle passed; the owned job exited empty. Keyboard, accessibility, other DPI, disabled glyph styling, other VCL class names, custom image/callback variants and physical input were not proven by this sample.
