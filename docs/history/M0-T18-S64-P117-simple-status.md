# M0 T18 S64 P117: Delphi simple status text

Real DelphiVCL4Python 1.0.7 x86/x64 at 144 DPI uses an application-runtime-owned TStatusBar in simple mode. The P116 attachment left its Segoe UI text native. In both widths the native paint reached system UxTheme and DrawTextExW, first for measurement and then text, on the status window's DC. This delivery borrows a private System bitmap font only for a same-thread, witnessed Delphi simple-status paint, a verified UxTheme caller and matching DC, and ASCII text equal to a bounded pre-paint snapshot. The application still owns the status text, font, layout and all native callbacks; its WM_GETFONT remains unchanged. RTL, disabled, non-ASCII, text over 512 characters, unverified owner/DC and inconsistent state remain native. Native Win32 status windows remain on their previous path; no original graphic bytes or public export changed.

The text snapshot is captured before native paint; the hook does not synchronously query the status control while native DrawTextExW holds its text pointer. A discarded earlier prototype queried inside the hook, allowing reentrant mutation to invalidate that pointer. The epoch changes on SB_SETTEXT and WM_SETTEXT; the two self-owned reentrant tests compare against the respective native frame. A version missing WM_SETTEXT invalidation failed this comparison in both widths. An earlier test compared only with the later native frame and was flaky because reentrancy can expose old or new native data; it was replaced, not counted as passing.

A per-attachment cache retains the font lease; it checks source handle, LOGFONT, realized TEXTMETRIC and the actual ASCII per-character advances used by the generator. Font, system settings, theme and DPI changes invalidate it. Borrowed references survive nested WM_SETFONT and are released after restoring the DC; destruction releases the attachment lease. Independent System font variants are excluded from the pre-existing shared cache. This is necessary: in a self-owned two-status-window test the operating system reused a deleted source HFONT at iteration 255 in both widths. The initial shared-cache candidate produced 3717 differing bytes; isolated variants produced zero. A deterministic same-source isolation test also passes in both widths and deliberately disabling isolation makes both fail. The fixture simulates nested WM_SETFONT while the lease is borrowed, with a verified trigger, and completed both widths; it is a task-local instrumented DLL, not a claim of general exception or all reentrancy coverage.

With a warmed x86 native model, 20 WM_PRINTCLIENT calls took 16 ms for the final isolated cache prototype; the uncached prototype took 562 ms and P116 reported 0 ms on the same GetTickCount64 clock (system timer granularity applies). These are short local samples, not universal performance guarantees. The cached model observed GDI 9→9 across repeated paint and 6→6 across 20 create/change/destroy cycles in each width; this does not prove all resource leaks absent. The first package run scheduled both actual handle-reuse probes concurrently and neither reused a handle in 1200 attempts, producing an inconclusive failure. The runner now serializes those probes and recognizes only their exact no-reuse marker as a reported skip; skip classification has positive and negative tests. The final package run actually reused the handle in both widths and had zero skips.

The clean C17 GCC 16.1.0/Ninja/ccache 4.13.6 x86/x64 build passed PE, 31-export ABI and byte-exact resource/provenance gates. The same four-file package passed 30 focused cases in 15.56 seconds with zero skips. The actual package was run in self-owned Delphi x86/x64 instances; native captures showed System-shaped simple-status text and each target and launcher exited zero with empty jobs. The previous P116 package failed the new pixels assertion in both widths. The tested four files were published to assets root and O:/winnt/system32 with matching SHA-256, and each destination passed both widths of the simple-status and actual-reuse models.
