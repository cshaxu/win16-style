# M0 T19 S2 — System glyph family trial

The owner rejected the P210 per-character proportional trial: MadShow showed different letter heights and lost detail. In the observed 14px Tahoma text, `i` has advance 2, but the System 16px cell has advance 4 with only 2 pixels of ink. Scaling the entire System cell into the original advance shrunk the glyph vertically as well. This explains a concrete mechanism in the failed design; the original user screenshot remains the visual acceptance authority.

This trial uses the existing local Windows System bitmap source. For each supported cell size it builds a private FNT with the application original advance and line metrics, removes horizontal white bearings and scales visible ink using a common line height, with horizontal fitting only when necessary. The underscore receives an explicit visible-row correction. This is a runtime-generated System-derived family, not a separately authored typeface or a claim of per-size manual font design. 12..64 pixel line heights use this generator; smaller than 12 retain the source font because 8/10-pixel visual prototypes merged strokes. System/NULL source behavior, menus, calendar, titles and original assets remain unchanged. The hand-drawn 5x7 experiment remained scratch; it was not shipped because the resulting tiny words merged in the existing cells.

The test-only `font_size_matrix` checked requests 1..64 on x86 and x64: 53 generated, 11 source-font cases, no allocation fallbacks on this host; line height/ascent and 95 ASCII advances were checked. For sizes 8..64, all 94 printable non-space ASCII glyphs were checked for non-empty pixels; seven CP1252 samples were checked at sizes 12..64. These are coverage/metrics checks, not proof of every glyph's readability, complete character identity or all language coverage. The first matrix found underscore missing at 15px in both widths; the source System underscore was at row 15 of a 16px cell, and the explicit visible-row correction made the test pass. P210's old implementation fails the new x86 and x64 pixel reference. A missing include-path compile, an incorrectly strict pure-black check for antialiased native text, a warnings-as-errors build failure, and two orphan-proposal governance failures occurred before correction; none is represented as a successful candidate.

The self-owned isolated MadShow test used `PrintWindow` on the proper private desktop with `assets` P210 and the final package as two separate instances. The final 615x471 image shows the common labels and numeric controls; loaded module `ntw16s32.dll` was the exact final-package path. The unmodified application was started without business actions, and each owned job was reclaimed. This is a native screenshot, not real keyboard/mouse or other DPI validation. At the recorded 14px size it is visibly more consistent than P210; the user's subjective acceptance remains pending. Original 8/10-pixel system-derived previews and the handmade 5x7 prototype were too crowded, leading to the source-font fallback instead of asserting that all sizes were manually completed.

`tools/Build-Package.ps1 -Task 19 -RunName s2-glyph-family-final4` rebuilt one snapshot with GCC 16.1.0, Ninja and ccache 4.13.6. Source and original resource identity, version, imports/exports and both ABI checks passed. The exact package ran 24 focused cases in 105.1 seconds, with zero skips: x86/x64 source-linked font matrix and pixel tests, actual-DLL font layout, VB fonts, controls and graphical choices, menus, owner-draw, mandatory demo, launch and propagation. Full matrix, physical input, all Unicode and other actual DPI remain uncovered. All four files were published to `assets/` and `O:/winnt/` and checked against the tested package:
