# M0 T18 S64: CoolBar / Rebar investigation

Embarcadero documents [`TCoolBar`](https://docwiki.embarcadero.com/Libraries/Sydney/en/Vcl.ComCtrls.TCoolBar) as a Windows rebar wrapper containing movable bands. The local DelphiVCL4Python 1.0.7 x64 `CreateComponent` factory can instantiate TButton, TToolBar and TControlBar but reports `Invalid class` for TCoolBar; this does not prove it is unavailable in Delphi generally. No real TCoolBar instance has yet been verified.

A self-owned C model registers `TCoolBar` as a superclass forwarding to the registered native Rebar procedure, and places two child buttons in separate bands. On private desktops, the released P165 DLL was loaded, but the model rebar was not attached. Both x86 and x64 used the actual WinSxS COMCTL32 version 6.16, resolved from the registered Rebar class procedure. The scratch probe locally applies `SetWindowTheme(bar,L"",L"")`, not a system-wide setting: the theme lookup changes from available to unavailable, and the 584x24 Rebar client capture changes 875 RGB pixels on both architectures. The two band IDs can be moved and restored by RB_MOVEBAND; this is a message-level operation, not a mouse drag.

However the native theme switch also changed child window geometry: first child `(19,33,226,57)` to `(17,33,224,57)` and second `(241,33,592,57)` to `(237,33,592,57)`, both widths. Restoring the original null theme association restored both child rectangles and a valid theme handle. The restored image differed from the original by 48 pixels; an unchanged repeat capture also differed by 48 pixels, but the different positions were not compared, so pixel-exact restoration is not proven. No application-specified theme association, bitmap band, custom draw, keyboard/physical drag, higher DPI, resource accounting or actual Delphi runtime behavior was tested. The child geometry changes mean that simply disabling theme without investigating layout and callback consequences is not yet justified as a general product implementation.

The first version of the capture helper accidentally returned TRUE on an assertion failure because its failure macro returned 1 from a BOOL function; its printed pixel counts are invalid. The next run properly failed the incorrect fixed-size assumption; the real client was 584x24. A later stronger assertion exposed the geometry change and failed as intended. The native v6 resource link emitted `multiple non-default manifests` warnings; the actual registered control module and DLL version above independently establish the executed v6 control, not that every manifest aspect is correct. Scratch sources and models are under registered `build/t18-s64-vb-mask-survey/rebar-*` and `coolbar-model*`. No product or published binaries changed.

Next investigate the exact rebar paint/notification boundaries and app-owned custom draw/bitmaps and geometry impacts before selecting a safe adaptation; keep actual TCoolBar integration explicitly pending. M0/T18/S64 stay open.

## Item custom-draw proof of concept

Microsoft documents [Rebar NM_CUSTOMDRAW](https://learn.microsoft.com/en-us/windows/win32/controls/nm-customdraw-rebar) as a parent notification with per-band identifiers. In the self-owned v6.16 TCoolBar native-superclass model, the parent requested item/postpaint notifications and observed PREPAINT, two ITEMPREPAINT/ITEMPOSTPAINT pairs with IDs 101 and 102, then POSTPAINT. In this one 584x24 layout, the item rectangles were `(2,0)-(11,24)` and `(224,0)-(233,24)`: each covered a narrow grip, not the band child. These are empirical rectangles for this configuration, not a documented universal gripper contract.

A scratch observer clipped the item-postpaint HDC to those exact rectangles and painted a system-color raised face. Compared with a same-notification no-overlay capture, x86/x64 each changed 372 pixels inside the two observed grip rectangles and zero outside; both child screen rectangles were unchanged. During overlay, RB_MOVEBAND moved and restored the two IDs, after which the children returned to their original positions. A second model assigned an application-owned background bitmap to the first band: both widths changed 402 pixels inside the same observed rectangles and zero outside, retained the exact bitmap handle, restored band order and child geometry, then deleted the test bitmap after control destruction. These are message-driven tests, not physical dragging, VCL integration or proof for other band arrangements.

A further experimental parent chain forwards PREPAINT to a modeled application handler first, applies the grip overlay only when it returns CDRF_DODEFAULT, and otherwise forwards the application's own custom-draw stages without overlay. In one synthetic custom-draw scenario each width retained one prepaint and two item-prepaint calls with zero overlay calls. A deliberately faulty x86 build that ignored the application's return produced two overlays, lost the two item callbacks, and failed the assertion. This is evidence for the tested scenario only: the scratch observer uses a global boolean and is not reentrancy-safe; it does not cover app mutation of the HDC, nested paint, custom-draw item bitmaps, flags, horizontal/vertical and narrow bands, changing items, clipped/DC transformed regions, DPI, accessibility or lifetime. It must not be copied directly into production. Linker manifest warnings and earlier invalid attempts remain as described above. All samples use isolated desktops and self-owned windows; no product or released binaries changed.

## Nested paint, exception and image-content boundaries

The prior bitmap sample preserved its HBITMAP handle and pixels outside the grip, but that did **not** mean the entire application image was preserved: 174 of the app bitmap's exact-color pixels were inside the grip and all 174 were overwritten on both widths. A revised scratch prototype queries each band's public background handle and skips overlay when a bitmap is present. The same test then preserved all 174 pixels and the bitmap handle, while changing 228 pixels in the other grip and zero outside the two grips; children stayed in place. A deliberately faulty x86 build that ignored the background handle changed all 174 and failed the new assertion. This corrects any broader reading of the previous bitmap result.

For the non-bitmap band, `RB_GETRECT` returned `(224,0)-(584,24)`, `RB_GETBANDBORDERS` returned left border 9, and the child was `(233,0)-(584,24)`; the reported item postpaint rectangle `(224,0)-(233,24)` matched that left band border exactly. A scratch validator now requires that equality, a nonoverlapping same-parent child, no bitmap, zero band style, horizontal orientation, DPI-bounded width and untransformed MM_TEXT DC before painting. It rejected a one-pixel expanded left edge for the otherwise accepted band on both widths. A faulty x86 variant omitting the left-edge check was caught by the model. These conditions are a conservative model for the observed case, not proof of all actual TCoolBar behavior.

The experimental global painting flag was replaced in scratch by a thread-local per-WM_PAINT stack and the repository's C native unwinder. Both widths passed a same-window nested redraw initiated from the application's PREPAINT callback: one nested scope, four observed item-postpaint callbacks and an empty scope afterward. An x86 fault that discarded the previous scope produced only two and failed. An application callback exception was caught after the native unwind and left the scope empty in both widths; an x86 fault suppressing cleanup left it nonempty and failed. The application custom-draw model still saw its original one PREPAINT and two ITEMPREPAINT notifications and received no overlay. Neither this test nor these manual fault variants establish nested destruction, reparenting during callbacks, GDI resource exhaustion, nonzero viewport, actual VCL runtime or complete app-draw preservation. The scratch validator performs queries during the callback and needs explicit revalidation of the target after each potentially reentrant call before production use. No product or binary changed.

The self-owned native identity model additionally observed same-owner parent and control, Unicode `TCoolBar` registration and real class names, with window extra storage 4/8 bytes on x86/x64. This is not a real Delphi sample and does not establish a production-safe identity contract.
