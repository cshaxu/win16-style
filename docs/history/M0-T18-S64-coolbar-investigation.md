# M0 T18 S64: CoolBar / Rebar investigation

Embarcadero documents [`TCoolBar`](https://docwiki.embarcadero.com/Libraries/Sydney/en/Vcl.ComCtrls.TCoolBar) as a Windows rebar wrapper containing movable bands. The local DelphiVCL4Python 1.0.7 x64 `CreateComponent` factory can instantiate TButton, TToolBar and TControlBar but reports `Invalid class` for TCoolBar; this does not prove it is unavailable in Delphi generally. No real TCoolBar instance has yet been verified.

A self-owned C model registers `TCoolBar` as a superclass forwarding to the registered native Rebar procedure, and places two child buttons in separate bands. On private desktops, the released P165 DLL was loaded, but the model rebar was not attached. Both x86 and x64 used the actual WinSxS COMCTL32 version 6.16, resolved from the registered Rebar class procedure. The scratch probe locally applies `SetWindowTheme(bar,L"",L"")`, not a system-wide setting: the theme lookup changes from available to unavailable, and the 584x24 Rebar client capture changes 875 RGB pixels on both architectures. The two band IDs can be moved and restored by RB_MOVEBAND; this is a message-level operation, not a mouse drag.

However the native theme switch also changed child window geometry: first child `(19,33,226,57)` to `(17,33,224,57)` and second `(241,33,592,57)` to `(237,33,592,57)`, both widths. Restoring the original null theme association restored both child rectangles and a valid theme handle. The restored image differed from the original by 48 pixels; an unchanged repeat capture also differed by 48 pixels, but the different positions were not compared, so pixel-exact restoration is not proven. No application-specified theme association, bitmap band, custom draw, keyboard/physical drag, higher DPI, resource accounting or actual Delphi runtime behavior was tested. The child geometry changes mean that simply disabling theme without investigating layout and callback consequences is not yet justified as a general product implementation.

The first version of the capture helper accidentally returned TRUE on an assertion failure because its failure macro returned 1 from a BOOL function; its printed pixel counts are invalid. The next run properly failed the incorrect fixed-size assumption; the real client was 584x24. A later stronger assertion exposed the geometry change and failed as intended. The native v6 resource link emitted `multiple non-default manifests` warnings; the actual registered control module and DLL version above independently establish the executed v6 control, not that every manifest aspect is correct. Scratch sources and models are under registered `build/t18-s64-vb-mask-survey/rebar-*` and `coolbar-model*`. No product or published binaries changed.

Next investigate the exact rebar paint/notification boundaries and app-owned custom draw/bitmaps and geometry impacts before selecting a safe adaptation; keep actual TCoolBar integration explicitly pending. M0/T18/S64 stay open.

## Item custom-draw proof of concept

Microsoft documents [Rebar NM_CUSTOMDRAW](https://learn.microsoft.com/en-us/windows/win32/controls/nm-customdraw-rebar) as a parent notification with per-band identifiers. In the self-owned v6.16 TCoolBar native-superclass model, the parent requested item/postpaint notifications and observed PREPAINT, two ITEMPREPAINT/ITEMPOSTPAINT pairs with IDs 101 and 102, then POSTPAINT. In this one 584x24 layout, the item rectangles were `(2,0)-(11,24)` and `(224,0)-(233,24)`: each covered a narrow grip, not the band child. These are empirical rectangles for this configuration, not a documented universal gripper contract.

A scratch observer clipped the item-postpaint HDC to those exact rectangles and painted a system-color raised face. Compared with a same-notification no-overlay capture, x86/x64 each changed 372 pixels inside the two observed grip rectangles and zero outside; both child screen rectangles were unchanged. During overlay, RB_MOVEBAND moved and restored the two IDs, after which the children returned to their original positions. A second model assigned an application-owned background bitmap to the first band: both widths changed 402 pixels inside the same observed rectangles and zero outside, retained the exact bitmap handle, restored band order and child geometry, then deleted the test bitmap after control destruction. These are message-driven tests, not physical dragging, VCL integration or proof for other band arrangements.

A further experimental parent chain forwards PREPAINT to a modeled application handler first, applies the grip overlay only when it returns CDRF_DODEFAULT, and otherwise forwards the application's own custom-draw stages without overlay. In one synthetic custom-draw scenario each width retained one prepaint and two item-prepaint calls with zero overlay calls. A deliberately faulty x86 build that ignored the application's return produced two overlays, lost the two item callbacks, and failed the assertion. This is evidence for the tested scenario only: the scratch observer uses a global boolean and is not reentrancy-safe; it does not cover app mutation of the HDC, nested paint, custom-draw item bitmaps, flags, horizontal/vertical and narrow bands, changing items, clipped/DC transformed regions, DPI, accessibility or lifetime. It must not be copied directly into production. Linker manifest warnings and earlier invalid attempts remain as described above. All samples use isolated desktops and self-owned windows; no product or released binaries changed.

## Nested paint, exception and image-content boundaries

The prior bitmap sample preserved its HBITMAP handle and pixels outside the grip, but that did **not** mean the entire application image was preserved: 174 of the app bitmap's exact-color pixels were inside the grip and all 174 were overwritten on both widths. A revised scratch prototype queries each band's public background handle and skips overlay when a bitmap is present. The same test then preserved all 174 pixels and the bitmap handle, while changing 228 pixels in the other grip and zero outside the two grips; children stayed in place. A deliberately faulty x86 build that ignored the background handle changed all 174 and failed the new assertion. This corrects any broader reading of the previous bitmap result.

For the non-bitmap band, `RB_GETRECT` returned `(224,0)-(584,24)`, `RB_GETBANDBORDERS` returned left border 9, and the child was `(233,0)-(584,24)`; the reported item postpaint rectangle `(224,0)-(233,24)` matched that left band border exactly. A scratch validator now requires that equality, a nonoverlapping same-parent child, no bitmap, zero band style, horizontal orientation, DPI-bounded width and untransformed MM_TEXT DC before painting. It rejected a one-pixel expanded left edge for the otherwise accepted band on both widths. A faulty x86 variant omitting the left-edge check was caught by the model. These conditions are a conservative model for the observed case, not proof of all actual TCoolBar behavior.

The experimental global painting flag was replaced in scratch by a thread-local per-WM_PAINT stack and the repository's C native unwinder. Both widths passed a same-window nested redraw initiated from the application's PREPAINT callback: one nested scope, four observed item-postpaint callbacks and an empty scope afterward. An x86 fault that discarded the previous scope produced only two and failed. An application callback exception was caught after the native unwind and left the scope empty in both widths; an x86 fault suppressing cleanup left it nonempty and failed. The application custom-draw model still saw its original one PREPAINT and two ITEMPREPAINT notifications and received no overlay. Neither this test nor these manual fault variants establish nested destruction, reparenting during callbacks, GDI resource exhaustion, nonzero viewport, actual VCL runtime or complete app-draw preservation. The scratch validator performs queries during the callback and needs explicit revalidation of the target after each potentially reentrant call before production use. No product or binary changed.

The self-owned native identity model additionally observed same-owner parent and control, Unicode `TCoolBar` registration and real class names, with window extra storage 4/8 bytes on x86/x64. This is not a real Delphi sample and does not establish a production-safe identity contract.

## Reparent during synchronous band query

A separate native x86/x64 private-desktop model subclasses its own rebar and changes the bar's parent immediately after forwarding `RB_GETRECT`, simulating synchronous reentrancy during the validator's query sequence. The previously modeled unguarded sequence accepted the now-reparented bar on both widths; a version that checks window, original parent and UI thread after each query rejected it on both (`unguarded_accepted=1 guarded_accepted=0 mutations=2`). The probe restores its own parent and destroys its own windows. This establishes a concrete revalidation requirement and a negative case, not a complete identity contract: destruction, HWND reuse, attachment generation, other band mutations and real VCL are untested. This is scratch evidence only, no product change; source and executables are under registered `build/t18-s64-vb-mask-survey/coolbar-reparent-model*`.

The same self-owned model also destroys the bar during `RB_GETRECT`. On both widths the guarded path returned false and made zero later band-info queries; the unguarded path returned false only after attempting one such query on the destroyed handle. A separate mutation reparents and restores the bar before returning from `RB_GETRECT`: the guarded current-parent check accepted it on both widths. The local subclass saw zero `WM_WINDOWPOSCHANGED` and zero `WM_PARENTNOTIFY` messages in that experiment. Therefore comparing the current HWND/parent/thread alone does not prove no intervening mutation, and these two messages cannot serve as a general generation witness based on this observation. These are synthetic cases, not proof that actual Rebar internally reenters in this manner; HWND reuse and real Delphi behavior remain untested. Scratch files: `coolbar-destroy-model*`, `coolbar-transient-model*`, `coolbar-transient-notify*`. No product change.

## Direct native-procedure query candidate

Source search for `SetParent`, destroy messages and generation counters found no existing SetParent interception in `src/ntw16s-dll`; attachments use destroy retirement and selected per-control epochs. The prior transient-parent experiment showed window-position and parent notifications alone are insufficient as a witness. A self-owned rebar model instead resolved the registered native class procedure and used `CallWindowProcW` to issue the same public band queries directly. On x86 and x64, both the system v5.82 and WinSxS v6.16 models returned the same band rectangle, borders, style, child and bitmap as the ordinary subclass chain. In the modeled sabotage case ordinary dispatch reparented the bar, while direct queries bypassed the sabotage and retained the original parent on both widths. Both v6 links emitted the previously observed multiple-manifest warning; the invoked class procedure's own module reported 6.16. An initial version-probe compile lacked shlwapi.h and did not run; adding the header fixed it.

This is a research candidate, not a product-safe proof: direct dispatch bypasses application subclass behavior and may not be equivalent for an actual VCL wrapper, owner callbacks, mutation inside the native procedure, or all versions. Identity, ownership and equivalence must be witnessed before use; a native procedure must never be guessed from the class name. No product change. Scratch: `coolbar-direct-{query,data,version,v6}*` and `coolbar-test*`.

A further x86/x64 v6.16 model registers an application-owned `TCoolBar` superclass whose window procedure forwards to the actual registered native Rebar procedure. Its normal query reached the wrapper four times while direct native queries reached it zero times; in the simple forwarding configuration, rectangle, border, style, child and bitmap all matched. A controlled negative wrapper then changed the returned `RB_GETRECT` right edge by one pixel: ordinary and direct results differed (`395` versus `394`) on both widths, and the comparison detected it. Thus the direct path visibly bypasses application window-procedure semantics; equality in a forwarding fixture cannot justify assuming all VCL or derived wrappers forward unchanged. The two v6 builds again reported multiple manifest warnings; the class-procedure module reported version 6.16. Scratch: `coolbar-wrapper-direct*`; isolated windows were destroyed normally.

A bounded binary-string search using `rg -l -a --no-messages -g '*.exe' 'TCoolBar' D:/programs/misc O:/winnt` found no matching file; absence of a class name string does not establish absence of controls or constitute a runtime inventory. No actual Delphi TCoolBar was observed in this search. No product changes.

## Real VCL bands and drawing notifications

The native scratch driver now creates two actual VCL TButton children under the actual GoVCL TCoolBar through the author's published stdcall APIs. The VCL automatically creates two bands. Both x86 and x64 released-package runs loaded the exact respective `assets/ntw16s32.dll` or `assets/ntw16s64.dll`, reported the root attached and the TCoolBar not attached, and completed with process exit 0. At observed 96 DPI both bands reported style `0xa1` (`RBBS_BREAK | RBBS_FIXEDBMP | RBBS_GRIPPERALWAYS`), no bitmap, and left border 13 pixels. A temporary self-owned parent subclass requested custom-draw item notifications and removed itself before form destruction. On both widths original parent responses were default; two PRE/POST item pairs reported grip rectangles 9 pixels wide, not the 13-pixel `RB_GETBANDBORDERS` left value. One item occupied `(0,0)-(9,24)` and the other `(0,26)-(9,51)`. The bar client was `(0,0)-(480,36)`, so the second band extends beyond the visible client and cannot be counted as a fully visible item.

These observations contradict two assumptions in the earlier restrictive synthetic validator: requiring zero band style and equality between item width and the whole left band border would reject this real VCL sample. They do not prove direct-query equivalence, correct appearance, actual overlay, application interaction, clipping of the second band, or any other Delphi version/DPI. `govcl-coolbar-bands*` and `govcl-coolbar-draw*` in registered scratch contain the self-owned probes; the latter emitted both successes and returned after a delayed shell session, so no timing claim is made. Product code remains unchanged.

## Real VCL grip drawing experiment

The fixture uses published VCL properties to disable autosizing/alignment and set the TCoolBar height, making both real bands fully visible in a 480x76 client at the observed 96 DPI. A self-owned parent subclass forwards the application's default custom draw and, only during this experiment, clips a raised-face overlay to the observed two item rectangles. The identical live window was redrawn and captured twice without the overlay; both x86 and x64 had zero differing RGB pixels. The next capture with overlay differed at 212 pixels inside the two observed grip rectangles and zero outside, with both child screen rectangles unchanged. The probe moved the bands once using `RB_MOVEBAND` and restored their original IDs and both child rectangles, then removed its subclass, freed the VCL form and exited 0 on each width. Both runs loaded the released assets DLL, attached the root and did not attach the TCoolBar itself.

This is a bounded real-runtime experiment, not product support: the observer is test-side, no style DLL overlay has been installed, the app did not provide custom draw or background bitmaps, no physical dragging or click callbacks were tested, and only one VCL build and DPI were observed. Its pixel counts and guards do not prove that arbitrary notification rectangles identify safe grips. Scratch `govcl-coolbar-overlay*`; product unchanged.

## Real VCL native query and common-controls versions

With the actual GoVCL DLL on x86/x64, the registered TCoolBar class procedure resolves to that DLL; the registered REBAR procedure resolves to WinSxS COMCTL32. Window extra sizes match (4/4 and 8/8). For both real bands the public message dispatch and direct registered REBAR procedure queries agreed on rectangle, ID, child, style and bitmap. This was observed both with system COMCTL32 5.82 and a manifest-selected 6.x control. It is evidence for this one actual VCL build and state, not authorization to bypass arbitrary application subclass behavior: the earlier fault wrapper demonstrates the semantic difference.

The earlier actual VCL bitmap experiment had used COMCTL32 5.82; it did not establish v6 coverage. Repeating its fixed-coordinate comparison under manifest-selected v6 failed on both widths (`inside=284 outside=96`) because the two observed grip rectangles moved from x=0..9 to x=2..11. The unmodified failed test remains a failure, not evidence of out-of-grip drawing. A revised test records the actual notification rectangles and compares against them: dual-width v6 reported identical repeated baseline captures, `inside=380 outside=0`, both child rectangles unchanged, bitmap 174 matching pixels unchanged and handle preserved while the other grip changed 194, movement restored, and exit 0. Dynamic comparison uses notification rectangles as its measurement boundary and is not an independent proof that those rectangles never contain application content. Scratch `govcl-coolbar-native-query*`, `govcl-coolbar-bitmap-v6-*`, `govcl-coolbar-bitmap-dynamic*`. No product implementation or release.

## Geometry guard prototype on real VCL

A scratch C validator combines witnessed VCL band flags (`BREAK`, `FIXEDBMP`, `GRIPPERALWAYS`) with a horizontal, non-RTL, untransformed DC, current parent/thread/window checks after synchronous queries, no band bitmap, same-parent child, full client/band bounds, a DPI-bounded width inside the left band border, and no intersection with the child rectangle. With real dual-width VCL and COMCTL 5.82 and 6.x, it accepted both actual grips, rejected each synthetic one-pixel left expansion, and repeated the prior pixel, bitmap and move/restore assertions; all four combinations exited 0. These conditions are still a prototype: the measurements cannot prove general safety for application-drawn content or identity across transient reparenting, and no product hook uses them.

A deliberate left-edge-check removal was **not** caught under 5.82 because its expanded rectangle also violated the separate client-left boundary: the faulty program exited 0, so that attempt is not a valid fault detection. Under v6, where the band starts at x=2, the same fault made both bad rectangles accepted (`bad_rejected=0`) and the x86 test failed (exit 1). The corrected guard rejected them. The first build loop also failed due to incorrect PowerShell argument construction and was rerun correctly; v6 links retained multiple-manifest warnings. Registered scratch `govcl-coolbar-geometry*`.

## In-progress DLL candidate

A bounded candidate is now present in `attachment.c` but is not released: same-owner TCoolBar/parent attachment and parent custom-draw observer, a nested WM_PAINT scope using the existing C unwinder, exact band/client/child/DC/DPI checks, and fallback for background bitmap, band text/image, unfamiliar flags or application-owned custom draw. Under the incrementally built candidate the actual GoVCL x86/x64 sample with both COMCTL 5.82 and 6.x reported attached, and a stabilized same-window remove comparison showed 212 or 380 changed grip pixels and zero outside; both child positions remained unchanged. The prior released DLL failed the same v6 positive check on both widths. A modeled application custom-draw callback received one prepaint and two item callbacks, zero item-post callbacks, on both candidate widths. This is limited evidence, not full product verification.

The first 6.x capture compared against an asynchronously changing initial frame and failed with 21043 apparent outside changes; a second same-styled capture demonstrated the same 21043 changes, and the comparison was corrected to require two identical subsequent styled frames before removing the style. The initial result remains a failed test, not a pass. An initial wrong Ninja target was corrected; sandboxed Ninja stopped emitting progress, so only the two owned build processes were stopped and an escalated Ninja incremental build succeeded on both architectures. Review caught a reference-order problem in the initial candidate; the attachment call reference now increments before reentrant retirement. Review also corrected forwarding of the synthetic item-post notification when a geometry check declines drawing.

This candidate still needs self-contained native tests for attachment/paint, app return and state, bitmap/text/icon fallback, unexpected callbacks, nested paint and exceptional unwind, destruction/reparenting/reference ownership, original graphics, same-batch clean package and dual publication. In particular current parent identity checks cannot prove a transient reparent-and-restore did not occur while synchronous queries execute; this is an unresolved correctness boundary, not a supported case. The custom-draw callback is a modeled application observer, not a third-party app. Source and hashes are in the worktree; no product release or P number is claimed.

## Witnessed native query and lifecycle regression in progress

The candidate now witnesses the actual same-owner `CallWindowProcW` forwarding to the registered system REBAR procedure during each individual WM_PAINT scope. Only the witnessed procedure is used for the candidate's band-state queries; it is kept in that nested scope rather than an attachment field, and the thread-local previous scope is restored on normal and abnormal unwind. This avoids dispatching candidate queries through a modeled application subclass that can synchronously reparent and restore the HWND, while ordinary application messages still use their original dispatch. It does not prove the native procedure itself never reenters and does not claim that arbitrary app subclasses are equivalent to native queries. The candidate also requires `WindowFromDC` to identify the exact bar. The real VCL test's relevant custom-draw DC was that window in both widths and COMCTL families; unrelated later DC observations were not treated as bar drawing.

A new self-contained `core-coolbar-lifetime` regression registers an application-owned rebar superclass and parent. Dual-width incremental candidate runs passed: verified attachment, one nested repaint and subsequent attachment, a controlled application callback exception caught with a successful next redraw, candidate queries bypassing an armed reparent/removal subclass, and ordinary later queries reaching it and producing correct remove/reparent retirement. The previously released DLL fails the positive attachment on each architecture. The first test fixture had a singleton band without a visible grip and failed; enabling `RBBS_GRIPPERALWAYS` corrected the fixture. The earlier direct-query candidate correctly failed the old test that expected its own internal query to enter the subclass; the revised test now explicitly verifies both the bypass and normal app dispatch. First CMake build of the formal test missed the resource include directory and failed; after adding `src` both widths built. The actual VCL same-window before/after comparison was rerun after the witness change: x86/x64 and COMCTL 5.82/6.x each passed at 96 DPI with 212/380 inside and zero outside changes, window positions preserved. Self-contained image/text/bitmap, false owner/procedure, scope fault mutations and complete same-batch validation still need work; no release.

## Text length and fake-class regressions

The first attempted pixel-stability check for a labeled band failed: two repeated x86 v6 captures differed by 363 pixels in the text/header area. The previous released DLL showed the same 363-pixel repeat difference in an independent diagnostic, so this particular comparison cannot attribute the drift to the candidate and was not counted as a pass. More importantly, on this system an `RB_GETBANDINFOW` call with a two-WCHAR buffer returned success and an empty buffer for `Band caption`, while its `cch` changed from 2 to 13. The candidate originally checked only the first character, so it could misclassify a truncated response as empty. The candidate now also declines if the returned count exceeds the buffer capacity. The Microsoft documentation describes cch as buffer size, not a portable promise of this observed output behavior; support beyond the tested 5.82/6.x implementation is not claimed.

The formal self-contained test creates hidden-until-configured bands with a short caption, a 300-character caption, a background bitmap, or an image-list index; after showing, it checks no candidate grip was verified, the original value is readable, and the exact attachment can be removed. For the text cases a test-only parent subclass deliberately narrows the incoming postpaint rectangle to a plausible 9-pixel grip; this makes the length check independently relevant instead of allowing the ordinary wide-caption geometry guard to mask the fault. The missing-length-check x86 fault was rejected (`painted=1`, exit 1); without the synthetic narrowing, the same fault passed because the separate geometry guard rejected the wide rectangle, so that first negative attempt was invalid. The corrected candidate passed all four cases on both widths and both locally observed common-control versions. These tests assert candidate status and read back app data, not pixel identity; the earlier separate real-VCL bitmap experiment has its own pixel evidence.

The wrong-parent-owner case also remains native. A same-name `TCoolBar` class whose procedure belongs to USER32 first exposed a product defect: the old released DLL allowed its creation, but the initial candidate rejected creation while attempting attachment. A minimal independent x86 reproduction confirmed this difference. The candidate now checks class-procedure owner before declaring the window eligible; the formal test verifies the fake window is created and not styled on both widths. This does not prove all framework subclasses or color/image/bitmap combinations. Full clean package validation is pending.

## Package test and existing menu-test teardown hang

The first same-snapshot clean build passed, and the four real VCL width/version checks passed against that package. The selected package run failed `menu-cancel-x86` with worker exit 6 after its 150-second outer budget. The parallel x64 test also remained in low-CPU waiting. A separate test against each previous released DLL reached case 14 and then timed out at 20 seconds as well; its two orphaned private workers were identified by PID, parent, path and start time and terminated. A separate 18-case focused run excluding those two failing menu cases passed in 7.86 seconds without skips; it does not erase the earlier failure.

Instrumented self-owned x86 probes showed that all case-14 assertions and both tested window destructions completed, and then the test blocked destroying its own active focus anchor. Skipping only the last post-destruction queue drain did not solve the anchor teardown; clearing focus/active window before destroying it also did not solve it. An exploratory run leaves the private, unstyled anchor to worker process teardown, skips the final case's post-destroy drain, retains every case assertion, and still executes the following independent native popup and its queue drain. All 15 scenarios in both DPI contexts and both widths then passed in roughly six seconds against both the candidate and the previous released DLL. This is a test-harness workaround for the observed environment, not a proven Windows root cause; it does not separately verify explicit anchor destruction. Process termination owns cleanup and the parent waits for worker exit before closing its private desktop.

The source test adopts this isolated-worker cleanup with a 30-second worker limit and 35/40-second package/CTest limits; no product menu code changed and no scenario assertion was removed. Both failed attempts and their limits remain part of the evidence. Since this test input changed after the first package snapshot, that package is not eligible for the new actual-package regression; a fresh clean snapshot and test are required.
