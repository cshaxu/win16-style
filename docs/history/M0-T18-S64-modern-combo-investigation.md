# M0 T18 S64: modern Delphi combo investigation (open)

The published P113 package was compared with bare launching of self-owned DelphiVCL4Python 1.0.7 combo samples at actual 144 DPI in x86 and x64. The runtime-owned TComboBox is class/real-class `TComboBox`, style 0x54010242. In both widths its root and the native EDIT child attached, but the combo shell did not: its screenshot retained the modern arrow and border. Bare and styled public GetComboBoxInfo, item-parent, count 2, selected index 0, open/close and selection preservation succeeded. The observer did not exercise a user's physical input. Target and launcher exited 0 and owned jobs emptied.

An observer limited to the owned runtime module captured the combo's own WM_PAINT calling the registered USER32 COMBOBOX procedure in both widths. Hook installation, redraw and import restoration succeeded. The actual runtime module paths and SHA-256 are `build/t18-s31-static-text/wheel32/delphivcl-1.0.7.data/purelib/delphivcl/Win32/DelphiVCL.pyd` `2272062b0e7e847a05a6344e2b31a04ed1edb5a52c0bf78a149e35739613eece`, and `build/t18-s31-static-text/wheel/delphivcl-1.0.7.data/purelib/delphivcl/Win64/DelphiVCL.pyd` `d7b856b9bc7d9fc411324c21584a8cbfd8c8f17bba00f65dae054a61bc35db76`. The actual P113 DLL SHA-256 values were x86 `1b596b1be5438360b34e5af6b912fc9a24ae45c1560d578547e33a678ca8a466`, x64 `dbc00073c73584fbf96def13444c8bf17663767173e3d1c074217aa66a4147ca`.

A scratch-only, deliberately incomplete proof extends the existing edit witness to COMBOBOX and invokes the existing control renderer through the already public combo protocol. Both actual samples then reported shell attached and a screenshot showed a classic arrow/border; open/close and selection preservation still passed and both jobs emptied. Its DLL hashes are x86 `9e96cbb1121909b3d6f82fe94c2c9fa1bfdebcb9391f3442e117e42a71cd2223` and x64 `20bac0c4262a5be63716840884b3add96e9e1ceb6d4f5508b9303425b408d559`. This is NOT a product candidate: it does not validate parent identity and unsupported live style transitions, and independent native EDIT child ownership, popup theme and scroll ownership, reentrant teardown, false witnesses, owner-draw/RTL, normal/dropdown-list modes and allocation failure are not proven. The temporary observer's direct CB_SHOWDROPDOWN calls do not prove real keyboard or mouse use. Other DPI and Windows versions remain unverified. The first scratch build used the wrong architecture resource compiler and failed at link; after configuring matching windres, both scratch DLLs built.

Next: create self-contained same-module, wrong-owner and fake-witness dual-width C fixtures; verify creation, child ownership and restoration, dropdown/list and edit semantics, dynamic roles, repeated attach/remove and reentrancy. Limit identity and validate it again before and after synchronous calls; only then propose production change and run clean four-file tests. The scratch tree and logs are under `build/t18-s64-vb-combo-modern`; they are not release artifacts. Product files and assets remain P113. M0/T18/S64 remain open.

Follow-up self-owned C model: the first apparent foreign-caller failure was an optimized tail call: after making the foreign function noinline and retaining its result, the candidate rejected the wrong caller in both widths. A wrong-parent negative exposed actual over-broad admission in the first scratch candidate. The next scratch candidate requires same owner and thread and the exact ordinary editable role; its dual-width model passes valid paint/protocol, fake paint, foreign caller, wrong parent, selection, reparent and owner-draw retirement. The model had to reset its delayed native initialization for every new window; without that reset, subsequent synthetic controls initialized differently and produced misleading attachment results. Its RealGetWindowClass changes from TComboBox to COMBOBOX after manual USER initialization, unlike the real observed VCL sample; the scratch guard therefore accepts either after that initialization. This is an experiment, not evidence to silently expand the production rule.

The real x86/x64 sample with the guarded candidate maintained its separately attached EDIT and exact font handle when its shell was removed. However removing while the popup was open closed it. Bare real Delphi, as well as the candidate, closed the popup on an explicit WM_SETFONT even with the same font; an x86 scratch experiment that skipped font restoration kept it open, but that experiment alone would risk leaving a borrowed font. A newer scratch experiment instead avoids replacing the editable combo shell's native font and leaves the separately attached EDIT responsible for text styling; in both actual widths, remove while open reported popup still open, EDIT still attached with the same font, list HWND valid, and subsequent close successful. Target and launcher exited zero, owned jobs emptied. The candidate's x86/x64 self-owned native model passed fake paint, wrong caller, wrong parent, selection, role change and post-install reparent. A reparent trigger on CB_GETCOUNT fired after a paint and left the target unattached, but its exact relation to the binder is not independently established. The model's child EDIT was not independently attached, so the real-sample child test is separate.

For eight synthetic dropdown open/close cycles the actual sample retained selection 0 and list HWND; baseline x86 GDI count 72 to 83, candidate x86 74 to 78, baseline x64 76 to 82 and candidate x64 74 to 78. This short observation does not prove a leak or its absence. Candidate seven is scratch-only: DLL SHA x86 `a23ac4e7c430047b723257f594d3c350638b465657fd3002911aa46439f3d6f1`, x64 `a5a891323cd23b0dcebae38126b463379e8e89bbdc4ac28938fb883dc8c55936`. Its font passthrough, parent and role guards, exceptions/reentrancy, popup theme/scroll ownership and font changes need durable self-contained tests and review before any product change; notably the scratch-only DLL pair is not a same-snapshot release package. All resources and installed files remain P113.
