# M0 T18 S64: real runtime-owned Delphi tree and list observation

A project-authored private-desktop runner launched the optional DelphiVCL4Python 1.0.7 test runtime and created actual `TTreeView` and `TListView` controls. Both class and real class retain the respective Delphi class name, and the class owner on each width is the corresponding absolute DelphiVCL.pyd runtime module rather than the Python executable. In an initial empty sample, bare/styled x86/x64 all reported neither control attached and exited 0. In the styled data sample the tree had a parent and child node, and the list had one item; Delphi collection counts and the public TVM_GETCOUNT/LVM_GETITEMCOUNT messages agreed (2 and 1). After synchronous redraw both controls still reported unattached on both widths; both samples exited 0. Runtime samples are optional, not project dependencies.

This establishes an actual missing runtime-owned entry path for these sampled classes, not that all drawing or behavior is wrong, nor that class name or count alone is safe to authorize a renderer. The runtime's real native-control forwarding, caller identity, custom-draw callbacks, image lists, item semantics, reparenting, lifecycle, owner-draw and version/DPI boundaries require evidence before product implementation. No product or binary was changed. Scratch: build/t18-s64-vb-mask-survey/lists-real.py, page-runner.exe and real-lists-data-*-styled.log. M0/T18/S64 remain open.

## Native paint witness

A temporary task-owned IAT observer intercepted the runtime module's CallWindowProcW during synchronous redraw of the populated controls. On each width, the tree and list each forwarded one WM_PAINT to their respective currently registered system native procedure; neither observed call used another procedure. Both redraws succeeded, the imported slot was restored, and both samples exited 0. Logs: build/t18-s64-vb-mask-survey/real-lists-forward-x86.log and real-lists-forward-x64.log. This covers one runtime and one paint per control, not all modes or application callbacks.

The existing protocol binder rejects unverified external owners. Its list role additionally requires report view and a valid native header; the observed item count and paint alone do not establish those conditions. A candidate must retain existing protocol checks and custom-draw fallback, verify the forwarding caller and parent, and handle removal/reparenting. Report-view data, callbacks and negative cases still need direct tests before a product change.

## Non-report view modes

A self-owned DelphiVCL4Python 1.0.7 sample created four distinct actual TListView instances, each with one item. At observed 96 DPI the released P202 DLL was loaded from assets and its SHA-256 logged. After synchronous redraw, x86 and x64 both reported `vsIcon`, `vsSmallIcon` and `vsList` unattached, while `vsReport` attached; native LVS_TYPEMASK and item counts agreed with the requested modes. Changing each of the three other views to `vsReport` and redrawing produced an attached report control with the item still present. Both isolated runs exited 0. Logs: build/t18-s64-vb-mask-survey/view-transition-{x86,x64}-p202.log. This demonstrates an actual missing entry path in one runtime, not complete visual or input evidence. The existing binder only accepts report view and requires a native header; the painting scope explicitly limits client typography to report mode. A safe extension needs independent public-protocol validation for other views, actual font/image/selection and custom-draw evidence, transition/lifecycle checks and negative cases; simply weakening the report check or treating attachment as finished styling is insufficient. No product binary changed.

The same four actual views were captured using a task-authored native PrintWindow helper in separate bare and styled runs at 96 DPI. Both widths exited 0; each non-report mode's 180x220 RGB image was identical between the two runs, whereas the report image differed by 5952 pixels. Files: view-capture-{x86,x64}-{bare,styled}-*.bmp and matching logs under the registered scratch. This confirms the sampled visible output remained unchanged, not that all app icons, image lists or view implementations are understood.

A parent/style recheck protects the protocol result against synchronous change; owner-draw, owner-data and grouped paint keep their prior fallback. It does not add icons, alter item data or extend the main-EXE candidate. This is pending validation, not a release.

With a temporary incremental candidate, real DelphiVCL4Python x86/x64 samples at 96 DPI attached all three non-report modes. These are bounded samples and not full-image or all application semantics.
