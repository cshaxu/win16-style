# M0 T18 S64: real runtime-owned Delphi tree and list observation

A project-authored private-desktop runner launched the optional DelphiVCL4Python 1.0.7 test runtime and created actual `TTreeView` and `TListView` controls. Both class and real class retain the respective Delphi class name, and the class owner on each width is the corresponding absolute DelphiVCL.pyd runtime module rather than the Python executable. In an initial empty sample, bare/styled x86/x64 all reported neither control attached and exited 0. In the styled data sample the tree had a parent and child node, and the list had one item; Delphi collection counts and the public TVM_GETCOUNT/LVM_GETITEMCOUNT messages agreed (2 and 1). After synchronous redraw both controls still reported unattached on both widths; both samples exited 0. Runtime samples are optional, not project dependencies.

This establishes an actual missing runtime-owned entry path for these sampled classes, not that all drawing or behavior is wrong, nor that class name or count alone is safe to authorize a renderer. The runtime's real native-control forwarding, caller identity, custom-draw callbacks, image lists, item semantics, reparenting, lifecycle, owner-draw and version/DPI boundaries require evidence before product implementation. No product or binary was changed. Scratch: build/t18-s64-vb-mask-survey/lists-real.py, page-runner.exe and real-lists-data-*-styled.log. M0/T18/S64 remain open.

## Native paint witness

A temporary task-owned IAT observer intercepted the runtime module's CallWindowProcW during synchronous redraw of the populated controls. On each width, the tree and list each forwarded one WM_PAINT to their respective currently registered system native procedure; neither observed call used another procedure. Both redraws succeeded, the imported slot was restored, and both samples exited 0. Logs: build/t18-s64-vb-mask-survey/real-lists-forward-x86.log and real-lists-forward-x64.log. This covers one runtime and one paint per control, not all modes or application callbacks.

The existing protocol binder rejects unverified external owners. Its list role additionally requires report view and a valid native header; the observed item count and paint alone do not establish those conditions. A candidate must retain existing protocol checks and custom-draw fallback, verify the forwarding caller and parent, and handle removal/reparenting. Report-view data, callbacks and negative cases still need direct tests before a product change.

## Report view

The real DelphiVCL4Python sample now creates one report column and one item. On both widths setting the binding property to the enum name `vsReport` produced LVS_REPORT, one SysHeader32 column, and an intact item count; the currently published DLL still reported both the report list and tree unattached. A temporary forwarding observer again saw one native WM_PAINT per control and restored its import slot, and both owned instances exited 0. Logs: build/t18-s64-vb-mask-survey/real-report-x86-styled.log and real-report-x64-styled.log. Initial integer property assignment did not produce report view; the native assertion detected that mistake. The test does not yet establish parent notifications, selection, actual styled pixels or safe reparenting.

In the same report-view fixture under the existing assets package, both widths selected the tree root via TVM_SELECTITEM and list item via LVM_SETITEMSTATE; native queries confirmed those selections and unchanged counts (two tree nodes, one list item). Both instances and the temporary forwarding observer exited 0. Logs: build/t18-s64-vb-mask-survey/real-report-x86-select.log and real-report-x64-select.log. The controls were still unattached; this is the old-package interaction baseline, not candidate or physical-input evidence.

The real-runtime scratch fixture now includes a candidate attachment assertion, before/after removal pixel comparison and post-removal selection/count checks. Running its assertion against the existing published package failed as expected on both widths at the missing-attachment check (exit 1), before claiming any pixel or removal result. This is a real old-package negative, not a passing candidate test. Logs: real-report-x86-old-negative.log and real-report-x64-old-negative.log in the registered scratch directory.

The shared incremental Ninja build s64-report-proto-195 configured x86 successfully but did not finish the x86 build within its 180-second budget; its result is failed-or-inconclusive. No x64 build or linked candidate was obtained from that run. Separate GCC syntax-only checks using the project's defines and strict warnings succeeded on both widths. A first syntax-only invocation omitted the required project defines and produced unrelated declaration diagnostics; it is not counted as a passing build. The timeout cause remains unconfirmed.

## Initial candidate and build diagnosis

An independent temporary diagnostic linked the two modified source objects with pre-existing local build objects and libraries. This is not a clean or releasable package. The real 96 DPI DelphiVCL4Python report fixture against this candidate attached both tree and report list on x86 and x64. The old assets failed the same attachment assertion on both widths. Candidate screenshots taken twice were stable; removal changed 1406 tree pixels and 508 list pixels on each width, with root and item selection and two/one item counts preserved after removal. Both samples and launchers exited 0. The changes do not alone prove exact Win16 appearance or application custom-draw, reparenting, all views, other DPI and runtime versions. Logs: real-report-x86-prototype.log and real-report-x64-prototype.log. No binary was deployed.

The clean alternate CMake/Ninja configuration also stalled during compiler ABI checking; its owned diagnostic was interrupted after observation. A minimal separate Ninja file executed `cmd /c echo` and produced the expected file, but Ninja failed to finish. Both the WinLibs Ninja and the separately installed Ninja exhibited this, including a PTY run. Independent direct GCC, disabled-cache ccache, normal isolated-cache ccache and shared-cache ccache compilation all returned 0. These observations narrow the issue to the observed Ninja invocation/environment but do not establish its root cause. Only the self-owned diagnostic processes were interrupted; no existing external process was terminated. Final clean dual-width Ninja build, tests and release remain mandatory.

A task-authored parent subclass was installed before the real runtime controls were created. It requested item custom draw, painted a magenta sentinel and returned CDRF_SKIPDEFAULT. Under the temporary candidate both actual controls attached; on x86 and x64 the tree retained 6048 magenta pixels and the list retained 4640, the same counts as their respective unstyled controls. The callback saw prepaint and item stages, selection remained intact, the subclass was removed and all four instances exited 0. This verifies this limited self-authored callback pattern, not all application callbacks or whole-image equality. Logs: real-custom-{x86,x64}-{bare,prototype}.log; diagnostic helper and fixture remain under the registered scratch path.

The same minimal Ninja command that hung inside the sandbox executed and returned exit 0 outside it; this is a demonstrated environment-dependent difference, not a diagnosis of the underlying mechanism. No global setting was changed. A separate ordinary project incremental build s64-report-proto-196 was launched outside the sandbox; its result must be inspected before drawing conclusions.

A real-runtime reparent test moved each candidate-attached control from its original form to a second task-owned form, sent a bounded ordinary message and verified the attachment retired; moving back did not silently reattach it. Tree selection, list selection and counts remained unchanged. Both x86 and x64 samples destroyed the second form and target form and exited 0. Logs: real-reparent-x86-prototype.log and real-reparent-x64-prototype.log. This is a specific SetParent sequence, not proof of every reentrancy or handle-reuse case.

The independent external-owner native fixture and test are now project test sources. The dual-width direct-compiled model passes the temporary candidate for fake paint, report owner-draw rejection, normal tree/list attachment, parent change retirement, item count and cleanup. The same positive attachment assertion fails under the old assets on both widths (exit 1). These are self-authored models, distinct from real runtime evidence; the original image assets and application callbacks are not part of the fixture. Package cases have been added for both widths. The incremental Ninja build s64-report-proto-196 passed x86/x64 and core ABI (one case each, no skips); build of the added model targets s64-report-model-197 is pending. Neither is a clean four-file release package.

The first Ninja integration build of the new model failed at x86 resource compilation because the newly added target omitted the existing `src` include path required by control_extensions.rc. The target was corrected to match the adjacent tests; rebuild s64-report-model-198 is running, and the failed attempt is not counted as a pass.

After adding the required `src` include directory, s64-report-model-198 built both widths under Ninja and passed each core ABI test, with zero skips. Build times were 2.49 seconds x86 and 4.41 seconds x64; this does not itself run the newly registered actual-package model cases. The clean package and its focused tests are still required.

Clean package attempt s64-p199-report-final stopped at the source receipt gate before building because the three modified sources and two authored test files had not yet had their receipts updated. The receipt hashes and project-authored test notices were then updated; a first check also exposed CRLF in the edited C files, which were normalized to LF and rehashed. Source manifest self-tests now pass 23 rejection cases plus the byte-exact receipt check; resource identity and its six substitution negatives pass. The stopped package is not a build or test pass.

This is not a clean package or release.

## P202 clean package and release

After the main-EXE regression fix, clean GCC/Ninja/ccache x86/x64 builds and ABI passed. The exact four-file candidate passed 22 focused actual-package cases in 50.16 seconds with zero skips, including both external-owner models, v5/v6 native trees and report lists, menu cancellation and page controls. This is focused coverage, not the full matrix or physical input.

Real DelphiVCL4Python x86/x64 samples against this candidate passed the attachment and removal pixel/selection checks, the limited CDRF_SKIPDEFAULT magenta callback comparison, and the SetParent retirement checks; all six exited 0. Their candidate DLL paths and SHA-256 were read in-process. Both installed assets DLLs were then independently checked with the actual runtime sample, preserving selection after removal and yielding the same 1406 tree and 508 list changed pixels; loaded DLL paths and hashes were recorded. Pixel change does not prove perfect visual identity. The old assets failed the new positive model on both widths.

P202 was published to assets root and O:/winnt root; all eight files matched the test package by SHA-256. Installed native fake-paint/owner-draw/reparent models passed x86/x64 at both destinations. Original graphic resource bytes and provenance passed identity self-tests; public ABI remains 31 named exports plus ordinal 1. Other DPI, runtime versions, physical input, IME and all custom-draw variants remain unverified; app-provided tree icons are unchanged.
