# M0 T25 S4：标题绘制与重绘审计（进行中）

S3 P1 的窗口状态取自 `GetForegroundWindow`，在非客户区激活通知与前台窗口变化之间可能取到旧状态；每个 `WM_NCMOUSEMOVE` 又无条件重画标题，并覆盖原有窗口图标。S4 在窗口所属线程记录 `WM_NCACTIVATE`，只在非客户区鼠标命中区域变化时补画，使用应用提供的小图标或窗口类图标，并在 `WM_SETICON`、标题、主题、样式及 DPI 变化后更新。窗口销毁时删除状态属性；没有修改应用图标所有权或系统主题。

标题字体使用 8 磅粗体 Tahoma，按窗口 DPI 换算；微软 [Windows UX 字体指南](https://learn.microsoft.com/en-us/windows/win32/uxguide/vis-fonts)说明 Windows 2000 目标使用 8 磅 Tahoma，[Windows User Experience 2001 指南](https://blog-geofcrowl-static-images.s3.us-east-1.amazonaws.com/2020-02-17-collection-higs/MS-Windows-User-Experience-2001.pdf)列出标题栏粗体。字体创建失败回退 Windows 现有 GUI 字体；未将此推定为所有语言及所有 Win2000 自定义方案像素一致。

2026-11-10 自建私有桌面双位宽 `run16s --2k --wait` 窗口探针：活动蓝色与失活灰色标题的实际窗口 DC 像素、初始图标、`WM_SETICON` 更新、`WM_SETTEXT` 更新均有像素差异；单次窗口缩放及最大化/还原后，不额外切换焦点即检查标题像素；标题命中和系统关闭通过。x86/x64 结果一致。探针使用同步消息，不代表物理鼠标、系统菜单、连续拖动、所有 DPI、工具窗口或原版截图已验收。

## 原版渐变对照与工具窗口

只读参考 `private/ntos/w32/ntuser/kernel/globals.c`（SHA-256 `0983d5b102a7baca49118f59ecad450c0377094b7766bc9bcb539ae91fa256e1`）列出活动标题 `RGB(0,0,128)` 至 `RGB(16,132,208)`，失活标题 `RGB(128,128,128)` 至 `RGB(181,181,181)`。`caption.c` 的窗口标题路径在扣除按钮区和图标槽后对文本区域绘制渐变；这些结论是只读行为分析，没有复制实现或资源。用户截图在按钮前采样 `RGB(14,115,198)`；修正后自有窗口相同边界附近采样 `RGB(15,130,207)`。这证明渐变区间和颜色端点修正，不证明完整原版像素或全部配色方案。

将普通窗口和工具窗口连续放在同一自建进程时，x86/x64 的绘制断言均通过，但私有桌面驱动返回 `PRIVATE_DESKTOP_LEAK`；串行复测同样返回该错误。此失败不计通过。拆为各自独立进程后，普通窗口及工具窗口 x86/x64 分别通过且驱动报告桌面释放，但不能证明同进程序列的清理已修复。只读复查期间未查到对应桌面的持有线程，以下测试桌面名称仍可打开：`Win16S-Dialog-26108-346120437`、`Win16S-Dialog-29336-346120531`、`Win16S-Dialog-23188-346136140`、`Win16S-Dialog-37772-346371906`；不能仅凭线程检查推定持有句柄的进程或擅自终止进程。

复查结果：上述前 3 个私有桌面 `OpenDesktop` 返回 2（对象不存在），可确认已释放；`Win16S-Dialog-37772-346371906` 仍可打开。没有据此声称最初的清理断言通过，也未确认最后一个对象的持有者。两种窗口分开测试时桌面均正常释放。

进一步交叉核对 `private/windows/shell/migrate/gradient.c`（SHA-256 `ddfab2d6af3766e235f3d17e5616061860a50f6046cf7e43424ef0bdd9ce3c17`）的 `Windows Standard` 及其大字号变体：活动与失活四个端点与上述内核默认色相同。来源是只读数据对照，不将该表或程序复制进本仓库。用户截图中的标题高度和按钮几何仍由 Windows 11 USER 度量决定，尚未宣称等于原版。

再次核验最后一个桌面 `Win16S-Dialog-37772-346371906` 时，`OpenDesktop` 返回 2（对象不存在），现已释放；原有清理断言失败仍保留，不归因为已知代码问题或宣称同进程序列回归通过。

## 未指定图标的窗口

原版 `caption.c` 的 `xxxGetWindowSmIcon` 在窗口和类没有图标时使用系统默认 WINLOGO；代码亦说明窗口级图标优先于类图标。原实现没有这项回退，导致有系统菜单但未设置图标的窗口丢掉图标槽。现按窗口小图标、窗口大图标、类小图标、类大图标、系统默认图标的顺序查询。自建无类图标窗口在私有桌面的 x86/x64 两个增量测试分别检测到默认图标像素 224、设置窗口大图标后变化 238 像素，均正常退出并释放桌面。测试使用本机系统 WINLOGO，不声称其图形与 Windows 2000 原版一致；未复制外部图像或代码。

## 几何边界

原版 `inctlpan.c` 的 `SetNCMetrics` 从非客户区外观配置取得普通及工具标题宽高，标题高度还包括边界线；`caption.c` 使用对应尺寸绘制标题和按钮。原版并非所有用户配置下固定一个标题高度。当前实现使用系统窗口的 `WM_GETTITLEBARINFOEX`，因此 Windows 11 决定实际标题、按钮和命中几何；单独缩小绘图矩形不能改变原生客户区或命中区域。几何实现及鼠标命中须作为后续窗口交互工作一起验证，不将渐变和图标验证写成原版几何一致。

P11 增加带菜单自建窗口的实际几何探针。已发布 P10 的 x86/x64 在本机均报告标题高 23、菜单距窗口顶端 31 至 50、客户区从 51 开始，菜单不重叠客户区；这不是原版标题高度通过。临时实验在 `WM_NCCALCSIZE` 中将标题与客户区按默认 19 像素高度调整后，原生菜单仍位于 31 至 50，而客户区提前至 47，重叠 3 像素，探针按预期失败。实验未发布并已移除，生产实现保持 P10。后续须同时处理菜单实际布局和菜单命中／交互，再推进标题及客户区几何；不得仅改客户区或宣称本次已实现原版高度。

后续候选先接入无菜单、非 RTL 的普通和工具窗口：按原版默认值及 DPI 计算标题高度，并同步调整客户区与客户区命中；带菜单窗口保留原生高度，避免 P11 所见的重叠。96 DPI 的 x86/x64 私有桌面增量测试中，无菜单普通窗口标题高 19、客户区从窗口顶端 27 开始且命中为 HTCLIENT；带菜单窗口仍为标题 23、菜单 31–50、客户区 51。工具窗口额外断言 16 像素标题高度。增量真实鼠标按下、拖离、最大化和还原在两位宽各一次通过；此范围不能推广到带菜单窗口、RTL、全部 DPI 或特殊应用，带菜单几何仍是未完成的主要工作。

正式包 40 项重点回归通过。正式包首次物理鼠标复测时 x86 的初次按下未被捕获（x64 通过）；探针增加前台等待后又出现两位宽未捕获，原因未确认。再增加最多 500 毫秒等待按下状态后，使用同一正式产品和单独增量编译的更新探针，x86/x64 各一次按下、拖离取消、最大化和还原通过。更新探针不在正式包构建快照中，产品源码与快照经 SHA 核对一致。不得以最终单次通过推断前述不稳定已修复。

进一步找到 Windows 2000 辅助功能向导 `accwiz.rc` 的 `IDS_WINDOWSDEFAULTSIZES` 字符串（SHA-256 `77d2aa83ba80effc99ef8faaab812fbf816bbe54312a68b13609e5b9b702d156`），按 `schemes.h` 的字段映射（SHA-256 `fffb39be68850262eef82ac5672de66989621c97c4db3a5aa3bbd8818fe95769`），该 Windows 默认组在 96 DPI 下普通标题按钮宽高为 18、工具标题按钮宽高为 15，普通及工具标题字体高度分别为 -11、-8。`inctlpan.c`（SHA-256 `811b46564e55365a524be50efc3a2f8d486c5b07189b6ae3dd5dc7af21c969d2`）将实际标题高度算为按钮高度加边界线；这些是该组默认设置，不代表所有用户配置或网图。

根据这组记录，工具窗口标题使用按 DPI 缩放的 8 像素字体高度，普通标题保留现有字号。相同增量探针在当前主机上，旧发布版工具标题字形高 9 像素并未满足该测试，新版 x86/x64 均为 5 像素并通过；具体字形由系统字体和栅格化决定，不等于原版逐像素比较。工具标题区域本身仍沿用当前系统几何，未宣称上述默认标题及按钮尺寸已经实现。

## P2 图标回归

用户在 Solitaire 截图中发现标题栏出现两个图标。只读对照原版 `winable2.c` 可见 `rcTitleBar` 排除了系统菜单图标区；现有 Windows 的原生非客户区绘制已绘制该图标，P2 又在标题文字区域画了一份。修复移除额外图标绘制及重复预留区域，保留系统图标绘制和命中。自有双位宽增量窗口探针实际检查原生图标区：设置大图标后改变 212 像素，而标题区同期变化 0 像素；普通窗口标题与图标更新测试通过。这不证明其他几何或图标资源与原版一致。

## 用户提供的配色参考

## 标题按钮状态补充

使用已发布 P4 的 `O:/winnt/run16s.exe --2k --wait`，在自建私有桌面分别运行 x86/x64 普通窗口。测试通过系统菜单禁用关闭命令并调用 `DrawMenuBar`；两种位宽的标题栏无障碍状态均报告关闭按钮不可用，实际按钮区域各有 94 个像素变化。重新启用后可正常关闭。测试还对窗口尺寸变化前后、系统命令最大化及还原时的按钮区域逐像素计算摘要，两种位宽均观察到最大化与还原图形不同且还原后图形恢复。测试结束私有桌面释放。此为命令及画面检查，不代表物理鼠标按住、拖离、释放、键盘菜单或所有 DPI 已通过。

后续自建可见私有桌面 `SendInput` 探针发现 P4 的真实回归：按住最大化按钮时原生鼠标跟踪循环把按钮画回宿主系统颜色，按钮区有 252 个系统面色像素。现由窗口附着器接管标题按钮的捕获、按下、拖离和释放绘制；在按钮内释放时仍投递对应系统命令，并在 `WM_GETTITLEBARINFOEX` 反映按下状态。x86/x64 的增量实测均观察到经典面色 362 像素、原生面色 0、拖离取消及点击最大化／还原成功；测试结束恢复原桌面与指针。此结果不证明完整 MSAA/UIA 事件、所有标题按钮、键盘、所有 DPI 或真实应用的特殊消息处理；这些仍须分别验证。

P7 在输入桌面仍为 `Screen-saver` 时，以 P6 已发布实际包和自建私有桌面窗口，分别对 x86/x64 发送按钮按下与释放消息并处理投递的系统命令。最大化、还原、最小化、恢复后关闭均观察到预期窗口状态；两种位宽的私有桌面均释放。该测试加入包测试清单。这是合成消息测试，不是物理鼠标输入，不能替代 P6 正式包中因屏保跳过的物理鼠标复测。

## 外框底色

此前仅绘制外框最外两条边，余下的当前系统非客户区边框仍可能呈现宿主浅色。现根据当前原生标题顶部与窗口外缘的距离填充四周经典灰色带，再画边缘；保留当前系统计算的客户区与命中区域。增量私有桌面双位宽实测的侧边框中间像素均为 RGB(192,192,192)，普通窗口、图标和按钮命令测试通过。该主机的标题区域距外缘 8 像素，而关闭按钮顶部距外缘 7 像素；因而改为先绘制边框、再绘制按钮，并排除系统菜单图标矩形，避免覆盖按钮或图标。未据此声称边框厚度、所有 DPI、滚动条或最大化几何与原版一致。

## 标题按钮默认尺寸

按上文 Windows 2000 默认资源数据，普通与工具标题按钮分别采用按 DPI 缩放的 18 和 15 像素正方形；在 `WM_GETTITLEBARINFOEX`、绘制及 `WM_NCHITTEST` 中使用相同矩形。关闭按钮与其余按钮之间留出缩放的两像素间隔；间隔按标题区域命中。原生客户区和标题高度没有改变，RTL、空间不足及标题高度不足以放置按钮时沿用原生矩形，尚未证明这些变体的原版几何。

以 96 DPI 自建窗口测试，旧发布版不满足按钮尺寸断言；候选的 x86/x64 按钮尺寸、中心及间隔命中、普通窗口系统命令和工具窗口测试通过。自建可见私有桌面鼠标探针早期出现 x86 按住状态两次失败，诊断期间两次通过；最终增量候选 x86/x64 各一次按下、拖离取消、点击最大化和还原通过。失败未归因，不因后续通过抹去；尚需正式包鼠标验证以及实际应用、高 DPI、完整无障碍和持续交互验证。
