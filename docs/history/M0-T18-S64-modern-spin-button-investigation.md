# M0 T18 S64: modern Delphi spin button

The P109 package leaves a real DelphiVCL4Python 1.0.7 x86/x64 TSpinButton unstyled beneath the now-attached TSpinEdit. At 144 DPI it is 15x31 in the DPI-aware target, owner is the same runtime module as its parent, and its class is its own registered class, not the legacy DoubleKiller path. A temporary import observer saw no direct runtime DrawFrameControl or DrawEdge during the forced redraw. A separate scratch diagnostic detour observed OpenThemeData(NULL, `button`) and two part-1 backgrounds into a compatible memory DC derived from this exact button window DC during an observer-marked WM_PAINT/WM_PRINT scope. Observed local rectangles were 15x15 and 15x17; the following TEXTGLOW calls used part 1 state 0 and must not be mistaken for button backgrounds. The diagnostic detour's logging is not an error-transparency or production caller-identity proof. DC lifetime and theme handle equality are observations, not universal ownership proofs.

A scratch-only prototype reused the existing classic button face when the observer's temporary target scope property and derived DC matched, then allowed the framework to draw its arrow. It is not a product implementation: its single TLS DC slot, class-name/caller checks, theme identity, nested scopes, errors, clipping and resource lifetime are not sufficiently validated. Separate 15x31 captures at actual 144 DPI changed 405 RGB pixels in each width, with all 32 baseline pixels whose RGB components were below 100 unchanged. This dark-pixel check does not prove preservation of every antialiased or colored pixel. Explicitly disabled parent samples also changed 405 pixels in each width, without validation of all disabled semantics.

A separate long-lived scratch observer subclass marked the owned control's drawing/input scope, and the self-owned external driver posted down/up to each button; both widths and both base/prototype runs reported `42 -> 43 -> 42` with two OnChange entries and zero exits/empty owned jobs. During an upper-button hold, the prototype's PrintWindow capture differed from its normal capture in 95 RGB pixels confined to x=2..12/y=2..12 in both widths. A further x64 trace observed button part-1 state 3 during the sequence, alongside state 1. These are synthetic messages and captured renderings, not physical input, full state/clip coverage, or proof of all color/glyph preservation. The scratch subclass and diagnostic DLL are not shipped. All instances were self-owned and cleaned; no product or binary was changed.

The legacy S27 path uses DrawFrameControl with a direct window DC and an EXE-owned native-EDIT parent; it does not cover this buffered themed path. A production candidate requires exact newly created parent/child and runtime ownership, a bounded same-thread paint/input scope and memory-DC lifecycle, independently verified BUTTON theme identity and eligible state/clip/geometry, preserving original arrows and application results, safe nested/reentrant destruction and a same-owner false-positive model. It must also retain legacy tests and pass actual same-batch packaging and dual publication before release. M0/T18/S64 remain open.

A further scratch diagnostic integrated the earlier experimental conservative theme registry around OpenThemeData, OpenThemeDataEx, dynamically resolved OpenThemeDataForDpi, and CloseThemeData. The first build failed on an x86 function-pointer cast, then on an x64 strict-aliasing cast; memcpy resolved those diagnostic build errors. With the existing 48-entry transaction, a self-owned x86 probe failed before finding its target and a separate x64 cmd target exited 0xc0000142. Static counting gives 49 candidate hook attachments including process hooks; increasing only the scratch transaction capacity to 52 let cmd exit 0 and both real Delphi widths complete. This is strong capacity evidence but no direct recorded ERROR_INSUFFICIENT_BUFFER, and is not a product change.

With registry recognition enabled, the actual dual-width spin-button captures still changed 405 RGB pixels, with the synthetic upper/lower button sequence 42->43->42 and zero process exits/empty jobs. A deliberately foreign observer drew BUTTON and TOOLBAR part-1 images in the same target-marked scope and derived DC, with the caller-module filter deliberately bypassed to isolate theme identity: BUTTON sample colors changed, TOOLBAR remained equal to baseline in both widths. A further diagnostic switch that bypassed theme checking changed the TOOLBAR sample in both widths. This shows the selected real APIs and cases are distinguished; it does not prove arbitrary theme aliases, failed closes, calls before hook installation, concurrent OS internals or all API paths.

The initial single-TLS-DC slot lost the outer DC when a second compatible DC was created and deleted within the same marked scope; in both widths its BUTTON positive control then remained native. A scratch bounded 16-entry map retained the outer DC and restored that positive control. However, a DC created in one scope and held into a later scope was incorrectly accepted in both widths; three sample RGB values changed versus native baseline. Adding a per-scope generation marker to the observer and recording it with each DC made the retained-DC samples match the native baseline while the nested same-scope positive still changed in both widths. The diagnostic observer intentionally bypassed the caller-module filter in these model cases; they do not establish same-owner application drawing safety. The map does not yet reclaim entries at scope exit, generation rollover/nested scopes and abnormal unwind are unproven, and the observer marker is not a product mechanism. An initial generation test failed before observation because the scratch observer introduced missing libgcc/libwinpthread dependencies; static-linking that observer fixed the subsequent runs. No product code or binaries changed.

A subsequent scratch candidate uses its own bounded per-paint stack and scope-local compatible-DC entries instead of the observer property. The real Delphi sample at 144 DPI still changed 405 pixels in both widths, attached the button and preserved the synthetic 42 -> 43 -> 42 sequence; both owned jobs emptied. A separate native C fixture with a same-module TSpinEdit/TSpinButton and real theme calls tested nested compatible DC creation/deletion, a DC retained into a later paint, a colored marker, detach and cleanup. The candidate passed both widths; the published P109 package failed the new attachment assertion in both widths. This model is not the Delphi runtime.

The same fixture then created an additional compatible DC inside the button paint and drew a separate same-sized BUTTON theme image from the same owner module, within the same scope and geometry. The candidate changed its sampled pixel from native 00fdfdfd to 00c0c0c0 in both widths. Thus these criteria cannot distinguish that independently drawn image from the button background; this is a synthetic same-owner counterexample, not proof a real Delphi application executes it. The candidate remains scratch-only and is not safe to ship on this evidence. Abnormal unwind, full clipping, theme API lifetime/failure transparency and other sizes/DPI remain unverified. No product source or binary changed.

A scratch follow-up tested a different boundary: retain the native theme backgrounds as a temporary pixel reference, wait until the runtime buffer is actually copied to the button destination, then replace the face and restore pixels changed after the backgrounds. The real x86/x64 sample each issued SRCCOPY from a compatible DC to the target window at 15x31; synthetic held/released input also issued 15x15 copies. The final copy caller belonged to a system module rather than the Delphi class owner, so requiring that caller to equal the owner prevented this genuine path. Runtime theme-background caller checks remained in the experiment. The self-owned same-module fixture passed x86/x64: classic face sample 00c0c0c0 vs native 00fdfdfd, the separately drawn same-scope image remained 00fdfdfd in both, retained DC 00c3c3c3 matched native, colored marker 001400dc survived, nested DC/detach/cleanup passed. This is one synthetic counterexample, not a proof against all same-source interference.

For real Delphi at 144 DPI, normal x86/x64 screenshot comparisons each observed 405 changed pixels and both widths preserved synthetic 42 -> 43 -> 42; target/launcher exited 0 and owned jobs emptied. Observer attachment was reported before the later draw and remained 0 at that point, so it is not evidence of early initialization. Direct PrintWindow captures of the held button had zero differences against the native held baseline in both widths, even after allowing the explicitly supplied print DC: that path remains unhandled or unverified. The scratch implementation uses slow per-pixel reads/writes and a large stack buffer; transparent error, allocation/stack pressure, clipped/partial presentation, printing, backgrounds modified after capture, all glyph colors, reentrancy and exception cleanup are not established. It is not production-ready, and no product code or binaries changed. An initial x86 observation stopped at an unrelated change-event timeout; subsequent runs set the fixture's documented skip flag and completed.

Correction to the preceding paragraph: its 405-pixel normal-screenshot comparison used a diagnostic build which, without the new experiment flag, still enabled the prior immediate-theme prototype. It was not a valid native baseline for the new algorithm. Additional instrumentation showed the first final-copy experiment matched but returned before overlay: during the second background the DC had a nonzero window origin, so resetting only the viewport origin made lower-half GetPixel fail. That invalidates the earlier inference that PrintWindow was an unsupported path; it remains a historical observation of an experiment that never completed the intended overlay.

The scratch algorithm now normalizes both DC origins during source capture, and a fresh true baseline was generated from the published assets package. At 144 DPI the real held-button captures with the corrected experiment differed by 405 pixels in both widths; all 32 baseline dark pixels matched. The owned x86/x64 runs exited 0, and their click sequence remained 42 -> 43 -> 42. These are synthetic inputs and dark-pixel sampling, not full glyph or physical-input proof. The source-DIB version replacing per-pixel GDI calls passed the same comparison and same-owner extra-image model. For 20 immediate synthetic model redraws, the published package took 2.584 ms x86 / 2.341 ms x64; the per-pixel version took 133.184 / 132.034 ms and the initial bulk-DIB version took 18.834 / 17.729 ms. These are single short observations, not a benchmark across machines or workloads.

A new self-owned model replaces the bitmap selected into the same DC after witnessed theme drawing, then copies an independently generated light image to the target. The initial bulk prototype miscolored its sampled 00fdfdfd pixel to 00c0c0c0 in both widths. Adding a selected-bitmap identity check in scratch made that sample remain 00fdfdfd in both widths, while the true Delphi held-button comparison still changed 405 pixels per width. Model nested DC, retained DC, marker, detach and cleanup assertions passed after this check. Immediate GDI process counts were stable at 18 -> 18 in one run per width, but later runs also observed 18 -> 25 in alternating widths; this aggregate observation is unresolved and is not proof of either a leak or leak freedom. Bitmap-handle reuse, background overwritten with identical pixels, exceptional cleanup, clipping, other DPI/versions and pixel-wide glyph fidelity are still unverified. The code remains diagnostic scratch, not a product change; no binary was published.

Follow-up resource, clipping, and exception models: across five batches of 20 redraws, aggregate GDI counts also varied in the published package (x86 17,17,24,24,17 and x64 17,17,17,24,24), so the earlier increases cannot by themselves be attributed to the scratch implementation. Instrumenting successful scratch DIB/DC opens and closes gave 322/322 with zero SelectObject/DeleteObject/DeleteDC close errors in each width after 100 redraws and additional tests. This does not cover allocation failure or exceptions inside helper operations. The same fixture sent WM_PRINTCLIENT to a memory DC clipped to 10x10: inside pixel 00c0c0c0 became classic while outside sentinel 00782850 was unchanged in both widths. A synthetic exception after the first witnessed theme background was caught in both widths, followed by successful repaint and balanced tracked resources; this does not cover every exception point. A nine-color synthetic glyph was preserved in both widths.

The separate scratch theme-registry model exposed an unsafe failed-close case: simulating a failed close and a subsequent open of the same handle left it eligible in both widths. An independent scratch-only adjustment marks the failed handle ambiguous/sticky and rejects it; both widths then passed that negative plus the prior shared-handle, class-alias, concurrent and nested-open and capacity cases. This is a simulated failed close, not a forced Windows CloseThemeData failure, and the adjustment has not been integrated into the diagnostic detours or product. Exceptions/reentrancy in the four API wrappers, pre-hook handles, handle-value reuse and unknown close outcomes still require proof. No product code, binary or production API changed.
