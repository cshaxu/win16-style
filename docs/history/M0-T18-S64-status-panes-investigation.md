# M0 T18 S64: Delphi multi-pane status investigation

A self-owned DelphiVCL4Python 1.0.7 sample with two ordinary status panes (Ready and Count: 42) was exercised with the P117 package at 144 DPI in x86/x64. Both TStatusBar windows were attached and the pane frames were classic, but actual WM_GETFONT and both visible text draws used Segoe UI. The clean capture shows both text panes with native glyphs. A temporary IAT observer inside the owned target recorded UxTheme calling DrawTextExW twice per pane: flags 0x420 for measurement and 0x820 for drawing. The drawing rectangles were (2,18,199,59) and (204,18,583,59), with the actual status HWND as WindowFromDC. All observed imports were restored, both targets and launchers exited zero, and owned jobs emptied. This is one runtime and DPI, not evidence for icon, owner-draw or other variants.

The P117 simple-status snapshot is intentionally inactive for multi-pane status. A potentially safer direction than querying SB_GETTEXTW during text rendering is to witness the native status control's DrawThemeText call and borrow only for its nested UxTheme text call, with an exact call scope, DC, native caller, pane geometry, ASCII and epoch checks. This is a hypothesis pending evidence of the entry caller, copy/lifetime and nested/exception behavior; no product change or release has been made. M0/T18/S64 remain open.

A scratch-only entry probe subsequently observed both panes calling DrawThemeText directly from their respective system WinSxS COMCTL32 module in both widths, part/state 0/0 and flags 0x820. The verified text rectangles matched the two pane bounds, and the same owned target/status DC was observed. All owned processes exited zero. This supports a bounded nested call-scope prototype without querying pane text in the drawing callback; it does not establish owner-draw, icon or exception semantics.

The bounded multi-pane prototype initially made x64 models loop in font lease release. A debugger attached only to the owned worker localized the loop; P117 source and an independent actual-DLL two-status model then proved an existing isolated-stock acquisition bug. P118 fixes that font ownership separately. With the fix, the scratch multi-pane prototype passed the previously affected border/icon models in both widths. The multi-pane text path itself remains experimental and is not included in P118.
