# M0 T18 S64: Delphi multi-pane status investigation

A self-owned DelphiVCL4Python 1.0.7 sample with two ordinary status panes (Ready and Count: 42) was exercised with the P117 package at 144 DPI in x86/x64. Both TStatusBar windows were attached and the pane frames were classic, but actual WM_GETFONT and both visible text draws used Segoe UI. The clean capture shows both text panes with native glyphs. A temporary IAT observer inside the owned target recorded UxTheme calling DrawTextExW twice per pane: flags 0x420 for measurement and 0x820 for drawing. The drawing rectangles were (2,18,199,59) and (204,18,583,59), with the actual status HWND as WindowFromDC. All observed imports were restored, both targets and launchers exited zero, and owned jobs emptied. This is one runtime and DPI, not evidence for icon, owner-draw or other variants.

The P117 simple-status snapshot is intentionally inactive for multi-pane status. A potentially safer direction than querying SB_GETTEXTW during text rendering is to witness the native status control's DrawThemeText call and borrow only for its nested UxTheme text call, with an exact call scope, DC, native caller, pane geometry, ASCII and epoch checks. This is a hypothesis pending evidence of the entry caller, copy/lifetime and nested/exception behavior; no product change or release has been made. M0/T18/S64 remain open.

A scratch-only entry probe subsequently observed both panes calling DrawThemeText directly from their respective system WinSxS COMCTL32 module in both widths, part/state 0/0 and flags 0x820. The verified text rectangles matched the two pane bounds, and the same owned target/status DC was observed. All owned processes exited zero. This supports a bounded nested call-scope prototype without querying pane text in the drawing callback; it does not establish owner-draw, icon or exception semantics.

The bounded multi-pane prototype initially made x64 models loop in font lease release. A debugger attached only to the owned worker localized the loop; P117 source and an independent actual-DLL two-status model then proved an existing isolated-stock acquisition bug. P118 fixes that font ownership separately. With the fix, the scratch multi-pane prototype passed the previously affected border/icon models in both widths. The multi-pane text path itself remains experimental and is not included in P118.

With a P118-based scratch DLL, an owned version-6 native two-pane fixture passed in both widths. Ordinary ASCII pane interiors changed by 331 and 447 pixels; a Chinese pane, SBT_OWNERDRAW pane including an application-origin DrawThemeText, and SBT_NOBORDERS pane retained their native interior pixels. The icon region had 230 colored pixels and none changed. The application font handle was unchanged; text mutation during snapshot fell back to the native frame, and the fixture cleaned up. The P118 package failed the first ordinary-pane pixel-change assertion in both widths. The first icon assertion mistakenly included neighboring antialiased text; restricting it to the system small-icon region removed this false positive. These fixture results do not prove nested theme-scope barriers, exception unwinding, other DPI or application versions. No multi-pane product change has been published.

Candidate P119 clean x86/x64 package and 28 actual-package focused cases passed in 16.14 s without skips. Actual-package DelphiVCL4Python 1.0.7 samples in both widths at 144 DPI produced status captures byte-identical to the prior scratch prototype; target and launcher exited zero and the owned job emptied. A scratch IAT probe raised a synthetic exception from UxTheme's DrawTextExW import while a pane was painting. The x86 probe caught it, restored the import and painted again. The x64 candidate exited with 0xC0000005, and the identical probe against P118 also exited 0xC0000005; a direct-raise self-check of the same x64 catcher passed. Therefore the cross-system-paint exception failure remains unexplained and cannot be attributed to the candidate or counted as a successful x64 cleanup test. P119 is not published.

The x64 vectored diagnostic recorded the synthetic e0425342 first, followed by c0000005 reading through the status drawing scope. In P118 the fault was ntw16s_status_frame; in P119 it was ntw16s_status_text_frame. A source inspection shows the ordinary WM_PRINTCLIENT status path sets status_current before DefSubclassProc and restores it only on normal return, unlike paths with explicit unwind cleanup. This is evidence for an existing scope-lifetime defect exposed by the synthetic exception, not yet proof of a complete fix or the only exceptional path. The new theme scope and ordinary status scope both need verified cleanup; P119 remains unpublished.

An experimental bounded cleanup around the existing WM_PRINTCLIENT status dispatch restores the prior status and paint scopes during unwinding. The formerly crashing x64 owned fixture then caught the same exception, restored the test IAT and successfully painted again. The regression has been added to the candidate; the clean package is being rebuilt. This verifies that specific print path and exception point only, not every WM_PAINT or exception path. The first clean-source build tree was modified for this scratch experiment after its previous package test; its previously built package files were not modified and their test result remains evidence for the earlier candidate only.
