# M0 T18 S64 P110: modern Delphi spin button

The modern DelphiVCL4Python 1.0.7 TSpinButton is runtime-owned, buffered and uses themed BUTTON backgrounds followed by TEXTGLOW. P109 styled the adjacent editor but not the button. P110 limits treatment to a new same-owner TSpinButton under a witnessed native-EDIT TSpinEdit, within its own paint/input scope. It witnesses the BUTTON theme and both half backgrounds on the same target-derived memory DC and selected bitmap. After the buffer is copied to the target, it composes the existing classic face and preserves pixels drawn after the native background. VCL keeps the arrow and input semantics. Unknown classes, untracked/ambiguous themes, incomplete source clipping, changed/deleted bitmaps and failed captures fall back to native drawing. TextGlow is separately witnessed; other theme draws invalidate stale background. The legacy EXE-owned spin path remains in place. No public export or product file was added.

The self-owned x86/x64 native model exercises theme identity, same-owner independent image, nested and retained DCs, selected bitmap replacement and replacement-back, different/failed themes, destination clipping, source clipping including a hole, nine colored foreground pixels, exception unwind, detach and cleanup. The new model fails against the P109 published DLL in both widths at the attachment assertion. During development a different-theme and source-clipping negative both detected incorrect recoloring in both widths before their fixes. Scratch-only injected failures at five DIB creation/copy stages and heap allocation fell back to native, with tracked cleanup; these fault injections are not shipped. The project theme tracker unit covers shared handles, aliases, failed close, nested/concurrent opens, capacity and exception cancellation. Four-thread actual theme stress completed 400 opens/closes per width. Actual non-null repeated close returned 80070006 identically to P109; actual same-value handle reuse was not observed.

The actual clean package with DelphiVCL4Python 1.0.7 at 144 DPI changed 405 pixels in the 15x31 held-button image in each width; all 32 pixels with RGB components below 100 matched baseline. Posted upper/lower inputs changed 42 to 43 and back to 42 with the expected two callbacks; target and launcher exited 0 and the owned jobs emptied. This is not physical-input or complete glyph-pixel evidence. Initial scratch testing recorded one unexplained x86 clip positive falling back to native; later bounded repeats passed, but the earlier observation remains unresolved. Other Delphi versions, non-144 DPI, unusual theme aliases/pre-hook handles, all states, exact glyph fidelity, complex exceptions and full T18 integration are not claimed. Application self-drawing and nonvisual controls remain outside scope.

Clean C17 MinGW GCC 16.1.0/Ninja/ccache 4.13.6 x86/x64 builds and ABI checks passed. The clean build snapshot.json SHA-256 is `0560922b7635ceac549783f358946401252fe59c57cf3f38ba7f7547e72aac94`. The identical four-file package passed 22 focused tests in 7.09 seconds and a separate 20 focused tests in 66.02 seconds, both without skips; the latter includes font, menu, VB and legacy controls. The same package was verified against real Delphi and published to both assets root and O:/winnt/system32. The new model passed both widths from both deployed locations. The longer font tests remain an efficiency issue, not a claim of fast full testing. Original five resource headers and provenance passed byte-exact verification.
