# M0 T18 S64: DoubleKiller Rich Edit investigation

A fresh copy of `D:/programs/misc/DoubleKiller.exe` (SHA-256 `cdd83ab909db749992d11ace2dff671493c0568d7a14697f8bef4b06d8647ca8`) was launched in self-owned isolated instances, bare and with the P120 assets launcher. Both instances exited zero and their owned jobs became empty. The styled process loaded `assets/ntw16s32.dll` SHA-256 `42a6aef0b6989f83d9cf23bb552ff330158d713af00355e60713f967b31d5bd5` and its root was attached. On the Help page the actual x86 `TRichEditURL` window was not attached; its style was `0x54212844`, extended style `0x00000200` (client edge). It is not evidence for generic Rich Edit classes.

In the target UI thread, public messages recorded a read-only rich text control, selection `(0,0)`, length 23401, event mask `0x04000001`, default Tahoma height 160 twips and matching format masks in both instances. This is a content-bearing formatted help view: those observations do not justify replacing its font or redrawing text and links.

A temporary test-only import observer first failed to locate the import by name because this executable has zero `OriginalFirstThunk` in its descriptors; no failed observation is counted as a negative. A second observer located the already-resolved `CallWindowProcA` slot by its actual USER32 address in the owned process, temporarily swapped it, sent an `EM_GETSEL` and redrew the visible Help control. Both bare and styled runs observed `EM_GETSEL` and `WM_PAINT` forwarded to the same procedure as the registered `RichEdit20A` class in `riched20.dll`. The test restored the slot (`restored=1`), and both processes and launchers exited zero with owned jobs empty. This proves the witnessed forwarding for this sample and these two messages; it does not prove any other Delphi version, all content, or the source of every nonclient draw.

A possible bounded implementation is to admit only a same-thread, same-owner, runtime-created `TRichEditURL` after a fresh same-owner ANSI native RichEdit paint witness, then reuse the existing outer client-edge painter without replacing fonts, scrollbars, formatting, text or application callbacks. This is a proposal, not yet implemented: the product currently witnesses `CallWindowProcW`, while this sample calls the ANSI entry point. The extra hook's transaction capacity, lifecycle and negative cases must be audited before changes. Tests need real content and formatting/selection preservation, scrolling and links without invoking external URLs, client pixels, edge-only differences, reparent/role changes, reentrant destruction, exception cleanup and dual-width native fixtures. Full-window screenshots in the two runs differ in geometry (bare 403 vs styled 411 pixels for the child), so no pixel-difference claim is made from them. No product or deployment changed; M0/T18/S64 remain open.

Static transaction accounting finds 52 hook requests when the optional DPI entry is present (2 process, 9 fixed style, 40 named style and 1 optional) against `HOOK_LIMIT=56`. A single ANSI witness would fit that static count, but capacity accounting alone does not validate aliasing, patch preparation, rollback, performance or runtime support; the actual executable's ANSI call path is the witness needed for this sample. No extra hook has yet been installed in the product.

An x86 scratch prototype adds a scoped `CallWindowProcA` witness for this exact class and, after the same-owner registered `RichEdit20A` WM_PAINT forwarding, attaches the existing frame/scrollbar painter. The first attempt erroneously omitted the new candidate from the coordinator's passive-candidate list, so the real window never reached its witness; correcting that list allowed the real owned instance to attach. A same-thread test observer captured the actual control before and after removing its style. After explicitly invalidating and synchronously redrawing both sides, 2376 outer-edge pixels and 4930 nonclient scrollbar pixels changed, while zero client pixels changed; the default format, selection, text length, event mask and scroll state matched. Earlier capture without symmetric redraw showed a transient 360-pixel text difference and is not used as preservation evidence. The original rich text content and image remain application/system rendered.

The real scrollbar's synthetic lower-arrow nonclient message moved its native position from 0 to 16 and released capture; independent `EM_LINESCROLL` moved first visible line 0 -> 3 -> 0 in both styled and removed states. The first attempt used `WM_VSCROLL/SB_LINEDOWN` and observed first-line 0 -> 0 in both states; that observation is not a successful line-scroll test. Target and launcher exited zero and the owned job emptied. The current screenshot shows the classic outer border and classic scrollbar. This is an x86 scratch experiment only, not a delivered implementation. It still needs strict reparent/role retirement, wrong-owner and unwitnessed negatives, dual-width native fixtures, real link/selection interaction, reentrancy, exceptional unwinding, resource release, actual-package tests and original-resource checks. The extra ANSI hook's runtime alias and transaction rollback also remain unverified. M0/T18/S64 stay open.
