# M0 T18 S64: Delphi MediaPlayer visual buttons

Self-owned DelphiVCL4Python 1.0.7 x86/x64 `TMediaPlayer` samples at actual 144 DPI display nine framework buttons with modern backgrounds. Exact class and real class were TMediaPlayer, owner the runtime module, class extra bytes zero, and enumeration found no child HWNDs. P93 assets attached the form but not the player. The sample did not open a media device or play media; target and launcher exit codes were zero and owned job counts zero.

A temporary diagnostic copy of the current DLL logged DrawThemeBackground. During ordinary drawing it observed nine part-1 BUTTON-looking calls with states 5 then 1, one rectangle per button, followed by the runtime's masked icon copies. In both widths the observed theme handle equaled a concurrently opened `OpenThemeData(NULL, L"BUTTON")` handle and differed from TOOLBAR in this experiment; handle equality alone is not a safe class identity under reuse, sharing or concurrency. Initial calls used the player's window DC; an observed buffered pass created a memory DC from a source whose WindowFromDC was the same player, drew the nine theme rectangles into it, and deleted it afterward. This is one observed DC lifetime, not proof for every print path or exception.

A scratch-only diagnostic hook reused the existing classic button face after theme drawing; the nine later icon mask operations still ran. At actual 144 DPI both widths changed 11,465 RGB pixels of the 298x40 player capture; in the nine observed icon rectangles all 224 baseline pixels with RGB components below 160 remained byte-equal, although background pixels in those rectangles changed. Explicitly disabled players showed the same measured counts. The dark-pixel test does not prove all icon colors, all icon pixels, dynamic states or media semantics. No media was opened. A first attempt to set ColoredButtons to a Boolean failed because it is a button set; that run did not reach valid observation and is not counted.

A per-window SetWindowTheme(empty,empty) trial returned S_OK; a positive control showed OpenThemeData(player,BUTTON) succeeded before but failed afterward while OpenThemeData(NULL,BUTTON) still succeeded. The full player capture nevertheless changed zero RGB pixels, so this API alone did not style the observed sample. A separate deliberate self-owned offscreen BUTTON-theme image was drawn outside the player: the prototype's stale-thread-window fallback modified its pixels in both widths. This is a verified false positive and forbids shipping that prototype. A proper candidate must avoid global/stale HWND inference, track only DCs derived from the exact target within a bounded drawing scope and retire them on deletion, establish BUTTON handle ownership conservatively, preserve original icon draw and application calls, and verify misleading calls, multiple targets, clipping, reentrancy, states and cleanup. The diagnostic logging changes LastError before the original theme call, so it is not evidence of error transparency or production-ready implementation. No product/binary changed. T18/S64 remain open.

A follow-up scope experiment instrumented the self-owned control subclass and scratch diagnostic DLL, but on this run the native driver failed to create its private desktop with Windows error 5, before launching the target. No scope observations or x64 run were obtained from this attempt. The experiment remains unverified; no code from it is in the product.

A sandboxed private-desktop attempt returned error 5; an authorized-environment retry could create the desktop. Its first x86 attempt failed because the freshly rebuilt scratch observer exported a decorated name (ready wait 258/error 1471); after correcting the scratch observer export, both x86 and x64 completed with target and launcher exit 0 and zero active owned processes. In each 144 DPI sample, an observer subclass marked the target WM_PAINT/WM_PRINT/WM_PRINTCLIENT scope while calling the original procedure. The diagnostic CreateCompatibleDC hook saw one DC created from the exact player window DC with this scope marker active; nine theme calls used the new DC and it was successfully deleted on the same UI thread. Observer subclass installation, redraw, capture, and IAT restoration succeeded. This establishes only the observed scoped path, not all lifecycles, theme class identity, nested/reentrant safety or resistance to application drawing inside that scope. Logging still does not preserve the incoming LastError, so this remains research instrumentation, not a product candidate.
