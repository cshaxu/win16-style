# M0 T18 S23 — VCL v5 progress border

The real 32-bit DoubleKiller 1.6.1.80 (`cdd83ab909db749992d11ace2dff671493c0568d7a14697f8bef4b06d8647ca8`) was run as a task-local copy on an isolated desktop; no scan, delete or user configuration change was requested. Its visible `TProgressBar` used the loaded x86 WinSxS ComCtl32 5.82, had `WS_EX_STATICEDGE`, and answered range 0..100 and position 0. The v6 state and color getter messages returned 0. The prior renderer correctly rejected those unknown values: 0 cannot establish whether a custom black color was set. Microsoft's [progress color documentation](https://learn.microsoft.com/en-us/windows/win32/controls/pbm-getbarcolor) describes the getter and `CLR_DEFAULT`; this observation does not treat an unsupported getter as a valid color.

The implemented role is limited to newly created, exact application-owned `TProgressBar` wrappers on the verified native v5 common-control module, with initialized range/position protocol, static edge, same-thread parent and supported style. The project overlays the existing classic black outline only on the verified nonclient edge, after native drawing. The original progress client paint, custom colors, range, position, font and application processing remain native. The role rechecks style and geometry at drawing time; unsupported layout, scrolling, marquee or insufficient nonclient space falls back to native. No public ABI, title/menu/font behavior, original bitmaps or provenance changed. This is a border-only improvement, not a v5 progress-fill renderer.

The actual clean candidate loaded `ntw16s32.dll` in the isolated sample at 96 DPI. Removing the attachment after capturing `WM_PRINT` changed 1,000 nonclient pixels and zero client pixels; native position remained 0 and the owned job exited empty. This is an empty actual progress bar, not proof of real scanning, filled states, other Delphi versions or physical input. A separate observer initially overwrote its first page log after detaching and falsely appeared to show nonattachment; restricting that observer to the next page corrected the record. No change was made to hide that result.

The self-contained x86/x64 native v5 model checked custom client colors and position 42, 656 nonclient pixel differences and zero client differences after detach at both 96 and 144 DPI, unsupported marquee and runtime style-change fallback, fake and emulated-state rejection, and stable GDI count across 12 captures. Existing v6 models passed both widths and DPIs. The prior S22 package failed the new v5 assertion on both x86 and x64. The 144-DPI checks are models, not a real 64-bit Delphi sample; in-place real progress mutations, live app scanning and all VCL variants remain untested.
