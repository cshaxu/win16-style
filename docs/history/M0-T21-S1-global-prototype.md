# M0 T21 S1：全局钩子隔离原型

## 用户要求与范围

用户要求手动全局模式覆盖已有及新程序，退出时尝试恢复原样；不能完全恢复可以接受，但要验证。UWP/XAML、自动登录启动不在本次范围。测试仅作用于新建私有桌面和本次自建进程，不在用户桌面安装钩子，也没有对用户已有进程操作。原型不属于产品，不能将其结果称为 `run16s --global` 已实现。

## 钩子和退出实测

自有 C 原型使用额外的测试专用 hook DLL 和双位宽测试控制器，在同一个私有桌面同时安装各自的 `WH_CALLWNDPROC` 全局钩子；钩子回调再显式加载已发布 ntw16s DLL。测试 DLL 和控制器仅为 scratch，并非产品四文件；将同样能力并入既有 DLL 的产品实现尚未验证。目标窗口的类和进程/线程均匹配自有测试目标时，才在该窗口 GUI 线程内调用真实已发布 DLL 的 `win16_style_install` 及 `win16_style_control_install`。不存在针对其他进程的扫描注入。旧窗口通过受控消息触发，新窗口使用首次显示消息自动触发。两个各自启动前已存在的自有程序和两个启动后的自有程序分别覆盖 x86/x64，结果：两宽已有和新窗口均附着，自有按钮均附着；四个窗口卸载后属性均清除；两种钩子撤销后另建程序不再接入。自有简单窗口在接管前、接管后及恢复后的 PrintWindow 标题区指纹分别不同、最终与起始相同。测试目标均正常退出。此为普通窗口及一个按钮的受控试验，不是所有应用或全部控件证明。首次自动新窗试验因观察器在窗口创建后、ShowWindow 前即读取状态，两宽均失败；改为有界等待显示消息后两宽通过，该失败不计作产品修复，也不能作为实际应用故障。

原型仅证明局部窗口样式安装与移除，不安装生产的 CreateProcess/文件对话框等完整进程钩子。

真实程序补充：在私有桌面各启动两份自有进程，分别为 64 位 O:/winnt/demo.exe 与 32 位 O:/windows/notepad.exe。对事先存在的主窗口发送受控消息后，钩子在其 GUI 线程接入已发布 DLL；随后启动的同程序主窗口由显示消息自动接入。demo 五个 Button 控件安装，旧记事本测试未计入按钮；两份实例都成功调用卸载且状态标记清除，进程正常关闭。实际加载路径为 O:/winnt/ntw16s64.dll 和 O:/winnt/ntw16s32.dll，SHA-256 分别为 ae6eed598f859056a02512fcf9f2a3f0fd543dfcec531f26d9034fcc7d08225d 和 72e8b694d2db4623851717ae1fe4fd29735320479a1d1a7df23598882fc6a211。demo 的 SHA-256 为 ac27cbdfa2039c6821c369d37ed9e7ae03814ea308bc125e261a599ec9a6022c；旧记事本为 cf2d882d6ec84bb4f9e6475d3b3674e4a480153ff3d34caab617f1a799a45ad0。

系统 C:/Windows/SysWOW64/rundll32.exe 加载自有 x86 原型 DLL，在私有桌面安装并维持 x86 全局钩子，实测旧记事本已有与新窗口接入；停止事件触发后宿主退出码 0。此证据只证明该有限宿主机制可用，不证明生产权限、通信安全或异常恢复。

## 恢复限制与风险

简单自有窗口的标题区 PrintWindow 指纹在卸载后与原始一致；真实 demo 和旧记事本则不完全相同。demo 有可见控件边界残影，原型尝试在卸载后对父窗及子控件发起完整重绘，仍观察到像素差异；旧记事本卸载前后的完整截图只见少量边缘差异。PrintWindow 不等同合成后的真实屏幕，激活状态及截图时序也可能影响差异；不能把这些差异直接归因到某个唯一原因，也不能宣称所有原样恢复。用户明确接受退出后有残影，S1 不以消除残影为收口条件；保留实际差异，不冒称逐像素恢复。

原型通过显式受控消息触达既有目标，并未证明任意无响应 GUI 线程、每个已有窗口、自动遍历现有全部进程、菜单/滚动条/编辑控件及自绘内容均可恢复。未验证异权限、受保护应用、其他会话/桌面、所有应用、子进程传播、退出异常、资源泄漏或真实鼠标交互。`win16_style_install`/remove 是局部窗口样式能力，不等同 DLL 注入与全部传播/窗口钩子初始化。现有 startup_hooks 只允许进程启动期事务，其 abort 失败可能终止当前进程，不得对运行中的用户进程复用。要完成产品仍须设计安全晚期接入、线程重入、识别、ACL、资源所有权及无法接入回退。普通 `run16s <filename>` 未修改。

用户明确要求研究已有进程接入；现行架构规则仍保留上阶段的扫描限制，后续产品实施如需受控枚举或注入既有目标，应在实施前按已获用户授权协调治理规则；此项不需重复征求授权。

## 构建、回归与交付

本 S 未改任何产品代码或二进制。`s1-clean` 的 x86/x64 GCC/Ninja/ccache 干净构建与 ABI、原资源和来源自检通过；但自动打包以 T21 检查现有 T20 产品版本时失败。保留该失败，不将其称作通过。随后针对该同一批重建文件，按其实际 T20 版本运行 check_package，四个 PE/版本/来源检查通过；该重建包不是已发布包，不覆盖 assets 或 O:/winnt。其双宽 DLL 分别再次用于自有独立桌面全局原型，已有/新窗口、按钮、卸载、撤钩后新窗口均通过。

首次 `t21-s1-version20-check` 聚焦包回归因脚本要求精确字符串 `draws=3` 失败；对应 x86 `menu-initial` 实际输出 `draws=6 idle=1`、进程退出 0，探针断言本来允许至少三次，属包脚本过严。第一次整轮不计通过。随后 `t21-s1-version20-retry` 选择双宽系统菜单代表项及强制基础用例，共 10 项通过、无跳过；覆盖普通启动、双位宽附着及传播，未运行全矩阵。过严标记留 TODO。

这批重新编译文件摘要与现行发布批次不同，未发布，也未声称更新产品。S1 原型源码和输出仍存于任务 scratch `build/t21-s1`，供 T21 后续自有隔离研究核查；原型未经产品化审计，不纳入正式包。用户明确接受退出后残影，故 S1 对该现象如实记录而不要求完全消除。

S1 按用户要求的可行性验证收口，T21 保持开放；全局产品入口、已有进程通用初始化、完整退出恢复及权限安全均未实现或未证明。后续 S2 继续实施，不能将 S1 研究结果扩展为所有程序已兼容。
