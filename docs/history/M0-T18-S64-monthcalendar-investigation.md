# M0 T18 S64: Delphi TMonthCalendar investigation

The [author's Delphi XE archive](https://mrxray.on.coocan.jp/Delphi/plSamples/164_DatePickerComponent.htm) has SHA-256 `646b7ea766d1c601308e58dcf14cf6f9fd5f6ede7a3a99b8b6f7fb727e8f6ff2`; its `06_SetLocaleInfo/Project1.exe` has SHA-256 `c29ed87676be83cbeca36e9b9eadf01fb302e43c6ca3b6ca1708efae447f41a1`. Source and form review found that the sample's button and normal close handler write global locale settings. The probe never clicks either button or sends WM_CLOSE; it terminates only its own bounded job after observation. Consequently cleanup is confirmed but normal program shutdown is not tested. No sample source or resource was incorporated into the product.

At 96 DPI the real x86 Unicode application-owned `TMonthCalendar` has no client edge and is unattached by P124. Both native and P124 instances returned the date 2015-11-02, accepted a change to 2015-11-15 and restored the original. A same-thread temporary import observer established that WM_PAINT and MCM_GETCURSEL were forwarded via CallWindowProcW to the registered `SysMonthCal32` procedure; it restored the import and the owned job emptied. This witnesses only the tested operations and sample.

On an isolated native instance, temporarily disabling that window's theme and setting the six public month-calendar colors to a white/black/dark-blue palette produced a visibly different calendar while preserving the selected date; all six reported prior colors were restored before returning the original theme. The theme-only comparison also changed approximately 36,000 client pixels. Microsoft's [MCM_SETCOLOR documentation](https://learn.microsoft.com/en-us/windows/win32/controls/mcm-setcolor) states that most colors have no visible effect while visual styles are active. These observations do not prove safe adaptation: the sample reported `MCM_GETMINREQRECT` width 225 before disabling its theme and 190 afterward (heights 160 and 158), which may change application layout or leave unused space. On restoring the original theme the minimum returned to 225 by 160. No claim is made that the temporary palette is a complete Win16 calendar.

Any implementation must first preserve application-selected colors and the documented MCM_SETCOLOR return value, track or safely retire on later color/theme changes, cover multiselect and date range, focus, notifications, resize, clipping, DPI, reentrancy and restoration, and establish a layout strategy for the changed native minimum dimensions. Existing styling must not replace the app's custom calendar contents or change system settings. This investigation made no product or binary change; scratch is `build/t18-s64-vb-month-survey`. M0/T18/S64 remain open.

## Font geometry and theme-text experiment after P127

In the same real x86 Delphi XE sample at 96 DPI, a self-owned probe measured the selected date's public calendar cell at 31 × 15 pixels. The control reports Tahoma with a 13-pixel text height; `30` measures 12 × 13 and `Wed` measures 22 × 13. The stock System font measures 16 pixels high, with those strings 16 × 16 and 30 × 16. Thus selecting the stock font without a layout change risks vertical clipping; these measurements alone do not prove how every theme positions text.

A scratch-only x86 DLL selected the stock System font into the drawing DC around calls to the existing `DrawThemeText` trampoline, restoring the prior selected object afterward. A same-window client screenshot on the real sample was byte-for-byte pixel-identical to the P127 package screenshot (225 × 187, zero differing RGB pixels). This experiment does not establish the internal reason, nor prove the result for other themes, but rejects this attempted route on the observed system. The helper forced termination of its own job to avoid the sample's global-locale close handler; cleanup reported zero active processes, not normal shutdown. The first scratch observer failed with error 127 because its x86 export had a decorated name; rebuilding it with an undecorated export fixed observation. Neither experimental DLL nor sample is a product input.

A safe font solution still needs evidence of the actual text rendering and measurement path, language coverage and clipping/interaction behavior. Do not change the application's font handle or claim an unchanged screenshot is a font adaptation.

## Theme text call path and unscoped drawing experiment

A scratch-only trampoline observer traced `ExtTextOutW` synchronously inside the native `DrawThemeText` call in the real sample. The selected face was Segoe UI, text height 15; date and weekday runs used `ETO_GLYPH_INDEX` (0x10). This explains why selecting System only around the outer theme call had no visible effect in that run: the nested observed output used Segoe UI. The glyph indices belong to that font and cannot be passed unchanged to a different font. The observation is specific to this theme and 96 DPI x86 sample.

A separate deliberately unscoped, scratch-only experiment replaced theme text calls with `DrawTextW` of the original string using stock System and the theme text color. It visibly changed the glyphs, but the weekday headings crowded together in the 31-pixel grid; it did not establish clipping, localization, accessibility or full text semantics and was not admitted into product code. Its use of a broad scratch hook is an experiment only, not a proposed implementation. Both owned jobs reported empty after forced termination to avoid the sample's locale-changing close handler. Further work must establish a safe identity scope and matching measurement/layout strategy rather than transcribing shaped glyph IDs or changing global font policy.

## Proportional bitmap and measurement experiment

A scratch-only test used the existing proportional System bitmap generator with an artificial 78/96 scale to obtain approximately 13-pixel glyphs, then drew original strings in place of theme text. This is a feasibility experiment, not a DPI policy or admitted implementation; the scratch instance retained the generated font until process termination and therefore is not a resource-lifetime test. In the 96 DPI sample, weekday rectangles were 31 × 15 and measured replacement strings used up to 25 × 14, so these tested headings fit. The screenshot alone concealed another issue: the `Today` string's native rectangle was 82 × 17 while the replacement needed 106 × 15. A blanket replacement therefore risks clipping and must not be shipped. The deliberately unscoped observation included unrelated themed controls as well; their reported overflows are not evidence about the month calendar.

The native month and numeric strings also contained U+200E LEFT-TO-RIGHT MARK (for example, before the year and date digits), while English weekday labels did not. Any implementation must preserve directionality and explicitly validate unsupported scripts rather than treating strings as ASCII or mapping foreign shaped glyph indices into System. One potential direction is per-run native fallback where measured text does not fit, with correct font lifetime, same-window paint witness, clipping, glyph and bidirectional-text tests; this remains a hypothesis rather than an implemented solution. All experiments used the single x86 sample and forced termination of its owned job to avoid its locale-changing close handler.

## Scoped, measured scratch prototype

A subsequent scratch prototype restricted replacement to the witnessed same-window month paint and selected theme roles/flags, checked text for ASCII plus U+200E, measured the proportional bitmap text and fell back to native when it did not fit. On the real x86 sample, comparison to P127 found 486 changed title pixels and 2643 changed grid pixels; the public Today region and remaining client area had zero changes. A next/previous-month interaction returned November → December → November and released capture. This demonstrates only the tested English locale and 96 DPI; it does not establish shaping, all Unicode, title overlap, other themes or physical input.

The scratch prototype then moved the cached font into the attachment and returned each borrowed reference through an unwind cleanup. In one isolated model run per architecture, 8 x86 and 8 x64 released font handles each immediately returned zero from `GetObjectW`; concurrent attachments, exception during text drawing and font-resource lifetime were not proven. The existing model's pixel assertion had to be relaxed in this exploratory copy because text changes also affect the selected-cell pixel count. Both model runs then completed, but this is not accepted as a regression pass: independent assertions distinguishing selection background from glyph changes and a negative font test are still required. The real sample again required forced owned-job termination to prevent its close handler changing global locale. Scratch code and binaries are not product inputs; no package was built or published for this experiment.

## Pixel separation and font-reference fault injection

A scratch model now counts exact active-palette background pixels separately from all changed selected-cell pixels. In both architectures the ordinary selected state had 454 new palette pixels, while the tested today-selected and disabled states had zero. The exploratory font-enabled case also required a nonzero changed text-region count; P127 lacked it and failed the new check in both widths. This establishes a useful negative but does not by itself identify every changed pixel as a correct glyph.

A scratch-only fault injected an exception after the font was selected during native text drawing. After invalidating the window first, both x86 and x64 tests caught the injected exception and successfully redrew. A temporary diagnostic export returned the cached font handle; after removal `GetObjectW` returned zero for both architectures. Removing the borrowed-font release deliberately caused that same assertion to fail on both architectures. Neither the diagnostic export nor the exception switch is acceptable in a product package; a production-independent observation mechanism and more coverage are still required. The first exception attempt did not invalidate the window and therefore did not execute the target draw, so it failed rather than counting as evidence. One subsequent rebuild copied an older source timestamp and initially reused the deliberately broken object; touching the source and rebuilding both widths corrected that experiment, and fresh broken binaries were separately confirmed to fail. No claim of a product fix or package delivery is made.

## Test-owned import observation

The scratch model now observes the product DLL's `SelectObject` import in its own process and GUI thread, captures the actual generated font handle, forwards the original function and restores the import afterward. Its observer also injects the drawing exception; the scratch product no longer needs the test-only export or environment switch. Both architectures pass the color/text comparison, exception recovery and captured-handle release assertion. Separately built candidates that deliberately omit the font borrow release fail the handle assertion in both architectures; the P127 package fails the new font-change pixel assertion in both. The observer is based on the existing project-authored `vcl_date_module` IAT fixture and does not patch a system API entry or another process.

This remains experimental: the product code has not been admitted, and the modified test's aggregate pixel check still needs a more precise glyph/region assertion, local-language and DPI coverage, concurrent borrowing and cleanup tests. The scratch model's passing marker alone must not be presented as full integration coverage.

The same test-owned observer also verified two simultaneously attached calendars in each architecture: both selected the same cached font; removing the first left its handle valid, while removing the second invalidated it. This covers that particular shared-cache order, not arbitrary reentrancy or every GDI resource.

## Region, fallback and failure checks before package

The scratch model now separates public calendar-body and footer rectangles: both widths observed 2629 changed body pixels, zero footer and zero unrelated pixels, with ordinary selection showing 454 added palette-background pixels. The simulated 144-DPI case changed no font pixels; this checks a branch only, not a real 144-DPI desktop. A shared text predicate accepted English text and U+200E while rejecting CJK, U+200F, line breaks and overlong strings; no real non-English calendar was exercised. A test-owned SelectObject failure after font-cache warmup left the native font path intact in both widths. The first negative test overlooked a title-only difference; adding a same-run header comparison made the intentionally broken `HGDI_ERROR` handling fail in both widths.

Review found the observed native text flags include `DT_NOCLIP`. The admitted code now explicitly intersects the existing DC clip with the native text rectangle before its replacement draw, and still needs verification of the revised code and arrow overlap for unusually long calendar titles. No new actual package, deployment or remote delivery is claimed.
