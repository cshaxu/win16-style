# M0 T18 S64: real VCL TFrame default investigation

The DelphiVCL4Python factory previously could not instantiate TFrame; that was only a binding limitation. The existing GoVCL 1.2.10 test-only libvcl exposes public `Frame_Create`, `Frame_SetParent`, `Frame_SetBounds`, `Frame_GetHandle` and related APIs. A self-owned C fixture created a form containing a real TFrame and a real VCL button, on a private desktop, separately using x86 and x64 libraries. The libraries remain test-only and are not included or required by the product. Their hashes are recorded in the CoolBar investigation.

Bare and P169-styled samples both reported class and real class TFrame, style 0x56000000, exstyle 0x00010000, window and client both 240x130, so there is no independent nonclient border in this default case. The styled root and child button were attached, the TFrame was not; the bare counterparts were not attached. On each width, a sampled parent background pixel was f0f0f0 before, and setting the frame's public ParentColor and Color properties made the sample exactly d29650 in both bare and styled runs. Form release destroyed root and frame and all runs exited 0. The fixture tests one default and one explicitly assigned color, not a full pixel comparison or all TFrame styles, versions, control states and DPI. It establishes that this sample's nested ordinary button enters the existing renderer; it does not establish that the TFrame family is fully styled or that background replacement is appropriate.

Initial fixture compilation failed due to a `handle_t` name colliding with an RPC typedef; after renaming, both widths compiled and passed. The later color extension first failed to link without gdi32; adding the missing test library fixed it. No product changes or binary publication in this investigation. Test-only sources and executables reside in the registered `build/t18-s64-vb-mask-survey` scratch. M0/T18/S64 remain open.

## Nested ordinary controls in a real TFrame

A second native fixture creates seven real visible children in the same real VCL TFrame: TButton, TCheckBox, TRadioButton, TEdit, TMemo, TComboBox and TListBox. In x86 and x64 P169 runs each control had the frame as parent, resolved its real USER Button/Edit/ComboBox/ListBox class, and reported attachment. The fixture set and read a checked state, edit text and one list entry; all three remained after individual style removal. Window PrintWindow captures before/after removal differed by 6300, 6243, 6240, 788, 844, 1034 and 848 RGB pixels respectively on each width; both captures contained nonzero pixels. These are observed differences, not an independent pixel oracle for correct Win16 appearance; capture stability, keyboard/mouse events, all control semantics, other states and DPI remain unverified. The seven attachments and state preservation establish a more useful nested-container case than the first single-button observation, but do not reclassify the TFrame family itself as fully supported. Form release and both fixture processes exited 0. Test-only fixture remains in registered scratch; no product change or binary release.
