# M0 T18 S64: Delphi TValueListEditor investigation

The [author's Delphi XE example](https://mrxray.on.coocan.jp/Delphi/plSamples/056_TValueListEditor_Button.htm) provides a source-and-binary archive SHA-256 `a330700855ee5698da8eb5b1e2b35cf0dd25bf28ddca8cc3c4c5e3adfbed7dbc`. The inspected `01-01_Basic/Project1.exe` is x86, SHA-256 `5c50d9eac287ddddfc2682060d67fd1fb10a13180ef960ae50c18594597f2b7f`; its form constructs a `TValueListEditor` with an ellipsis editor, and the source's button event only opens a message box. The sample and its original files remain solely in `build/t18-s64-vcl-value-survey`; no sample code or artwork has been incorporated into the project. The displayed sample initially failed to observe with error 193 because the probe driver was x64 and its hook DLL x86; the corrected matching x86 driver succeeds.

Both bare and P128-styled isolated jobs exited zero after normal close. The P128 process loaded `assets/ntw16s32.dll` SHA-256 `6492f9b51b05f8bf490b4d7fd87ca47acfb059a4d42a8aee1127b28ef91ce757`. Its root attached; application-owned `TValueListEditor` (`style=54010000`, `ex=00000200`, no visible scrollbar) and its `TInplaceEditList` child (`style=540000c4`) did not. The right-hand ellipsis button is part of that child rather than a separate Button HWND. Its modern appearance was visible in the native screenshot.

A scratch-only x86 hook recorded that the same application module calls `DrawThemeBackground` on the child DC for a 17×20 right-edge rectangle, button theme part 1, state 1. A correlated `OpenThemeData` call identified the theme handle as `button`. A restricted experimental overlay reused the project's existing button-face painter after native rendering; normal and experimental 250×241 same-sized captures differed by 323 pixels, all within the 17×20 button bounds. The sample still painted its own ellipsis. This cross-instance image comparison is preliminary and is not a substitute for a same-window before/after comparison.

An owned-thread probe synthesized a click and automatically closed only the modal dialog produced by the sample. P128 and the experiment each produced one dialog, retained the text `A-100` and released capture; both jobs exited zero. The experimental DLL SHA-256 is `48e14bc6a707f9551122c7181066d6f707006f4f1c14e11520b44784b32e0325`. Neither observation proves other edit modes, theme states, focus/keyboard, selection, reparenting, DPI, clip, exception handling or resource lifetime. The unscoped scratch overlay is not an admitted production change: a production design must establish same-window paint and owner identity, role/geometry, theme lifetime, state semantics and safe fallback, then verify both widths, real application and a clean actual package. M0/T18/S64 remain open.

## Pick-list editor and native dropdown

The same real sample's first value row switches the existing editor from an ellipsis button to a dropdown button. P129 left the arrow visually modern. A scratch observer recorded an application-owned call on the same `TInplaceEditList` DC and right-edge rectangle, part 1 state 1; its `OpenThemeData` handle corresponded to `combobox`, not `button`. The parent/value editor and the frame remained unchanged. Alt+Down opened an application-owned `TPopupListbox`, 13 items, initially no selection and not attached. Choosing index 1 and sending Enter to the focused editor produced exactly the selected list text, hid the list and left capture empty. Direct synthetic button click, F4 and Enter sent to the popup did not open/commit the list, and are not counted as successful interaction. The sample exited zero in owned jobs.

A scratch implementation tracked the COMBOBOX theme handle through open/close tickets, scoped its extra check to the already-witnessed editor paint and reused the existing classic button face and original 7×9 combo glyph. On the same real editor, removal changed 340 pixels inside the button and zero outside; the original glyph matched 63/63 pixels. A new isolated run again opened the 13-item list and selected index 1 with matching text, popup closed and capture empty. This is an x86/96 DPI sample, with no physical input or claims for other locales or versions.

Self-owned x86/x64 models verified the 63/63 original glyph, clip boundaries, wrong drawing context, disabled/hot/pressed fallback, shared existing ellipsis behavior and cleanup. P129 fails the new positive dropdown assertion on both widths. An experimental inversion of the arrow pixel selection (without editing the original resource) failed the glyph assertion in both widths. Theme tracker model cases cover COMBOBOX identity, stale tickets and aliasing with BUTTON; source samples and experimental DLLs remain in scratch. The subsequent P130 package and deployment are recorded in [P130](M0-T18-S64-P130-valuelist-dropdown.md).

## Popup list boundary investigation

P130's real x86 sample creates its 13-item `TPopupListbox` as a child of an application-owned, same-thread parent (`44b10041`), then reparents it to the desktop before displaying it (`54a10041`, ex-style `88`). Its class belongs to the sample executable. The desktop belongs to another thread; that does not make the sample-owned list a shared host. An observer temporarily replacing only this owned executable's `CallWindowProcW` import, then restoring it, recorded `WM_PAINT` forwarded to the registered USER32 `LISTBOX` procedure. This evidence applies only to the observed sample and exact creation/paint sequence, not every VCL listbox.

A scratch-only x86 DLL admitted the application-owned original parent and deferred the native-procedure witness until after the list had moved to the desktop. After a synchronous frame redraw, the list was attached. A same-window remove-and-redraw comparison found 2,268 changed nonclient pixels and zero changed client pixels, with the same Tahoma font handle and all 13 items retained. Selecting item 1 and sending Enter to the editor returned the item's three-character Japanese text, closed the list and released capture. The owned job exited zero. An earlier image read before synchronous frame redraw showed no pixel change; attachment alone was therefore not treated as rendering evidence.

This experiment has not been admitted as a product change: x64, negative ownership/forwarding cases, reparenting and lifetime, scrolling, DPI and package regressions remain untested. The scratch candidate and probes are under `build/t18-s64-vcl-value-survey` and must not be published. A possible limited implementation is to retain the observed creation owner and same-thread original parent, require the exact native LISTBOX paint witness and expected desktop reparenting, and reuse existing nonclient rendering without changing the client or font; it must retire safely when that identity changes. No product source or binary was changed in this investigation.
