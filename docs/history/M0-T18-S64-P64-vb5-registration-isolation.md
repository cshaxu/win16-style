# M0 T18 S64 P64: isolated VisData registration boundary

A scratch-only x86 debugger continued P63. At the initial debugger breakpoint it installed guards for eight observed native registry mutation entry points, redirected `LoadTypeLibEx(REGKIND_REGISTER)` to `REGKIND_NONE` within the owned target, and later simulated selected registration results without performing the requested mutations. This is deliberately altered application behavior for diagnosis, not an installation, a product mechanism, or a proof of ordinary execution. The trace does not cover all possible registry APIs, direct syscalls or writes before the initial breakpoint; it cannot prove the complete registry was unchanged.

With registry creation denied, `RegisterTypeLib` for the sample's own typelib returned `8002801c` and the Error dialog appeared. `LoadTypeLibEx(REGKIND_NONE)` separately identified its typelib as `{ECDCAED1-6F9C-11D0-B4D0-00A0C911E8B6}`, exactly matching the requested `TypeLib` key. A read-only 32-bit registry access check returned 5 for create access to HKCR TypeLib, and returned 2 when looking up that typelib key. This is evidence of a registration boundary, not by itself a complete causal proof for the unmodified process.

A negative-control test attempted to create a uniquely named HKCU test key: the guard produced access denied and the key was absent before and after. A second negative control simulated successful creation and value assignment using a duplicated read-only handle; the target observed success and the unique test key was still absent. In the sample, after simulated `RegisterTypeLib` success, class/key/value registrations were also simulated within that target. A private native probe answered No to the exact SYSTEM.MD startup prompt, and a real `ThunderRT5MDIForm` titled VisData became visible. This only proves progression in the modified diagnostic environment, not a normally registered startup. The two specifically checked VisData typelib/CLSID paths remained absent after the observations.

The probe then posted the source-identified Microsoft Access menu command against a private copy of Biblio.mdb. No file dialog or VB5 Data control was observed. One instrumented run exited `c000041d`; after removing loader/COM breakpoints before posting the command, another exited `c0000005`. The private database retained SHA-256 `dfb0194a5b9d7986d5a5ce2ca86567c245ebb97a3792dd1142b1327a077b599c`. Because registration was simulated and the debugger altered the process, neither exit can be attributed to the original application or win16-style. Both jobs were reclaimed with no active processes. No Data control was tested and no proposed product workaround is justified by these observations.

No tracked product or test source changed and both published directories still have matching four-file hashes. The scratch instrumentation is not a supported sandbox or a product dependency. Further work requires a genuine usable VB5 Data sample or a better isolated startup path and real control/behavior evidence. T18 and S64 remain open.
