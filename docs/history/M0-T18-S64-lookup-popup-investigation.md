# M0 T18 S64: Delphi lookup popup investigation

The private real x86 XDB sample described in [the lookup investigation](M0-T18-S64-lookup-investigation.md) opens an application-owned ANSI `TPopupDataList`, style `0x94a00000`, extended style `0x80`, with the application `TMainForm` as its window owner. `GetScrollInfo(SB_VERT)` returned min 0, max 4, page 0, position 2 in one run. A target-thread-only observer reported that the P156 published DLL had not attached the popup; both modules and target were confined to the self-owned job and private desktop. The target exited zero. `LB_GETCOUNT` returned zero, which is not proof of standard LISTBOX protocol.

A diagnostic scratch DLL traced the visible lookup control receiving `WM_LBUTTONDOWN`, nested creation of `TPopupDataList`, installation attempt, then `WM_LBUTTONUP`, all on the same UI thread. At popup install time its owner was the application main window, not the lookup child. This one sample supports a scoped creation witness but does not prove all VCL versions or keyboard/reuse paths.

An unconstrained scratch experiment used the existing frame-scrollbar installer and attached the popup, but both PrintWindow and WindowDC same-window remove comparisons showed zero RGB differences. Inspection found this installer does not enable native nonclient painting. A second scratch experiment used the existing grid nonclient installer: removing it from the same popup changed 2,712 RGB pixels, of which 502 were on the one-pixel frame and 2,210 in the 17-pixel scrollbar area; zero changed in the 102x130 list client. PrintWindow and WindowDC results agreed. Selection after removal closed the popup and the target exited zero. A third scratch experiment limited the installation to `TPopupDataList` created while the same-owner lookup's mouse-down callback was active and owned by that lookup's root. When selection was executed with the experiment still attached, the popup closed, target exited zero, and the `TDBText` bound-key display region matched the published baseline both before and after selection. The scratch scope is not exception-safe and is not a production implementation.

Scrollbar input remains unresolved. Sending synchronous `WM_NCLBUTTONDOWN` followed by `WM_NCLBUTTONUP` produced a 2-second timeout in the native case, while the scratch case returned from down and later failed to close the popup; the same happened on a second run. Inspection of the existing renderer showed that capture completion uses `WM_LBUTTONUP`, so the first probe's release was not representative and cannot establish a product defect. With `WM_LBUTTONUP` both runs released capture and exited zero, but the native popup had closed at release and its scroll range changed while the scratch popup remained open until the later list click. That experiment therefore does not establish equivalent scrolling either. No fault is attributed without a representative asynchronous input sequence and explicit scroll/selection assertions. No production files, system settings or published binaries changed.

Next work must verify genuine popup ownership and lifetime, nested/reentrant creation and exception-safe scope restoration, real scrollbar arrow/thumb sequences and cancellation, capture semantics, dynamic scrollbar visibility and x86/x64 negative models before any production admission. Other DPI, real physical input and applications remain unverified. Scratch remains registered under `build/t18-s64-vb-mask-survey`; a temporary observer is targeted only at the owned target UI thread.
