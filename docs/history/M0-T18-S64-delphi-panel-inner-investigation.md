# M0 T18 S64: Delphi panel inner bevel investigation

The actual DelphiVCL4Python 1.0.7 x86/x64 ordinary TPanel was exercised on a private desktop at 144 DPI with four configurations: outer none plus inner raised, outer none plus inner lowered, raised outer plus lowered inner, and outer none plus inner raised with width two. A scratch native import observer traced the framework's original Polyline calls, restored its slots and closed the owned process. Inner-only raised/lowered are drawn on the outermost coordinates and therefore already satisfy the existing P75 outer-pair contract. Combined borders and two-wide inner borders add a second pair one pixel inward: `(1,118)-(1,1)-(248,1)` and `(248,1)-(248,118)-(0,118)` on the same 250x120 DC, with complementary system highlight/shadow pens.

Paired old P74 versus current P77 packages were exercised on both widths in all four configurations. For inner-only raised, 369 RGB pixels changed; lowered, 368; combined and wide, 369. Every difference was on the outermost ring; second ring and independently counted interior remained identical. This establishes bounded sample support for inner-only and establishes that the second ring is not changed in these combined cases. It does not establish whether every second ring should historically be black.

An experimental scratch DLL replays a second matching pair at inset one only after a successful outer pair; relative to the current package, the real combined sample changed 364 RGB pixels and the wide inner sample 365, all on the second ring and none on the outer ring or deeper interior, on both widths. The prototype is not production-ready: its pending outer witness can survive an invalid intermediate Polyline, it cannot yet prove exclusion of application-drawn geometry inside the same paint, and reentrancy, interrupted pair, clip, reparent, visual historical correctness, image/child ownership and resource lifecycle have not been verified. It has not been committed as product code or released. Self-owned sample processes closed after WM_CLOSE; the abbreviated driver did not independently check their exit codes or job active counts.

A project-authored model then simulated an application drawing the same complementary second-ring polylines from the same module after the ordinary outer pair. In both widths the published package preserved the second line at system shadow `00a0a0a0`, while the scratch prototype changed it to black; the test failed as intended. This is a deliberate native fixture showing an ambiguous call shape, not an observation of a particular real application callback. A first model attempt observed `GetPixel == CLR_INVALID` because its parent was not shown after the process startup show state; it is excluded. The corrected model shows the parent twice, updates it, and measures the actual pixels.

Another fixture inserted an unrelated two-point Polyline between the outer and inner pairs. The first scratch candidate still turned the second ring black on both widths, demonstrating stale witness use. Clearing the scratch outer witness on any invalid Polyline made the interrupted case pass in both widths, but the same-module application-draw case still failed in both. This fixes one experimental state bug and leaves the material identity ambiguity unresolved; no production code or binaries were changed.
