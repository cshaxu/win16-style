# M0 T18 S64: current high-use application regression

At the user's request to focus on practical ROI, this bounded check used the P180 assets package and fresh owned instances on private desktops. The x86 native drivers and observers were already built from the P180 clean snapshot, except the previously retained MD5summer and Actor probes. No disk scan was initiated and HD Tune was not run.

- MadShow: bare and styled checks reached the application, captured images and reported four buttons, thirteen edits and two frames, respectively 0 and 19 attached, zero probe assertion failures. The driver then failed after the capture at a later cleanup stage with error 5; the exact failing call is not identified.
- DoubleKiller: a byte-identical task copy was used. Four styled pages each reported 28 buttons, three edits and two combos, 33 attachments and zero probe failures; the driver subsequently failed with error 5 after recording page and root captures, at an undetermined cleanup step.
- MD5summer: a byte-identical task copy was used. Two styled observations reported three buttons, one edit and one combo, four applicable attachments and zero failures; combo opened/closed preserving selection, and minimize/restore/move reached their probe markers. After WM_CLOSE the main window disappeared, but the process wait returned 258 after five seconds; the full driver failed.
- Actor: the styled two checkbox glyph checks and four BM_CLICK cycles per checkbox reached their assertions and restored initial states. The subsequent process wait timed out and the driver failed.

The sampled style DLL path was assets/ntw16s32.dll. The failed full-driver outcomes are not counted as passes and must not be attributed to product code solely from stale GetLastError. Bare MadShow also failed after capture, and an earlier bare Actor run had the same wait timeout. All owned jobs were closed, and a post-check found no remaining tested image processes. Natural shutdown and independent job-empty assertions did not complete; physical input, full visual correctness and other DPI remain uncovered. Captures and logs are in registered scratch `build/t18-s64-user-app-regression`. No product code or binaries changed in this check.

A follow-up self-owned bare Actor probe queried Windows Wait Chain Traversal after the close timeout. In two short runs the UI thread was blocked waiting on another thread in the same process, and WCT reported no cycle. In the second run the awaited thread was also reported blocked, but its WCT chain contained no further identified object; this does not establish why it waits. This is evidence about bare Actor only, not a diagnosis of the other programs or a style DLL regression. The test job closed on failure. Scratch source and logs: `build/t18-s64-vb-mask-survey/actor-wct-all.c`, `actor-wct-all-run/err.txt`.

A further self-owned bare Actor run combined WCT with `NtQueryInformationThread(ThreadQuerySetWin32StartAddress)` and the target module map. Its UI thread start address belonged to `actor.exe`; WCT showed it waiting on another same-process thread whose start address mapped to `C:\Windows\SysWOW64\msctfmonitor.dll`. WCT reported that thread blocked with no further resolved wait object and no cycle. This narrows the observed wait, but a thread start module is not its current call stack and does not establish the underlying cause or affect other programs. No system services or product settings were changed; the owned job was closed. Scratch: `build/t18-s64-vb-mask-survey/actor-thread-start.c` and `actor-thread-start-run/err.txt`.

Visual review of these stored styled captures shows classic-looking push buttons and edit borders in MadShow, buttons and checkboxes on DoubleKiller's Options page, MD5summer's buttons/combo/scrollbars, and Actor's two checkbox glyphs. This is a bounded visual observation, not a pixel-accurate Win3.x acceptance or proof of all variants. Actor text is visibly garbled in both the earlier bare capture `build/t18-s64-vb-mask-survey/actor-p179-current-retry/bare/actor-bare.bmp` and this styled capture; the screenshots do not establish the cause, font or code page. The common exit failures above remain unresolved.

An independent private-desktop control launched the project's bare `demo.exe` in its own job. The visible demo window was found and WM_CLOSE was posted, but its process wait timed out after five seconds in two runs. A follow-up observed the window still present and WCT reported its UI thread waiting on another thread, without a cycle. No ntw16s launcher or DLL was involved. This establishes that the private-desktop/launch environment can reproduce a similar wait in a self-authored application, but does not prove the root cause, that all application timeouts are identical, or that ordinary interactive desktop behavior is affected. The owned job was closed. Scratch: `demo-close-control.c` and `demo-close-wct.c`.

A further bounded control invoked the same bare demo probe's worker directly on the worker's current session desktop, without creating its private desktop. It found the owned demo window and successfully posted WM_CLOSE, but WaitForSingleObject returned 258 after five seconds and exit remained STILL_ACTIVE (259); the job then reclaimed the owned process. The probe did not identify whether this desktop was the visible input desktop, and no style DLL was loaded. Therefore the earlier timeout cannot be attributed solely to use of a newly created private desktop; the underlying wait and the real applications' behavior remain unproven.

A readiness control on the current worker desktop sent WM_NULL with SendMessageTimeout (2-second limit) to the owned bare demo; it returned success with error 0, then the probe waited one additional second before posting WM_CLOSE. Process wait still timed out at five seconds (258, STILL_ACTIVE 259); the owned job reclaimed it. This rules out a merely unresponsive message queue at that particular readiness check, but does not prove full startup completion or identify the later wait. Scratch: demo-close-ready.c/exe.

A paired bare demo test checked synchronous versus posted close after the same successful WM_NULL readiness check and one-second delay. SendMessageTimeout(WM_CLOSE, SMTO_ABORTIFHUNG|SMTO_BLOCK, 2000 ms) returned success, the window disappeared and process exited 0 in three current-session runs and one private-desktop run. The original PostMessage variant immediately afterwards timed out in both environments (258). All instances were owned and jobs closed. This identifies an actionable difference for this demo probe, not a universal remedy: the existing Actor observer already uses synchronous SendMessage and still timed out, and the reason for the posted-message behavior is not established. Scratch: demo-close-sync.c/exe.

Follow-up x86 scratch drivers added stage markers and a 3-second synchronous-close candidate without changing repository test sources. On this run the bare and styled MadShow and styled DoubleKiller stopped at first observation, before close. A split check showed that SendMessageTimeout(WM_APP+0x371) succeeded (error 0) but the observer-ready event timed out (258) for bare MadShow and styled DoubleKiller; successful message delivery does not establish the injected observer callback ran. All runs returned failure and owned jobs were closed. The old error=0/5 alone was not a useful failure location. This run did not verify the close candidate, so it is not an application pass. The first scratch compile failed because _WIN32_WINNT was unspecified; setting 0x0A00 fixed compilation. Scratch sources: vb6-sync-driver.c and doublekiller-sync-driver.c.

After the ready-event timeout, the scratch driver enumerated modules in each owned target while the hook was still installed. In bare MadShow and styled DoubleKiller it found zero module names containing probe; SendMessageTimeout had returned success and SetWindowsHookEx had returned a handle, but no observer module was seen in either snapshot. This supports a failure before observable observer execution, not a determined OS loader error: the filter/snapshot do not capture transient loads or their reasons. Enumeration itself left ERROR_NO_MORE_FILES (18), so that later last-error value is not the hook failure. Both owned jobs were closed.

A test-only x86 diagnostic on an owned bare MadShow instance directly loaded the same observer DLL after the missing-hook observation: a bounded remote LoadLibraryW thread returned a nonzero module handle. Sending the observation message again with the original hook still installed succeeded, but the ready event again timed out (258). This shows the DLL can load by this explicit path in that one process and that merely loading it does not restore this hook callback; it does not establish why Windows did not invoke the hook, or prove behavior in other targets. The job reclaimed the owned target and its loaded test DLL. Diagnostic scratch: vb6-loadcheck-driver.c.

A test-only alternative loaded an instrumented observer into the owned MadShow process and installed its WH_CALLWNDPROC hook from a short-lived target-process thread against the already identified UI thread. In bare and styled runs, the original cross-process hook still produced ready timeout 258, but the local hook delivered the callback and signaled the event (0); its installer thread unhooked and exited 0. The observer reported bare buttons=4 edits=13 frames=2 attached=0 failures=0; styled reported 4/13/2 attached=19 failures=0 and module enumeration showed assets/ntw16s32.dll. The scratch diagnostic deliberately retained the original failure return and terminated the jobs; these are control-observation passes, not complete application or natural-shutdown passes. Original cross-process failure remains unexplained. Initial x86 probe lacked undecorated stdcall export (127); rebuilding with the stdcall alias resolved export lookup; one PowerShell linker-option syntax attempt failed before compilation. Scratch: vb6-local-probe.c and vb6-localhook-driver.c.

A fuller scratch MadShow driver used unique named start/stop events and an in-process temporary observer hook, waited for its explicit removal, captured the form, then attempted a bounded synchronous WM_CLOSE. In both bare and styled instances the callback/capture completed and SendMessageTimeout returned success with error 0; IsWindow reported the main form gone. Each target process nevertheless remained active after a 3-second wait (258, exit 259), so both full runs failed; jobs reclaimed them. This separates observation success and form destruction from process shutdown, and the bare failure prevents attribution solely to ntw16s. It does not establish why processes stayed alive or prove normal desktop behavior. First scratch build had a duplicate local variable name and was corrected before running. Scratch: vb6-local-full-driver.c and vb6-local-probe.c.

The same owned-process, bounded local-observer approach was adapted in scratch for DoubleKiller. Four page observations each reported 28 buttons, 3 edits and 2 combos, 33 attached and zero probe failures; the first page's existing button-removal comparison reported 1843 changed pixels and the expected pre-removal center. The actual assets x86 DLL was enumerated, the temporary hook installer exited, and captures were written. Synchronous WM_CLOSE returned success but the sampled root window was still present and target wait timed out after 3 seconds (258, exit 259); the full run failed and the job reclaimed the instance. The data do not establish why the root persisted or whether a close confirmation appeared; no scan was initiated. A first scratch generator had a PowerShell scalar-indexing error and its output was discarded, then a corrected generator built the executed driver. Scratch: dk-local-probe.c and dk-local-full-driver.c.

A follow-up sampled the same owned styled DoubleKiller root at two times: it existed immediately after synchronous WM_CLOSE returned, but after the 3-second process timeout IsWindow returned false. EnumThreadWindows on the original UI thread succeeded without invoking the callback; no confirmation window on that thread was observed at that time. This corrects the earlier implication that the root necessarily remained present throughout the wait. It does not rule out a transient confirmation, a window on another thread or identify the process shutdown wait. The full test still failed and its job reclaimed the process. An initial diagnostic used wide stderr after narrow output, suppressing callback output; it was changed to narrow output before the recorded final run.

A bounded bare DoubleKiller control using the same local observer and close procedure also returned successfully from synchronous WM_CLOSE, showed the root initially present but absent after the three-second process timeout, and had no windows enumerated on the original UI thread at that point. The process remained active (258/259); the owned job reclaimed it. This prevents treating the corresponding styled observation as evidence that the style DLL alone caused the exit wait; it does not establish the underlying cause.

The existing P180 clean-snapshot candidate package (whose four hashes match the published assets) was rechecked with Test-Package's eight mandatory cases plus VB5/VB6 checklist and graphical check/option native models in both widths. Result: passed-focused, 16 cases, zero skips, physical input not tested. These are self-authored native models and do not replace the incomplete real-application shutdown checks above or constitute a new clean build or release. Receipt: build/t18-package/s64-p180-vb-common-recheck/result.json.
