# M0 T18 S64: Delphi simple status investigation

A task-local DelphiVCL4Python 1.0.7 `TStatusBar` with `SimplePanel=True` and `SimpleText="Ready - sample status"` was run in self-owned isolated x86 and x64 processes at 144 DPI, bare and with the P116 actual assets package. Its observed class and real class were both TStatusBar; its class owner was the matching DelphiVCL runtime. The status HWND was attached under P116, but WM_GETFONT reported Segoe UI -18, as in the bare sample. Both targets and launchers exited 0 and owned jobs emptied. Application state and other processes were not touched.

The native status capture measured 598x60 bare and 608x60 styled because the styled top-level client is wider. Comparing the entire common 598x60 client pixels showed exactly 57 differences in each width, bounded at x=585..597, y=47..57 near the shifted right edge; there were no differences at x<500, including the left text. The screenshots and logs are retained under `build/t18-s64-vb-status-simple`; this is evidence for the particular sample, not for every simple status bar. The standard public messages reported SB_ISSIMPLE=1, SB_GETPARTS=1, SB_GETTEXTLENGTHW index 0=21, index 255=0 and SB_GETRECT index 255 returned 0. This explains why simply substituting a supposed simple-pane rectangle for the existing multi-pane path is unjustified. Existing code explicitly avoids collecting panes in simple mode; its native paint/module and epoch checks remain necessary.

A scratch observer attempted to observe DrawThemeText through the system COMCTL32 import, but did not bind a matching import in either the bare or styled x86 process; imports were restored. This failed probe does not establish which API actually renders the text or whether that API may be safely intercepted. A follow-up x86 bare probe successfully bound COMCTL32 imports of DrawTextW and ExtTextOutW, but observed neither during forced redraw and PrintWindow capture; both imports were restored. This rules out only those direct IAT calls in this observation, not calls through other modules or other text APIs. Additional COMCTL32 import probes for TextOutW and DrawTextExW likewise attached and saw no calls during the same bounded redraw/capture; all probes were restored and the owned process exited normally. Other text calls, icon and custom colors, runtime state changes, IME, localization, DPI, keyboard/physical input and resource lifetime remain unverified. No product source or binary was changed or published. Next identify the actual native paint call and caller/DC/clip ownership without relying on class name alone, then test safe font and cleanup behavior against native and owner-draw fallbacks before proposing a product change. M0/T18/S64 remain open.

A follow-up UxTheme IAT observer in the self-owned x86/x64 sample caught DrawTextExW at both measurement (flags 0x420) and drawing (0x820), in bare and P116 runs. Caller was system UxTheme, WindowFromDC was the actual status HWND, selected font Segoe UI. Actual drawing rectangles were (2,18,573,59) bare and (2,18,583,59) styled; imports were restored and all jobs emptied. This is bounded evidence for this version and paint path, not proof for memory DCs or arbitrary nested theme calls. Next test an exact status-paint-scoped font lease with same-thread identity, native status witness, UI role, caller, DC, text and epoch guards; preserve original WM_GETFONT and fallback for unsupported text.

A scratch font-replacement prototype proved the real x86/x64 simple status sample rendered System-shaped ASCII text while WM_GETFONT remained the application Segoe UI. Its initial text query inside DrawTextExW could reenter application code and invalidate the native text pointer, so that design was discarded. The current draft snapshots up to 512 characters before native paint and sends no status messages inside the text hook. In self-owned v6 x86/x64 models, ASCII pixels changed, non-ASCII and 513-character strings remained native, and both SB_SETTEXT and WM_SETTEXT reentrant mutations fell back to their respective native frames; the version lacking WM_SETTEXT epoch invalidation failed the latter on both widths. An earlier comparison against only the post-mutation frame was flaky and is not counted as proof.

A short x86 model measured 20 WM_PRINTCLIENT calls with GetTickCount64 (millisecond-valued, system timer granularity applies): the published P116 package rounded to 0 ms, while the current draft took 562 ms (an earlier prototype measurement was 500 ms). GDI objects were 8 before and 8 after the draft run, which does not prove leak freedom. The original package naturally failed the new styled-pixels assertion after the timing was recorded. The draft recreates its bitmap font lease on each measurement and draw. This overhead is unacceptable for release: investigate a GUI-thread-owned cache keyed to the realized font, safe invalidation for WM_SETFONT, theme/DPI and destruction, and nested/reentrant borrowed-font lifetimes before rebuilding and testing. The draft source and tests are uncommitted, candidate binaries are scratch-only, and neither deployment location has received them.
