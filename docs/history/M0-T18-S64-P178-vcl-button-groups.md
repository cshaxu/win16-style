# M0 T18 S64 P178: VCL button container frame models

TButtonGroup and TCategoryButtons are exact-name candidates for the existing grid nonclient frame and scrollbar renderer only when the application-owned Unicode class, same-owner parent and other grid eligibility checks hold. Application client drawing, icons, button content and interaction remain untouched. These restrictions are not evidence that actual VCL controls use this path.

The previous P177 package failed the positive attachment assertion in the self-authored x86/x64 models for both names. The P178 models pass on both widths: the target edge changes by 2736 pixels and the client by zero; scrollbar state, negative identity cases, reparenting and cleanup pass in the fixture. These are models, not genuine Delphi controls; actual button appearance, real layouts, other DPI and integration remain unverified. The available GoVCL test library does not export factories for either class.

The first clean package run timed out in x86 CMake compiler detection under the sandbox and was not released. The retry completed clean x86/x64 builds and ABI checks. The actual same-snapshot package passed 20 focused cases in 12.75 seconds, no skips; this is not the full integration matrix and physical input was not tested. Four files were published to both assets root and O:\winnt\system32 with matching hashes. Both installed copies passed both model cases on x86 and x64. Original graphics, title and font rendering were not changed.

M0, T18 and S64 remain open.

The locally available DelphiVCL4Python 1.0.7 Win32 and Win64 bindings were inspected with Python `hasattr`: neither exports `ButtonGroup`, `CategoryButtons`, `Outline`, `TabbedNotebook`, `DriveComboBox`, `DirectoryListBox` or `FileListBox`. This only limits these bindings as test factories; it is not evidence that genuine controls cannot be tested or that model-only support works in real applications.

Embarcadero's [VCLButtons example](https://docwiki.embarcadero.com/CodeExamples/Sydney/en/VCLButtons(Delphi)) explicitly assigns `BorderStyle := bsNone` to TButtonGroup. This documented configuration cannot satisfy P178's CLIENTEDGE gate and its button items are outside P178's nonclient renderer. This is source-level evidence of a coverage gap, not a run of that example; actual button drawing and interactions need a genuine Delphi sample.

## Real TCategoryButtons sample candidate

The author's [WhiteStarUML portable release](https://sourceforge.net/projects/whitestaruml/files/WhiteStarUML-NoInstall-5.5.8.zip/download) was obtained using curl after the earlier downloader returned HTML. The 30,723,693-byte ZIP has SHA256 c8a4fd77420e2c586e33e6c47e5c428c61ac3df6009a0e0f5b5fdcc809d3bdf6; its 7,289,096-byte executable has SHA256 f4ae9a7b968f2fdf15926dd4ba64af4c4ba7e1c80ad986da5db1e5d59f961235. Static inspection found a TPF0 form resource with TCategoryButtons named PaletteNavBar and category data. This establishes a promising real sample, not runtime creation, behavior, compatibility or a fix. The archive was extracted only into registered task scratch; no installer, registration or application execution occurred. Startup side effects and safe environment isolation remain to be investigated before launch.

The independently retrieved public mirror source `staruml/src/Main.pas` calls `AddInManager.LoadAddIns` on first main-form appearance and calls `OptionDepository.SaveOptionValues`, `MainForm.SaveToRegistry`, and `ContributorManager.SaveToRegistry` on normal closure. `MainFrm.pas` creates registry keys and writes window state. This source has not been proved identical to the 5.5.8 executable; it is a reason to isolate registry and add-in side effects before executing the sample, not proof of that binary's exact runtime behavior. Sample remains unexecuted.

The author's separately published 5.5.8 source ZIP (18,796,813 bytes, SHA256 b330c0d2dd2134fb7a609e83ffc4773626540f183c1e23be1a542ec3b17dfaf1) confirms that version's `NavBarFrameVclImpl.pas` declares `PaletteNavBar: TCategoryButtons`, with real category item and click handlers. Its `Main.pas` calls `AddInManager.LoadAddIns` at startup and saves options/registry on close; `MainFrm.pas` opens registry keys for writing. Matching release version strengthens the sample selection but does not verify the executable was built byte-for-byte from that source. The program remains unexecuted pending isolation of startup and registry side effects.

A separate self-owned x86/x64 native experiment used `RegOverridePredefKey` only within its child process, mapped HKCU to a uniquely created volatile key, wrote a marker there, and verified from its parent that the original HKCU path was absent. Both child runs exited 0, the mapped value was correct, and the unique backing keys were removed. The first x86 attempt returned child exit 12 when creating a nonvolatile child under the volatile key; it cleaned up and was corrected to a volatile child. This narrow test does not prove that an external sample can be redirected before its initialization, that all registry access or subprocesses are isolated, or that add-ins are safe. WhiteStarUML remains unexecuted. Scratch source: `build/t18-s64-vb-mask-survey/registry-isolation-probe.c`.

A test-only x86 debugger probe created its own process, set a breakpoint on its EXE entry, verified an application-main event was not signaled, restored the instruction, suspended the target thread, detached the debugger, resumed, and observed the event and zero exit. Output: `before=258 detach=1 resume=1 after=0 done=0 exit=0`. The probe only establishes ordering for this self-authored EXE; DLL loader initializers run earlier, and registry redirection, WhiteStarUML, child processes and add-ins were not tested. Source is task scratch `build/t18-s64-vb-mask-survey/entry-order-probe.c`.

A combined self-owned x86 prototype paused at EXE entry, restored the breakpoint, detached with the original thread suspended, loaded a scratch-only DLL whose DllMain is inert, and invoked its registry override export from a remote thread. After resuming, the child's first application write reached the unique temporary HKCU backing key; the unredirected marker path was absent, child exited 0, and the temporary key was deleted. Output: `REMOTE_ISOLATION status=0`, `ENTRY_REG mapped=0 value=1234 outside=2`, `ENTRY_CLEANUP tree=0 key=0`. Initial PowerShell compiler argument parsing and a local C variable collision failed before execution and were corrected. This is one same-bitness x86 process only; loader-time DLL initialization precedes the breakpoint, remote module-address assumption and failure cleanup need hardening, and this does not isolate child processes or add-ins. It is not authorization or evidence to execute the third-party sample. Scratch-only `entry-registry-probe.c` and `registry-entry-dll.c`; no product changes.

Correction after inspecting the exact 5.5.8 `AddInMgr.pas`: its old registry enumeration implementation is commented out. The active `SetupAddIns` recursively scans `ExtractFileDir(Application.ExeName) + EXT_DIR` for description files and processes them. Therefore earlier wording that plugin loading reads registry is not established by this source. Separately, `POptionManager.LoadOptions` calls `OpenKey(RootPath, True)`, which can create a key. The EXE statically imports bundled Delphi `rtl190.bpl` and `vcl190.bpl`, which initialize before its entry breakpoint; their imports contain registry and other APIs, but an import alone does not prove a call or side effect. Actual execution remains untested.

A self-owned x86 native probe duplicated its token, lowered the child to low integrity, and attempted writing a uniquely created medium-integrity task file and temporary HKCU key. Both operations returned ACCESS_DENIED as asserted by the child; parent confirmed the registry value absent, child exited 0, and both test objects were removed (`LOW_PROBE error=0 wait=0 exit=0 value=2 cleanup_registry=0 cleanup_file=1`). This is a limited mandatory-integrity-control test, not a sandbox: it does not block reads, network, writes to low-integrity objects, COM brokers or descendants, and was not run against WhiteStarUML. Source is task scratch `low-token-probe.c`.

A first low-integrity, private-desktop native observation used a separate task-local copy of WhiteStarUML 5.5.8 with eight `.aid` plugin descriptions renamed only in that copy. The sample executable hash remained f4ae9a7b968f2fdf15926dd4ba64af4c4ba7e1c80ad986da5db1e5d59f961235. Its owned process exited 0xc0000142 before a visible window, so no category control or drawing was observed. The same observer launched this project's own demo under the identical low-integrity/private-desktop combination and it also exited 0xc0000142. This establishes an environment/launcher limitation to investigate, not the exact cause or a product defect. Both jobs were terminated/closed by the observer; no WhiteStarUML process remained. This is not a normal application run or a style test; network/COM isolation and complete side-effect coverage remain unproven. Scratch-only observer and logs are `whitestar-low-observer.c`, `whitestar-low-observer.log`, and `demo-low-observer.log`.

## Visible real VCL control observation

The initial low-integrity/private-desktop launch failed with 0xc0000142; the same failure occurred with the project demo. A scratch-only observer then created its own private desktop with a low integrity label: the demo showed normally (the observer intentionally timed out because the demo has no category control). A fresh, low-integrity, job-owned WhiteStarUML copy, with eight task-copy `.aid` files disabled, showed its TMainForm and one visible TCategoryButtons. The exact class owner resolved to the copy's `vcl190.bpl` (SHA256 1bfa53384d47565f323706a5e0eb147de76fac4a78d02a9db0668a8501a02ced), not the main EXE. The sampled HWND style was 0x54010000, exstyle 0x00000200, window 157x250, client 153x246. A second owned sample launched by the published run16s had the same visible control and confirmed `assets/ntw16s32.dll` in the actual target module list (SHA256 e488bd2d65f1bccd7fb9ff268f75c2b94c2c448794776b81b9c8a5896d612459). Captured bare and styled control BMP files were byte-identical, SHA256 5a36cd43f9c37f74187bc08dde47e316395744c9f4ffbc8273b04971916c382e; PrintWindow reported success. The final x64 observer needed EnumProcessModulesEx(LIST_MODULES_ALL) to reliably enumerate the x86 target, whereas an earlier EnumProcessModules call failed to report the DLL.

The published P178 category identity predicate requires owner==GetModuleHandleW(NULL), so this observed VCL-package-owned class cannot satisfy it. This is a real gap in that predicate, not evidence that merely relaxing it will safely style the control or its buttons. The sample did not exercise plugin behavior, user input, normal shutdown, other DPI or versions; the self-owned jobs were terminated and closed after observation, not asserted as graceful exit. Low integrity is not a complete network/read/COM sandbox. Actual callback, button content and interaction tracing remain necessary. Scratch contains `whitestar-low-modules.c`, `whitestar-category-bare.bmp`, `whitestar-category-styled.bmp`, and associated logs.

Correction and protocol follow-up: the initial same-byte BMPs depict an empty pale-blue client area with borders, not category headers or buttons, so they do not establish whether actual category-item drawing would differ. At 96 DPI a new owned styled instance reported Unicode/real class TCategoryButtons, same-owner parent `TPaletteNavBarFrameVclImpl` in vcl190.bpl, and GetScrollInfo(SB_VERT) success (range 0..10, page 10, position 0). The source gate still excludes the BPL-owned control. Native enumeration found the startup New Project dialog and a single posted BM_CLICK on its enabled default OK dismissed it; the category grew to 157x376 but still showed a blank client. The task-copy add-in descriptors were disabled, which may affect content; causation has not been established. Self-owned job terminated after capture, not graceful shutdown. No input or drawing claim about actual category items is made. The initial diagnostic compile failed because its target Windows version macro omitted the GetDpiForWindow declaration; that test-only issue was corrected before execution. Scratch: `whitestar-low-protocol.c`, `whitestar-project-probe.c`, and logs.

## Real category items from bundled model

Launching separate low-integrity owned instances with the distribution's `Samples/Sample unicode names.uml` argument caused the main title to identify that model and the real TCategoryButtons to display the Annotation category and buttons. In the styled target EnumProcessModulesEx confirmed the published `assets/ntw16s32.dll`; the control and parent belong to the same `vcl190.bpl`. At 96 DPI both reported native vertical scroll range 0..21, page 15, position 0. Captures were taken after the model appeared: the bare control was 157x380, styled 157x376, so whole-image equality is not meaningful. In their aligned common area the top 248 rows had zero RGB differences; 208 pixels differed elsewhere, without evidence distinguishing layout/timing from styling. Thus these observations expose the real category-item appearance but do not establish a comprehensive pixel equivalence or interaction behavior. Control class ownership still fails P178's main-EXE predicate. Scratch captures: `whitestar-model-bare.bmp` and `whitestar-model-styled.bmp`; observer `whitestar-sample-model.c`. Eight add-in descriptions stayed disabled in the task copy, and instances were job-terminated rather than closed gracefully. No product change.
