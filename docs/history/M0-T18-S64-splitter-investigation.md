# M0 T18 S64: default VCL splitter observation

The frozen VCL inventory lists TSplitter as native or unverified. A self-owned DelphiVCL4Python 1.0.7 fixture created one `TSplitter` using its default `alLeft` alignment. The application-level binding did not expose a Handle for it. At reported 96 DPI, styled x86 and x64 runs attached the released matching DLL to the form; the native x86 control run had no style DLL and the form was not attached. During a synchronous form redraw in all three runs, the observer saw the splitter area filled on the same parent-window DC using the very same brush as the parent background (solid COLORREF `00f0f0f0`). The splitter's fill rectangle was 20 pixels wide, clipped to its area; the original and styled form client heights differ, so the rectangle heights are not a pixel-for-pixel comparison. No separate splitter border was observed in these calls. Observer IAT changes were restored, captures succeeded and the isolated owned processes exited.

This supports only the conclusion that the observed default sample inherits the parent background in these runs. It does not establish classic appearance for other splitter styles, colors, sizes, Delphi versions or DPI, and no splitter dragging, neighboring control resize, callback, mouse capture or lifecycle test was performed. It is not grounds to reclassify the entire TSplitter family as implemented or to intercept arbitrary parent FillRect calls. Further testing should construct a realistic pair of resizable sibling panels, exercise movement and cancellation, and inspect nondefault ordinary border styles. No product code or binaries changed.

## Drag and beveled sample follow-up

A second self-owned fixture placed a 150-pixel-wide left-aligned TPanel next to a 10-pixel-wide TSplitter. At reported 96 DPI, x86 and x64 bare and released-style runs each received a synchronous message-level drag: left button down, move 35 pixels, then left button up on the parent window. In all four runs, the panel and splitter moved from x=150 to x=185; capture was present after down and absent after up. These are synthetic Windows messages, not a physical-input test. The owned targets exited and the driver reported capture/close success.

A further message-level attempt sent `WM_CANCELMODE` during a second drag followed by button up. Both bare and styled processes ended with the width at 210, so this sequence did not establish cancellation; an earlier attempted Escape sequence also changed the size in the bare process. Neither result proves a regression or a valid cancellation test. With `Beveled=True`, the styled x86 sample used two FrameRect calls on the shared parent-window DC after the background fill. Their coordinates and clipping alone cannot establish the owner of those calls. No Beveled visual comparison, other orientation, real DPI variation, interaction callback, or physical input is verified; the family remains unverified and no product interception was added.
