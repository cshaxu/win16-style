# M0 T18 S64: Delphi MDI child frame investigation

A self-owned DelphiVCL4Python 1.0.7 sample creates `TForm` with `FormStyle=fsMDIForm` and an `fsMDIChild` TForm. The released P162 package launches it in a private desktop/job for each width; both processes load the matching assets DLL and exit with code zero. The parent caption is classic but the child caption remains visibly modern in both `build/t18-s64-vb-mask-survey/mdi-owner-{32,64}.bmp` captures. This is a real observed missing style, not a claim about all Delphi MDI applications.

Both child classes are `TForm`, style 0x56cf0000, extended style 0x000001c0, directly parented to USER `MDIClient`. Toolhelp module enumeration resolves each child class owner to that target's DelphiVCL.pyd, not the Python executable. The existing attachment code allows the external-owner MDI frame exception only for witnessed VB5/VB6 classes; other external child frames fall through to ERROR_NOT_SUPPORTED unless another candidate applies. Those facts are consistent with the observed failure, but no target-side attachment rejection log or negative controlled prototype has yet verified the precise decision point. Do not claim the cause proved solely from class and code.

A target-thread diagnostic was attempted: first x86 build exported the stdcall name with @12 and the driver failed to find it (127); after fixing that lookup the hook did not report before the bounded wait and the owned job was reclaimed. Neither run is attachment evidence. The screen capture probe, which does not inject this observer, succeeded separately on both widths. The driver never manipulated unrelated processes. Scratch sources and captures remain in the registered `build/t18-s64-vb-mask-survey` directory.

Next: establish a safe Delphi-specific MDI identity with direct target-side rejection/attachment proof and class-owner/parent-owner checks, then verify bounded child caption states and MDI lifecycle, malicious/wrong-owner and reparent negative cases, and real dual-width samples before proposing any product change. Existing shared external/OCX protection must not be generally disabled. Maximized child menu merging, other VCL versions/DPI and physical input remain untested. M0/T18/S64 remain open.

## Controlled prototype

On a copied P162 source snapshot, a scratch-only change added one exception to the external-child guard: exact `TForm` with caption and WS_EX_MDICHILD, USER `MDIClient` parent, and `TForm` MDI host with the same class owner as the child. Matching x86 and x64 scratch DLLs were built with GCC/Ninja/ccache and placed alongside the released launcher in an isolated research package. Real self-owned samples loaded the respective scratch DLLs, displayed the child with a classic title, and exited zero; `mdi-proto-32.bmp` and `mdi-proto-64.bmp` preserve the observations. P162 same-sample captures kept the modern child title. Since only this guard exception was changed, the controlled comparison supports that guard as the first difference responsible for this sample; it is still not a direct rejection trace.

The first sandboxed CMake compiler check stalled in its ccache process and was stopped after a bounded wait. The first native build then failed because the research copy omitted LICENSE, required by the version resource; copying the existing LICENSE into that scratch copy allowed both builds to succeed. Neither attempt is a product package. The prototype has not established a sufficiently complete identity/lifecycle contract: it does not verify the MDIClient's USER32 owner, thread/process identity, attachment of the MDI host, reparenting or style transitions. Nor has it tested maximize/restore, negative foreign-owner cases or pixel/layout regressions. It must not be published or copied as a final implementation.

## Identity and lifecycle prototype

A self-owned external-module C fixture registers TForm and creates a USER MDIClient and child. With the initial prototype, its dual-width positive cases attached and maximize/restore worked, but moving the child to a different parent left it attached on both widths; this failed the explicit `!attached(w)` assertion. This is a real prototype defect, not a pass.

The revised scratch implementation additionally checks child/client/host thread and process, USER32 ownership of MDIClient, exact TForm classes, the child's and host's matching owner, an attached host and the MDI child frame bits; it stores the original parent and host and removes its attachment when those identities no longer hold. Dual-width models then recorded `initial=1 root=1`, wrong host `bad_host=0`, `after_reparent=0`, `after_host_remove=0` and `MDI_FIX_OK`; both exited zero on private desktops. Genuine dual-width VCL samples also loaded the revised scratch DLLs, maximized/restored through MDI messages and exited zero with classic child titles (`mdi-safe-{32,64}.bmp`). These are bounded synthetic-message tests, not physical input or comprehensive lifecycle validation. An initial revised build failed at an undeclared alias used before its definition and was corrected before the successful builds.

The scratch model and fixture are not yet checked-in tests. Before product integration they need stronger negative coverage for wrong client owner, wrong class/module, child style changes, reentrancy and handle lifetime, plus old-package rejection and fault-negative evidence, actual-package and existing VB MDI regressions. In particular, independently review whether child and host attachment lifetimes can be confused by handle reuse. Scratch only; no product or released binaries changed.
