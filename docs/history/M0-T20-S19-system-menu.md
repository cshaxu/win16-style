The released demo showed the native modern system popup. The original owner-draw preparation can fail for the actual demo system menu; restoring its state leaves native USER painting. The private popup scope now paints supported native system-menu rows using the existing System menu renderer after USER painting, without replacing the menu handle or command dispatch. Application owner-drawn and unsupported bitmap items cause this overlay to be skipped.

Evidence: on a private desktop a DPI-aware native observer captured the actual window DC (not just WM_PRINT). The real demo negative fixture detects the old package. The native self-owned menu test verifies popup state restoration and application owner-draw callbacks; it does not claim no temporary owner-draw conversion, since the pre-existing renderer temporarily uses it.

A posted WM_NCLBUTTONDOWN did not open the native menu on the inactive private desktop; this is a probe limitation and mouse activation remains unverified. Dynamic no-flicker on real mouse movement remains unverified. Do not close S19 on these results alone.

## Initial menu paint follow-up

The owner reported blank first-open notepad menus until hover. A self-owned 32-bit O:/windows/notepad.exe on an isolated desktop received a scoped thread-only tracing hook. Both S18 and initial S19 showed WM_INITMENUPOPUP and nine WM_MEASUREITEM notifications, then WM_ENTERIDLE with no WM_DRAWITEM until a later PrintWindow call; thus an early PrintWindow screenshot is an unreliable first-paint witness. In the candidate, a bounded synchronous client invalidation only when a popup receives SWP_SHOWWINDOW caused nine WM_DRAWITEM notifications before WM_ENTERIDLE and before any capture or mouse-move message. This isolated finding does not independently prove the same missing-message mechanism on the user desktop.

A new self-owned regular menu fixture checks actual WM_DRAWITEM before idle without requesting a screenshot. With the previous released package it failed on both x86 and x64 (draws=0, idle=1); candidate passed both (draws=3, idle=1). A private-desktop GetWindowDC/BitBlt sample was found capable of containing compositor pixels from a different desktop, so the earlier screenshot and blue-pixel test do not alone prove actual visible drawing. Do not rely on them as real screen evidence; the menu system appearance still needs a trustworthy live display check. A scoped in-process thread hook was removed and all test-created processes cleaned up.

P2 delivery: s19-firstpaint clean-built both widths using GCC 16.1.0, Ninja and ccache; ABI, original resources and source identity passed. s19-firstpaint-check passed 16 focused package cases with no skips, including x86/x64 first paint, system menu, application owner-draw, cancellation, demo, startup and propagation. s19-firstpaint-publish deployed the identical four tested files to assets and O:/winnt. The published 32-bit DLL in a self-owned notepad received nine WM_DRAWITEM notifications before WM_ENTERIDLE, before screenshot or hover; the scoped trace hook was removed. Baseline and candidate each use native messages on an inactive private desktop; this does not verify actual composited first frame or physical mouse movement. S19 remains open for those previously recorded system-menu and flicker boundaries.
