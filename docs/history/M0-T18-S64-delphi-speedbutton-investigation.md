# M0 T18 S64: Delphi SpeedButton theme investigation

The current published package leaves a self-owned DelphiVCL4Python 1.0.7 ordinary `TSpeedButton` visibly modern. In both x86/x64 samples at 144 DPI, the framework's normal, down and disabled button background used the observed `BUTTON` theme part 1 states 1, 3 and 4, respectively; the flat sample used `TOOLBAR` theme part 1. Theme handles were traced at `OpenThemeData`, not guessed from the part number. A separate draw-theme call for `TEXTGLOW` shared part 1 but state 0. The x86 OpenThemeData caller was the actual DelphiVCL runtime module. A diagnostic logging change caused GCC to split the draw hook, so its apparent immediate caller was the diagnostic DLL itself; a short stack showed the runtime above it. That logging caller address must not be used as production identity.

A scratch-only prototype tracked one thread-local BUTTON handle and reused the existing BitBtn face painter after the original theme call, only for the sampled panel DC, full rectangular clip and button-local coordinates. Against separate same-configuration captures, the normal, down and disabled buttons changed 5,793 RGB pixels each on x86 and x64, all inside the 130x45 button; flat changed zero. A real grouped button received one synthetic mouse click, executed its Python OnClick once and became down in both widths with and without the prototype. No physical input was tested. The first attempt sent messages before the form event loop and did not reach the observer; an initial external coordinate also missed the button. Neither attempt is counted.

A button directly parented by the form at x=300 generated the same BUTTON part/state on a `TForm` DC with window origin (-300,-30). A separate overlapping form-parented button was drawn with `WindowFromDC` reporting the panel and a nonzero viewport: the DC window alone does not prove actual graphical-control parentage. The initial prototype deliberately only accepts its observed zero-viewport panel case; it does not support the form case. This is a significant scope and ownership constraint, not evidence of general support.

A standalone native theme-lifetime probe opened BUTTON twice and got the same handle, then opened TOOLBAR with a distinct handle; the still-live second BUTTON and a later BUTTON open reused the shared value. Four cycles demonstrated the same behavior. Therefore a single thread-local handle and clearing it on the first close cannot safely represent real lifetime. A production candidate needs bounded thread-safe class/refcount tracking with correct failed/late closes and handle reuse, input/return/error preservation, scope/owner/clip proofs, and explicit fallback for unobserved OpenThemeDataEx/ForDpi and unsupported state. Matching the BUTTON theme, rectangle or caller module alone does not prove a windowless TSpeedButton when VCL and application code share an executable. No product source or binaries were changed. Samples, native probes, diagnostics and images remain under registered ignored `build/t18-s64-vb-speedbutton`; diagnostic mixed DLLs are not release packages. M0/T18/S64 stay open.

Additional x86/x64 native calls showed `OpenThemeData` and `OpenThemeDataEx` share the same live BUTTON handle, whereas `OpenThemeDataForDpi(...,96)` returned a different handle. In this MinGW x86 toolchain the static import library did not provide `OpenThemeDataForDpi`; dynamic GetProcAddress succeeded. The diagnostic hook on OpenThemeData did not observe the Ex or ForDpi calls. Therefore a tracker of only one API cannot safely count all opens.

A self-authored scratch C registry model on both widths checked duplicate BUTTON opens and one-at-a-time closes using real theme calls, rejection of a synthetic same-handle different-class alias, and a simulated overlapping open/close failing closed. It is deliberately conservative and not production code; its global fallback on concurrent operations still needs a usability and correctness review, and Ex/ForDpi, real threads, failures, overflow and lifetime races need independent tests.

With a self-authored 16x16 application glyph, both-width base/prototype captures retained the same 128 solid `(R=220,G=40,B=25)` glyph pixels at identical positions; other antialiased pixels were affected by the changed background, so this is not a claim that every glyph or transparent edge is bit-identical. Native synthetic input on disabled samples produced no OnClick callback in both base and prototype for both widths. This does not prove keyboard, focus, other glyph states or physical input.

The revised scratch registry uses bounded records and permanently rejects an individual handle whose open overlaps a close; table exhaustion disables recognition rather than guessing. Fresh C17 `-Wall -Wextra -Werror` builds passed on both widths: actual shared handle close sequencing, simulated class alias, sticky overlap rejection, a real second thread synchronized across an open/close overlap, cross-handle ticket rejection, and 128-record capacity fallback. The initial executables were stale; the revised source initially failed compilation for misleading indentation and was fixed before these fresh runs. The overlap test exercises the registry, not concurrent calls into UxTheme itself. This does not establish production safety: nested opens, native failures and exception cleanup, or identification of an actual framework graphical control remain unresolved. No product code or binaries were changed.

A further real two-thread test opened `BUTTON` via OpenThemeData in one thread and OpenThemeDataEx in another, then closed the latter while the first registration remained pending. Both widths returned the same live handle, CloseThemeData returned S_OK, and the registry conservatively refused the overlapped handle. This validates that specific real API interleaving, not arbitrary concurrent UxTheme behavior. A separate nested-open model found the prior scratch design could transiently recognize the inner handle before the outer registration completed. The revised model suspends recognition while opens remain pending; x86/x64 nested, concurrent, shared-handle, alias, capacity and real API overlap cases passed. A deliberate version without the pending-open guard failed the nested assertion on both widths. The registry remains experimental, has no production integration, and cannot identify a windowless control or handle every unobserved theme-opening path.

A separate test of the documented per-window `SetWindowTheme(panel,L"",L"")` path returned S_OK in self-owned x86/x64 samples. A positive control on each width opened BUTTON against that panel before the call, failed to open it against the panel afterward, and still opened BUTTON with a null HWND. Compared with the corresponding otherwise identical bare capture, all 250x120 parent-client RGB pixels, including the 130x45 SpeedButton area, were identical on both widths. This is consistent with the previously traced framework `OpenThemeData(NULL,L"button")` bypassing the parent-window association; it does not prove all VCL versions, Flat/state variants or all windowless controls behave the same. It uses only the owned panel window, not system-wide theme settings, and all four sample targets exited after WM_CLOSE; the abbreviated driver did not independently verify exit status/job activity. Microsoft documents per-window empty-string behavior at https://learn.microsoft.com/en-us/windows/win32/api/uxtheme/nf-uxtheme-setwindowtheme. No product changes or binary release.
