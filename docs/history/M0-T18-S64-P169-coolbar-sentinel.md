# M0 T18 S64 P169: fail closed on unwritten CoolBar band text

P167 initialized the two-character RB_GETBANDINFOW buffer to zero and used the observed cch update to reject long text. Microsoft documents cch as the input capacity, not a required output length. If a successful native query does not write the buffer and leaves cch unchanged, that zero could be mistaken for an empty caption. This is a simulated compatibility risk, not a defect reproduced in the installed COMCTL implementation. The buffer now starts with nonzero sentinels: no write and nonempty text both reject the grip, while an observed empty caption writes a zero. Existing length, ownership, image, geometry and lifecycle guards remain.

An owned dual-width fixture temporarily patches only its own injected DLL CallWindowProcW import for the target bar and synthesizes a successful query leaving the incoming first character and cch unchanged; the slot is restored before content readback. P167 reports `FAULT_UNWRITTEN hits=1 painted=1` and fails the new assertion on both widths. The candidate reports hits=1, painted=0 on both widths; actual 4096-character captions and short captions also return unchanged and reject painting. This injected scenario is not a claim about current Windows. A separate native scratch probe checked captions of 0, 1, 2, 12, 300 and 4096 characters with 2, 4, 16, 512 and 4097-character buffers, on both widths: on this system insufficient buffers remained unchanged and cch returned required capacity; sufficient buffers contained the expected first character. If an implementation returns an empty string for truncated nonempty text while leaving cch unchanged, this guard still cannot distinguish it: no universal guarantee is claimed.
