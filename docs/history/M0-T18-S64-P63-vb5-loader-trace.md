# M0 T18 S64 P63: VisData startup call trace

A project-authored x86 debugger in task scratch traced a bounded self-owned VisData process on a private desktop. Software breakpoints recorded `LdrLoadDll`, `CoGetClassObject`, `CoCreateInstance`, `LoadRegTypeLib` and `LoadTypeLibEx`; this instrumentation affects only the process created by the probe and is not product code. Both the original and the P54 private-manifest copy still reached the same Error dialog and were reclaimed with empty owned jobs. The private-manifest run recorded 20 loader entries and 20 successful returns; the original recorded 20 entries and 19 successful returns before its error dialog ended observation, so its final call has no observed return. Static imports before the debugger's initial breakpoint and other APIs were not traced. Neither sample produced an observed call to the traced COM creation or `LoadRegTypeLib` entry points before the dialog.

`LoadTypeLibEx` did run. In each sample it succeeded for the task-local MSVBVM50.DLL and its resource `\\2` with mode 1 (`REGKIND_REGISTER`), and for that sample's EXE with mode 2 (`REGKIND_NONE`). The probe did not take a prior registry snapshot or intercept registry writes. Therefore it cannot establish whether the two `REGKIND_REGISTER` calls wrote registration data. This corrects P54's broad statement that the run occurred without registration: no explicit installer, `regsvr32`, or component registration was invoked by the probe, but VB itself requested type-library registration. Do not repeat these runs without isolating or auditing that boundary.

A self-authored negative-control process loaded a deliberately missing DLL and called the monitored typelib and COM APIs with a nonexistent GUID. The tracer observed `LdrLoadDll` returning `c0000135`, `LoadTypeLibEx` returning `80029c4a`, `LoadRegTypeLib` returning `8002801d`, and `CoCreateInstance` returning `80040154`, then reclaimed the owned process. This validates those tested entry and return paths, not every possible loader, COM, registry, or Visual Basic runtime path. The evidence narrows the observed failure but does not identify the actual root cause or establish that VB5 Data is impossible.

No product source, test source, or binary changed. T18/S64 and VB5 Data remain open. This research probe is not an installed component or project dependency.
