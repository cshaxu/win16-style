# M0 T18 S24 P1 — v5 progress color tracking experiments

The S23 real DoubleKiller x86 sample used ComCtl32 5.82 and returned zero from the newer progress color/state getters. S24 investigates a public way to preserve application colors before attempting to style the native client; no production renderer or ABI changed.

A self-contained C witness registers a progress superclass in a newly owned isolated process. Its own `WM_CREATE` sends `PBM_SETBARCOLOR` and `PBM_SETBKCOLOR` before returning. On both x86 and x64 ComCtl32 5.82, a same-thread CBT and call-window observer saw both creation-time setters, their previous values were `0xff000000` (`CLR_DEFAULT`), and the newer color getters returned zero. Later normal sends returned the previous explicit colors. A direct `CallWindowProcW` to the acquired native procedure changed the color but did not pass the call-window observer; the next setter returned the bypassed color. Therefore a cache driven only by that observer is insufficient. The test changes only its own newly created control, restores its thread hooks, destroys the control and exits; it does not probe an existing application with mutating setters.

A separate self-owned process reused this repository's existing startup-transaction trampoline code on the publicly obtained v5 native class window procedure before creating the test control. It observed that same direct call on both widths (one additional native call), while the ordinary call-window observer still saw none. The patch was local to that single test process and ended with it. This is a candidate route, not a product implementation: the test installs after its own loader completes and class registration, while the current product's bootstrap runs inside DllMain and expressly permits no GUI initialization. It has not shown how to safely acquire and hook the procedure before every application can create or mutate a control, handle multiple activation contexts/modules and threads, retain pre-attachment state, or clean up and fall back on failure. No system-wide hook, existing user process injection or shared system setting was used.

Both witnesses are now self-contained native regression cases and distinguish the observed miss from the captured direct call. A separate local model found the native progress class registered before its explicit `InitCommonControlsEx` call on this machine; this observation occurs after process loading and is not evidence that a GUI call is safe inside DllMain. Further implementation requires an independently validated post-loader/pre-use boundary or another complete method, without adding a guessed color or missing setters.

Further scratch-only experiments tested a possible post-loader entry boundary on this machine. A self-owned executable's TLS callback ran before the locally intercepted `BaseThreadInitThunk` on both widths. At that interception, a worker successfully loaded a DLL and queried the progress class, but this is only evidence for those test processes and this system, not a general loader-lock guarantee. The existing hook engine rejected a second transaction with `ERROR_INVALID_STATE` (5023) in both processes. The x86 thunk on this machine used a register-based calling convention, and an initial stdcall prototype did not complete normally; the interface is undocumented, so neither its calling convention nor this boundary is a portable production contract. An earlier TLS callback or another thread can precede the observed boundary. No production hook was installed, and these observations do not prove a safe universal initialization or justify guessing missed colors. The scratch probes remain in `build/t18-s24-progress-colors` while S24 is open.

A separate scratch-only paint witness explored whether a control's actual drawing operations can expose colors without changing target state. On the local x86 and x64 ComCtl32 5.82, an owned smooth progress control with position 42 and explicit bar RGB(11,22,33) and background RGB(44,55,66) drew via `SetBkColor` and `ExtTextOutW`; its own erase followed by `WM_PRINTCLIENT` returned 1 from erase and observed COLORREFs `0x0042372c` and `0x0021160b`, respectively, alongside restored white. The sampled client pixel matched the bar color. The witness first had a bad address selection: a direct-call self-check recorded zero interceptions, so those initial results are invalid and are not evidence. Resolving the actual export addresses corrected the self-check to one brush creation and one fill interception on both widths. This is one locally observed implementation and state, not a documented identification protocol or a complete product solution: empty/full, clipping, partial redraw, themes, reentry, multiple controls, DC and resource ownership, other Windows builds and safe installation must still be established. No application or product code was changed. The probe remains in the registered S24 scratch directory.

The expanded scratch witness tested positions 0, 42 and 100, distinct and equal explicit colors, and three DC clip regions on both widths. At position 0 the distinct bar color did not occur in observed `SetBkColor` calls, whereas at 42 and 100 it did. With equal colors, comparisons against the two expected values naturally could not distinguish their roles. The observed `ExtTextOutW` operations began with an opaque full-client background followed, when filled, by one-pixel-wide bar rectangles; the clipping experiments still issued the same observed call counts. This is local implementation evidence, not an API guarantee or proof of all actual partial-update paths. A further owned-control comparison used `CLR_DEFAULT` and then explicit colors equal to two sampled output pixels: those two pixels matched, but the first 32 observed background-color calls and the `ExtTextOutW` counts differed (148 versus 150). It does not prove the full images equal or the default/explicit states indistinguishable; in particular, inferring the original state from one sampled pixel is unjustified. The test sent erase and print messages only to its own witness and does not establish that doing so to arbitrary applications is safe. A reliable, content-neutral and lifecycle-safe production contract remains unproven.
