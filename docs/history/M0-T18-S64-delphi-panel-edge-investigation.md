# M0 T18 S64: Delphi ordinary panel edge investigation

The published package was observed with self-owned DelphiVCL4Python 1.0.7 `TPanel` samples in x86 and x64. On a 250x120 client at actual 144 DPI, default `bvRaised` and `bvLowered` each drew two three-point `Polyline` paths at the full outer edge, in opposite `COLOR_BTNHIGHLIGHT`/`COLOR_BTNSHADOW` order. `bvNone` drew neither; `BevelWidth=2` drew a second inner pair at inset one. A parent-coordinate `FillRect` and separate caption draw were observed; neither alone establishes safe background replacement. A red Color assignment was visible as a public property but the themed sample's observed parent fill stayed system colored, so this experiment does not establish custom background handling. The observer was installed in and restored from only the self-owned sample, and all runs exited with their jobs empty. These observations concern one runtime/version and DPI, not all Delphi panel paths.

A scratch-only observer let the original `Polyline` execute then overlaid its observed outer shadow line in black, leaving the light line, inner bevel, caption and background alone. For both widths, comparing exact 250x120 RGB client buffers against separate same-configuration published-package captures showed: default 369 changed pixels, lowered 367, width two 369, and no-bevel zero. In every comparison zero changed pixels lay outside the outermost client row/column. This does not verify child contents, reparenting, clipping, application painting, DPI other than 144, GDI/pen restoration across all paths, or actual product safety. Observer logs and captures reside in registered ignored `build/t18-s64-vb-panel`. A first `bvNone` setup used an invalid numeric enum and failed before showing; only the corrected string-property run is counted.

A possible next prototype is a paint-scope witness that validates both original outer polylines, their current pens, exact geometry, same DC, real class and runtime caller, and matching complementary system colors before changing only the shadow stroke. Unknown, partial, custom, disabled and incompatible cases must remain native. The two-path witness, child/clip and callback boundaries, colors, caller/module, lifecycle and both-bit-width tests are not yet implemented or proven. No product code or binaries were changed by this investigation. M0/T18/S64 stay open.

A later scratch candidate requires both complementary system-color outer `Polyline` calls in the same owned `WM_PAINT`, same current DC, exact geometry, same process/thread and same parent/class/call-site module. It replays only the shadow line in black with saved/restored DC state. It requires the parent to remain the same between the two calls. Actual x86/x64 runtime captures at 144 DPI each showed 369 changed outer pixels for default and width-two, 368 for lowered, and zero for no bevel; no interior pixels changed. Separate real panels with child `TButton` showed 369 outer changes and zero differences within the child rectangle per width. The capture is a client DC and is not proof of physical input.

A self-authored model passed on both widths for paint outside scope, no edge, custom pen, incomplete pair, interior-only clip, expected pair, partial clip, parent change/retirement, parent change between paired calls, disabled fallback/re-enable, wrong parent owner, and three repeat paints with observed process GDI 12 to 12. The published package failed the positive matching assertion on both widths. A deliberately broken scratch candidate without the mid-pair parent check was detected on x86. An early model run used `UpdateWindow` while the test parent was hidden by startup flags; it did not dispatch the expected paint and is excluded. The corrected model explicitly shows the parent and synchronously sends `WM_PAINT`. The model and candidate remain scratch only; final inclusion, installed-package verification, further reentry and exception/resource testing remain.

Actual four-file candidate real samples preserved outer-only differences after fixing the child button focus to the same state in both runs. An initial child comparison found 258 interior differences: the baseline button had focus cues and the candidate button did not. That uncontrolled comparison is not counted; explicit `SetFocus` plus `GetFocus`/button-state checks gave zero child and interior differences on both widths.

An additional wrong-caller probe reached its assertions but repeatedly waited during destruction of its hidden second parent, even when the foreign-caller case was skipped. A captured self-owned x86 process had MSCTF and COM worker threads and a waiting UI thread, but the diagnostic stack did not identify a complete cause. Disabling IME for this self-owned ASCII fixture thread (`ImmDisableIME(0)`, the existing project's test isolation approach) let the same probe finish. This is correlation and a test-environment adjustment, not proof of a product defect or that the original wait was caused by IME. The first candidate's 20 focused cases passed; the final model adds the wrong-caller case and IME isolation, requiring a fresh same-snapshot package and test.
