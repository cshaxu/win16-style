# M0 T18 S64 P65: bounded VisData database-window investigation

The P64 `c000041d` report had exception address `KERNELBASE.dll+1505a3`, the same address used for a shared loader-return breakpoint. Earlier traces had shown multiple threads reaching that return while a breakpoint was already in use. This is evidence that the debugger could interfere; it does not establish the cause of either P64 process exit. A new scratch observer omitted loader and COM return breakpoints and removed its remaining non-registry breakpoints before the database menu action. It retained the P64 target-only registry simulation and its documented limitations. A negative-control process confirmed the guarded key creation and value assignment were simulated while its unique test key remained absent.

With that observer the real VB5 MDI opened the standard Microsoft Access file dialog instead of immediately exiting. Two attempts to populate its filename and post the dialog command/button left the dialog visible; they are not successful file selections. A separate scratch-only hook then simulated `GetOpenFileNameA/W` success with a fixed path to the self-owned `research.mdb`. An independent project-authored fixture called the W entry point and checked the returned exact path; the real VisData execution called the A entry point. Both were bounded owned jobs and were reclaimed. The sample showed child windows titled `Database Window` and `SQL Statement`, with an OCX `TreeViewWndClass` child, after the simulated selection. The source's `ShowDBTools` path shows those forms for an open database, but this diagnostic did not establish the database tree contents or successfully observe a Data control or record navigation. One first-chance `c000008f` occurred in a system DLL; it was not established as the cause of a failure.

The test used an existing private Biblio copy. Its SHA-256 remained `dfb0194a5b9d7986d5a5ce2ca86567c245ebb97a3792dd1142b1327a077b599c`; the specifically checked VisData typelib and CLSID keys and the fixture test key were absent afterwards. The targeted registry guard does not audit every possible registry operation and does not prove the entire registry unchanged. Native file selection and application registration were simulated; this result is not normal unmodified sample behavior or an end-to-end acceptance pass.

No product source, tracked test source, resources, or binaries changed. Both published directories still match each other. VB5 Data creation, database tree contents and navigation remain unresolved; T18 and S64 remain open.
